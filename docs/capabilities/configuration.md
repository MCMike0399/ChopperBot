# Configuration capability (admin console)

> Topic doc — part of the [CLAUDE.md](../../CLAUDE.md) router. Read it BEFORE working in this area, and keep it current in the same change as any behavior change (doc protocol ①/② in the index).

Lives in the single hardcoded `CHOPPERBOT_CONFIG_CHANNEL_ID`. It composes the core routing/discovery/system source, per-capability admin sources, `config_moderation` and `config_db`; each multiplexes operations behind an `action` parameter.

- **Authorization is a code gate, not the channel (added 2026-08-13).** Channel access used to _be_ the authorization — the preamble said so out loud. That was always thin (it rests on Discord channel overwrites being perfect, forever) and cannot authorize the console by itself: this console re-binds any channel to any capability, reads the whole DB and purges capability data. `buildTurn` now calls `isModTurn()` (moderation-tier role or Administrator, see docs/framework.md) and a caller who fails it gets a refusal prompt and **zero tools** — `composeToolSources([])` — so there is nothing for an injected instruction to reach. It **fails closed**: an unresolvable member (DM, failed fetch) is not a mod. Denials are logged `configuration.turn_denied`.
   - **Know who passes before you rely on it:** `npx tsx scripts/verify-mod-authority.ts` (read-only; resolves both authority tiers against every guild the bot is in). Running it on 2026-08-13 is what surfaced that the console then lived in a **private lab server with no approver role and no Administrator role** — i.e. drivable only by that guild's owner. That finding is what prompted the migration below; re-run it after any change to `CHOPPERBOT_CONFIG_CHANNEL_ID` or `set_moderation_roles` / `set_event_roles`.
   - **The console moved into Revolución Z on 2026-08-13** — `#chopperbot-monitor` (`1537527391205720114`), 🚓Moderación🚓 category, hidden from `@everyone`. The two layers now agree instead of one carrying everything: Discord's overwrites let 🚓Moderación🚓 + ⭐Administradora⭐ _see_ the channel, and the code gate independently checks that the author passes the moderation tier (four staff role IDs or Administrator). Alerts moved with it — see the `CHOPPERBOT_CONFIG_CHANNEL_ID` entry in [environment.md](../environment.md) for the two-step migration (the old binding row does **not** clean itself up).
- **`config_system action:health` is the "¿cómo va el bot?" entry point** (added 2026-08-03, `configuration/health.ts`). One call returns an overall `status` (`ok`/`degraded`/`down`), a Spanish `problems` list (each naming the fix), and per-subsystem blocks: `runtime`, `llm`, `capabilities`, `discord`, `instagram_monitor`, `calendar`, `file_scanner`, `event_intake`, `moderation`. The moderation block reports the configured/default workspace, escalation ping IDs and “acciones de moderación en 30 días” grouped by outcome. The preamble tells the model to lead with the verdict and **not** to chain the per-capability `status` tools to assemble an overview. The `calendar` block also covers the daily announcement (channel, hour, mentions, last sent) and flags **events in the next 24 h with no Discord scheduled event** — otherwise a link-less announcement is only visible by watching `#anuncios`.
   - **Why it exists:** the console had `bot_info` (uptime/Node/DB size) plus a separate `status` on `config_instagram`/`config_filescanner`/`config_eventintake`, so the commonest operator question took 4–5 calls — and three things were **not observable at all**: whether the LLM is actually answering, which capabilities **failed `init()`**, and the calendar's publish state (exactly what hid the Aug 1 rollover miss).
   - **`bot_info` used to name the wrong brain.** It reported `BEDROCK_MODEL_ID` (Sonnet) as "the model", which was already legacy and off every hot path by the 2026-07-13 Kimi repoint, and both that var and the whole Bedrock backend were deleted in the v4.1 migration (2026-09-14). Both `bot_info` and `health` now report **ONE** backend: the `text` block carries `textBackend.provider` + `textBackend.modelId` + `textBrainDisplayName()` (live **DeepSeek V4.1 Flash**, `deepseek-flash`), and the `vision` block **mirrors it exactly** — same `backend`, same `model` — because the model is natively multimodal, with a `note` saying so. The `vision_model` key survives only because operators ask "what reads the flyers?": the honest answer is the same model. They used to hardcode Kimi even after the cutover — that lie is gone. **Don't reintroduce `BEDROCK_MODEL_ID` here** — it would again tell operators the bot runs on a model it never calls.
   - **Boot failures are plumbed, not guessed.** `app.ts` collects `{id, error}` for every capability whose `init()` threw and hands it to `configCap.recordSkippedCapabilities()` after the init loop, so health reports _why_ (`file_scanner: VIRUSTOTAL_API_KEY not set`) rather than the operator diffing the registry against a hardcoded expected list. It also flags `orphan_bindings` (a channel bound to an unregistered capability → messages there are silently ignored).
   - **Every block is independently guarded** by a `safe()` wrapper: an un-migrated or broken subsystem degrades to `{ error }` for that block while the rest of the report still returns — the failure mode that matters most is precisely when something is broken. `llmHealth.snapshot()` (added alongside) exposes consecutive failures / last success / last error; it's **process-local and resets on restart**, as does IG's `requests_24h`, which is why a `< 10 min` uptime is itself listed as a problem.
   - **Gotcha — don't report role settings raw.** `getModRoles()` / `getModerationRoles()` return `[]` when unconfigured, but matching falls back to `DEFAULT_EVENT_ROLES` / `DEFAULT_MOD_ROLES`; health reports the effective lists (`authority.{moderation,events}` + `event_intake.mod_roles_effective`) so an empty list isn't misread as "nobody can approve".
- **Verify:** `npx vitest run src/capabilities/configuration` (incl. `health.test.ts` — triage behavior + the broken-subsystem degradation), the read-only `npx tsx scripts/verify-config-health.ts [--json]` (builds the report against the LIVE DB; also a shell-side triage tool for when Discord itself is the broken thing), and the live `LOG_LEVEL=warn npx tsx scripts/config-health-smoke.ts` (drives the real model: asserts ONE `health` call, no per-capability chaining, a human summary instead of a JSON dump, and that "¿con qué modelo piensa?" names the **single** multimodal brain — one model for text **and** images — and never the retired Sonnet/Claude). **Known gap:** that script's Scene 3 still carries a `check(/nova/i.test(reply))` for "named Nova for images" and a banner printing `+ Nova (imágenes)` — leftovers from the two-backend era. The model is now _prompted_ not to name Nova (the configuration preamble says so outright), so that check is expected to fail until `scripts/config-health-smoke.ts` itself is updated; it is a script defect, not a bot behavior.
- **Test gotcha:** `dotenv` loads the real `.env` into the vitest process, so any assertion about an _unset_ optional env var (e.g. `CALENDAR_OUTPUT_CHANNEL_ID`) must stub `config.<KEY>` and restore it — otherwise the test passes or fails depending on the host's `.env`.

## Separate authority settings — v2.3.1

The console requires **moderation**, independently of event approval. Gestión alone receives zero console tools. `config_eventintake set_mod_roles` remains an alias for `set_event_roles` (event/calendar authority); `set_moderation_roles` changes console/IG/review/sanction/recording authority separately. Both accept names/IDs and empty resets defaults. The effective events list always includes moderation roles; event settings never grant moderation. `status` and `config_system health` expose both effective tiers and their configured/default source under `authority`.

Migration v3 preserves the existing event list and initializes the new moderation list to safe defaults. Verified with real role IDs, in-memory migration/availability tests and read-only live callers.

## Moderator workspace administration (v2.4.0)

`config_moderation` edits framework-owned per-guild settings, rather than event-intake state: the workspace is shared by general_chat, evidence delivery, escalation and the console. Migration `__framework__` v2 owns `framework_moderation_settings` and `framework_moderation_trail`.

- `status`: effective `moderation_channel_id`, `escalation_ping_role_ids`, and action/outcome counts over 30 days.
- `set_channel {channel_id}`: live replacement in this guild. Requires a restricted text/news channel whose audience can read guild audit information; unresolved roles/users or a broader audience fail closed. Log channels cannot be selected. Use an unbound channel so general_chat can serve partner turns; this tool does not modify bindings.
- `set_escalation_pings {role_ids}`: replace at most four existing moderation-role IDs, or `[]` for silence. Rejects everyone and non-moderation roles. The send uses an explicit allowlist, with no user/reply/mass parsing. Default is no ping. Alta always stays silent; only urgente uses this allowlist.

All operations re-fetch the requesting member and console access and recheck moderation at invocation. Empty ping lists remain empty; they are not re-seeded at restart. The default RevZ workspace is `1436206995140247652`; other guilds require configuration. Changes take effect on the next turn/send, without restart. RevZ now has `1436055845392879778` as the sole escalation ping ID, applied through this validated tool and verified with status. No other setting changed.

`config_system health` includes `moderation` (workspace/pings + `actions_30_days`). `config_db list_tables`, schema/inspection and read-only queries include both framework tables automatically. Trail columns record guild, actor, target, action, short reason/summary, trigger, channel, outcome and timestamp. Verified refusals create no Discord line; unconfirmed outcomes explicitly do not prove the effect failed. Successful actions are logged to the workspace; log failure is separately journalled and never retries a sanction. Framework records are outside capability-scoped purges.

Verification: real-ID availability/revocation/settings-independence tests, mocked effects, 1,407 tests overall and green typecheck/build. The live bot no longer has Administrator: Técnico was removed by an admin after 25 minimal channel/category overwrites. Read-only authority and workspace/log probes pass. `config_moderation status` verifies the default workspace and the sole configured ping ID. No community announcement was published for 2.5.0.
