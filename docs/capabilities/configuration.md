# Configuration capability (admin console)

> Topic doc — part of the [CLAUDE.md](../../CLAUDE.md) router. Read it BEFORE working in this area, and keep it current in the same change as any behavior change (doc protocol ①/② in the index).

Lives in the single hardcoded `CHOPPERBOT_CONFIG_CHANNEL_ID`. It composes six tool sources (`source.ts` core + the four per-capability admin sources + `db-source.ts`), each multiplexed behind an `action` parameter.

- **Authorization is a code gate, not the channel (added 2026-08-13).** Channel access used to _be_ the authorization — the preamble said so out loud. That was always thin (it rests on Discord channel overwrites being perfect, forever) and stopped being acceptable when the bot was granted **Administrator**: this console re-binds any channel to any capability, reads the whole DB and purges capability data. `buildTurn` now calls `isModTurn()` (approver role or Administrator, see docs/framework.md) and a caller who fails it gets a refusal prompt and **zero tools** — `composeToolSources([])` — so there is nothing for an injected instruction to reach. It **fails closed**: an unresolvable member (DM, failed fetch) is not a mod. Denials are logged `configuration.turn_denied`.
   - **Know who passes before you rely on it:** `npx tsx scripts/verify-mod-authority.ts` (read-only; resolves the approver tokens against every guild the bot is in). Running it on 2026-08-13 is what surfaced that the console then lived in a **private lab server with no approver role and no Administrator role** — i.e. drivable only by that guild's owner. That finding is what prompted the migration below; re-run it after any change to `CHOPPERBOT_CONFIG_CHANNEL_ID` or `set_mod_roles`.
   - **The console moved into Revolución Z on 2026-08-13** — `#chopperbot-monitor` (`1537527391205720114`), 🚓Moderación🚓 category, hidden from `@everyone`. The two layers now agree instead of one carrying everything: Discord's overwrites let 🚓Moderación🚓 + ⭐Administradora⭐ _see_ the channel, and the code gate independently checks that the author holds an approver role (all five resolve in this guild) or Administrator. Alerts moved with it — see the `CHOPPERBOT_CONFIG_CHANNEL_ID` entry in [environment.md](../environment.md) for the two-step migration (the old binding row does **not** clean itself up).
- **`config_system action:health` is the "¿cómo va el bot?" entry point** (added 2026-08-03, `configuration/health.ts`). One call returns an overall `status` (`ok`/`degraded`/`down`), a Spanish `problems` list (each naming the fix), and per-subsystem blocks: `runtime`, `llm`, `capabilities`, `discord`, `instagram_monitor`, `calendar`, `file_scanner`, `event_intake`. The preamble tells the model to lead with the verdict and **not** to chain the per-capability `status` tools to assemble an overview. The `calendar` block also covers the daily announcement (channel, hour, mentions, last sent) and flags **events in the next 24 h with no Discord scheduled event** — otherwise a link-less announcement is only visible by watching `#anuncios`.
   - **Why it exists:** the console had `bot_info` (uptime/Node/DB size) plus a separate `status` on `config_instagram`/`config_filescanner`/`config_eventintake`, so the commonest operator question took 4–5 calls — and three things were **not observable at all**: whether the LLM is actually answering, which capabilities **failed `init()`**, and the calendar's publish state (exactly what hid the Aug 1 rollover miss).
   - **`bot_info` used to name the wrong brain.** It reported `BEDROCK_MODEL_ID` (Sonnet) as "the model", which has been legacy and off every hot path since the 2026-07-13 Kimi repoint. Both `bot_info` and `health` now report the **selected** text brain (`textBackend.provider` + `textBackend.modelId` + `textBrainDisplayName()`, live **DeepSeek V4 Flash** since 2026-08-13) + `vision_model` (Nova Lite). They used to hardcode Kimi even after the cutover — that lie is gone. **Don't reintroduce `BEDROCK_MODEL_ID` here** — it would again tell operators the bot runs on a model it never calls.
   - **Boot failures are plumbed, not guessed.** `app.ts` collects `{id, error}` for every capability whose `init()` threw and hands it to `configCap.recordSkippedCapabilities()` after the init loop, so health reports _why_ (`file_scanner: VIRUSTOTAL_API_KEY not set`) rather than the operator diffing the registry against a hardcoded expected list. It also flags `orphan_bindings` (a channel bound to an unregistered capability → messages there are silently ignored).
   - **Every block is independently guarded** by a `safe()` wrapper: an un-migrated or broken subsystem degrades to `{ error }` for that block while the rest of the report still returns — the failure mode that matters most is precisely when something is broken. `llmHealth.snapshot()` (added alongside) exposes consecutive failures / last success / last error; it's **process-local and resets on restart**, as does IG's `requests_24h`, which is why a `< 10 min` uptime is itself listed as a problem.
   - **Gotcha — don't report `mod_roles` raw.** `EventIntakeStore.getModRoles()` returns `[]` when unconfigured, but `isModByRole` falls back to `DEFAULT_MOD_ROLES`; health reports `mod_roles_effective` + `mod_roles_source` so an empty list isn't misread as "nobody can approve".
- **Verify:** `npx vitest run src/capabilities/configuration` (incl. `health.test.ts` — triage behavior + the broken-subsystem degradation), the read-only `npx tsx scripts/verify-config-health.ts [--json]` (builds the report against the LIVE DB; also a shell-side triage tool for when Discord itself is the broken thing), and the live `LOG_LEVEL=warn npx tsx scripts/config-health-smoke.ts` (drives the real model: asserts ONE `health` call, no per-capability chaining, a human summary instead of a JSON dump, and that "¿con qué modelo piensa?" names the **selected** text brain + Nova and never Sonnet).
- **Test gotcha:** `dotenv` loads the real `.env` into the vitest process, so any assertion about an _unset_ optional env var (e.g. `CALENDAR_OUTPUT_CHANNEL_ID`) must stub `config.<KEY>` and restore it — otherwise the test passes or fails depending on the host's `.env`.
