# Configuration capability (admin console)

> Topic doc — part of the [CLAUDE.md](../../CLAUDE.md) router. Read it BEFORE working in this area, and keep it current in the same change as any behavior change (doc protocol ①/② in the index).


Lives in the single hardcoded `CHOPPERBOT_CONFIG_CHANNEL_ID`; channel access **is** the authorization. It composes six tool sources (`source.ts` core + the four per-capability admin sources + `db-source.ts`), each multiplexed behind an `action` parameter.

- **`config_system action:health` is the "¿cómo va el bot?" entry point** (added 2026-08-03, `configuration/health.ts`). One call returns an overall `status` (`ok`/`degraded`/`down`), a Spanish `problems` list (each naming the fix), and per-subsystem blocks: `runtime`, `llm`, `capabilities`, `discord`, `instagram_monitor`, `calendar`, `file_scanner`, `event_intake`. The preamble tells the model to lead with the verdict and **not** to chain the per-capability `status` tools to assemble an overview. The `calendar` block also covers the daily announcement (channel, hour, mentions, last sent) and flags **events in the next 24 h with no Discord scheduled event** — otherwise a link-less announcement is only visible by watching `#anuncios`.
  - **Why it exists:** the console had `bot_info` (uptime/Node/DB size) plus a separate `status` on `config_instagram`/`config_filescanner`/`config_eventintake`, so the commonest operator question took 4–5 calls — and three things were **not observable at all**: whether the LLM is actually answering, which capabilities **failed `init()`**, and the calendar's publish state (exactly what hid the Aug 1 rollover miss).
  - **`bot_info` used to name the wrong brain.** It reported `BEDROCK_MODEL_ID` (Sonnet) as "the model", which has been legacy and off every hot path since the 2026-07-13 Kimi repoint. Both `bot_info` and `health` now report `text_model` (Kimi) + `vision_model` (Nova Lite) instead. **Don't reintroduce `BEDROCK_MODEL_ID` here** — it would again tell operators the bot runs on a model it never calls.
  - **Boot failures are plumbed, not guessed.** `app.ts` collects `{id, error}` for every capability whose `init()` threw and hands it to `configCap.recordSkippedCapabilities()` after the init loop, so health reports *why* (`file_scanner: VIRUSTOTAL_API_KEY not set`) rather than the operator diffing the registry against a hardcoded expected list. It also flags `orphan_bindings` (a channel bound to an unregistered capability → messages there are silently ignored).
  - **Every block is independently guarded** by a `safe()` wrapper: an un-migrated or broken subsystem degrades to `{ error }` for that block while the rest of the report still returns — the failure mode that matters most is precisely when something is broken. `llmHealth.snapshot()` (added alongside) exposes consecutive failures / last success / last error; it's **process-local and resets on restart**, as does IG's `requests_24h`, which is why a `< 10 min` uptime is itself listed as a problem.
  - **Gotcha — don't report `mod_roles` raw.** `EventIntakeStore.getModRoles()` returns `[]` when unconfigured, but `isModByRole` falls back to `DEFAULT_MOD_ROLES`; health reports `mod_roles_effective` + `mod_roles_source` so an empty list isn't misread as "nobody can approve".
- **Verify:** `npx vitest run src/capabilities/configuration` (incl. `health.test.ts` — triage behavior + the broken-subsystem degradation), the read-only `npx tsx scripts/verify-config-health.ts [--json]` (builds the report against the LIVE DB; also a shell-side triage tool for when Discord itself is the broken thing), and the live `LOG_LEVEL=warn npx tsx scripts/config-health-smoke.ts` (drives the real model: asserts ONE `health` call, no per-capability chaining, a human summary instead of a JSON dump, and that "¿con qué modelo piensa?" names Kimi+Nova and never Sonnet).
- **Test gotcha:** `dotenv` loads the real `.env` into the vitest process, so any assertion about an *unset* optional env var (e.g. `CALENDAR_OUTPUT_CHANNEL_ID`) must stub `config.<KEY>` and restore it — otherwise the test passes or fails depending on the host's `.env`.
