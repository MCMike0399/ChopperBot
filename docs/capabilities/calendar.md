# Calendar capability (global)

> Topic doc — part of the [CLAUDE.md](../../CLAUDE.md) router. Read it BEFORE working in this area, and keep it current in the same change as any behavior change (doc protocol ①/② in the index).


Rewritten 2026-06-21 from per-user to a single **global** server calendar. Mods talk to it in the bound **input** channel; rendered month PDFs + a master ICS are published to a separate **output** channel.

- **Writing is mod-only, in code (added 2026-08-13).** The prompt always said "cualquier moderadorx de este canal", but nothing checked — the real guarantee was "whoever can post in the channel", and an event created here is *published* state (month PDF, ICS, the Discord events list, the next morning's announcement to the whole server). `buildTurn` now calls `isModTurn()` (approver role or Administrator — same list as event_intake, see docs/framework.md); a non-mod gets the **read-only slice** (`calendar_list_upcoming` / `calendar_search_events` / `calendar_get_event`, no publisher, no Discord-event syncer, attachments not offered as banners) plus a short "solo consulta" prompt, and `allowWrite:false` re-refuses at the point of effect. Fails closed. Asking what's coming up stays open to everyone in the channel.
- **Two channels, two roles.** The capability is bound to the INPUT channel via the normal routing table (`config_bindings action:bind … capability:calendar`). The OUTPUT channel is a calendar-specific setting: seeded on first boot from `CALENDAR_OUTPUT_CHANNEL_ID` into `calendar_settings` (single row), then the DB value wins (change it from the config channel: `config_calendar action:set_output_channel`). Resolution order at runtime: DB setting → `CALENDAR_OUTPUT_CHANNEL_ID` → none (publish becomes a no-op reported as `published.ok=false`).
- **Global store** (`store.ts`, migration **v5**): `calendar_events` dropped per-user scoping (`created_by` is now attribution only — any mod sees/edits any event). v5 also adds `calendar_published` (tracks the Discord message id per artifact so we EDIT in place) and `calendar_settings`. Recurrence (`daily`/`weekly`/`monthly` + optional `recurrence_until`) lives in `recurrence.ts`; `expandOccurrences` is reused by the snapshot, the renderer, and the ICS.
- **Bounded recurring series** (`recurrence_count` / `recurrence_until_iso`, added 2026-08-03, **no migration**). A series can end. `recurrence_count` ("cada martes, 4 veces") and `recurrence_until_iso` ("hasta el 31 de agosto") are two spellings of the same bound and are **mutually exclusive** (passing both is a tool error, not a silent pick); both resolve at write time into the single pre-existing `recurrence_until` column via the pure `untilFromCount()` in `recurrence.ts` — which is why no schema change was needed and the renderer / ICS `UNTIL=` / `expandOccurrences` all kept working untouched. `recurrence_count: 1` collapses to a one-off rather than a degenerate 1-instance series. On update (scope `series`) a count is measured against the series' **effective** start and frequency, so a single call that also moves the series or changes its rhythm re-bounds against what it will BE, not what it was; `recurrence_until_iso: null` clears the bound, and dropping `recurrence_freq` clears it too. Tool results carry `occurrence_count` / `recurrence_until_local` / `recurrence_open_ended` so confirmations are concrete ("semanal, 4 sesiones, la última el Tue Jul 28").
  - **Why this exists (real failure, journal 2026-07-10):** a mod booked a weekly book club and the bot created **four separate one-off rows** (#14/#15/#16/#17, plus #11 and later #19 — six rows for one series) because the tools only offered "weekly → forever" *and* the prompt then said `NUNCA preguntes "¿hasta cuándo se repite?"`. That directive is now **reversed**: the prompt asks about the range **once, non-blocking**, treats "todo julio"/"por un mes"/"6 sesiones" as a range to resolve, and still creates an **indefinite** series when the mod has no end date (a permanent asamblea is legitimate — 3 such series exist live). Scenes 8–10 of `scripts/calendar-bedrock-smoke.ts` replay this against the real model; the hard check is "ONE row, bounded".
  - **Theming one session is its own tool — `calendar_set_session_theme`** (added 2026-08-13, v1.19.0). The community's weekly clubs decide the night's movie/theme one or two days before, often by just sending the flyer. That is an occurrence override (title + optional description + optional same-day retime), and the generic update tool already did it — but it asks the model to assemble scope + anchor + ISO math, and live on 2026-08-13 it instead created a duplicate "Cine Club: Persepolis" series for the week's film. The narrow tool takes `id` + `occurrence_date_iso` + `title` (+ optional `description`/`start_at_iso`/`location`), refuses non-recurring masters and cross-day retimes, then republishes and **creates-or-refreshes** the Discord event (an unlinked series gets one — the theme being decided late is exactly when the Discord event doesn't exist yet). The system prompt carries the matching rule: "la peli/tema de la semana NO es un evento nuevo" — search the ACTIVITY name ("club de cine"), never the movie title, and never create. Covered by `__tests__/set-session-theme.test.ts`; drive it by hand with `scripts/calendar-tool.ts calendar_set_session_theme '<json>'`.
- **Recurring-event exceptions** (migration **v6**, `calendar_event_overrides`, added 2026-06-21): edit or cancel a SINGLE occurrence, or "this and following". A row overrides/cancels the occurrence whose ORIGINAL anchor time is `occurrence_start_at` (NULL field = inherit); `expandOccurrences` applies them (cancel → skip, retime → shifted, same-day only). The tools `calendar_update_event`/`calendar_delete_event` take a **`scope`**: `series` (default; also for one-offs), `occurrence` (just `occurrence_date_iso`), or `following`. "Following" is a **series split** (no override rows): the original master's `recurrence_until` is truncated to just before the split and a NEW master is created from the split point (delete-following just truncates). Splitting at the first occurrence collapses to a whole-series edit. A whole-series `start_at`/`recurrence_freq` change wipes the master's overrides (the rhythm changed). The prompt makes the model ASK "¿solo ese día, este y los siguientes, o toda la serie?" when scope is ambiguous, and the tool result carries `updated_scope`/`deleted_scope`.
- **Follow-up conversation** needs no new infra — the existing reply-chain `buildHistory` already threads multi-turn context. The system prompt (`capability.ts`) drives it: require title + start date/time before creating, ask one concise question at a time for missing/ambiguous bits (location, "¿se repite?", and for a series "¿cuántas sesiones o hasta cuándo?"), Spanish-first. Only title + time + (date or cadence) are blocking; everything else asks at most once and never holds up the create.
- **PDF rendering** (`render.ts` + `template-geometry.ts`). The 7 templates in `calendar/` (Jun–Dec 2026, **not gitignored** → they deploy with the repo and are read at runtime from the repo root) are Canva designs with the grid, day numbers and branding already drawn. `scripts/calibrate-calendar-templates.ts` bakes per-month grid geometry into `template-geometry.generated.ts` (poppler, **dev-time only**): **rows** come from the day-number text bounding boxes (`pdftotext -bbox`); **columns** come from detecting the true vertical grid lines in a grayscale raster (`pdftoppm -gray`), because the day numbers are right-aligned and inset ~8px from the real cell border — using the text edge made event blocks bleed left across the gridline (fixed 2026-06-21). The horizontal grid is identical across templates, so the calibration applies a **consensus** column set to all 7 (one template's line-detection miss can't desync it). Row pitch differs (~97pt for 5-row months, ~80pt for the 6-row Aug/Nov). Each day's (row,col) is computed **arithmetically** (Monday-first, fixed UTC-6) by the pure grid math in `grid.ts`, which is shared by the renderer and the publisher (so both agree on placement). The renderer (pdf-lib, standard Helvetica) overlays compact red "event blocks" (bold time + title) into the cell; recurring events expand so a weekly series lands in every week and every month. Text is sanitized to WinAnsi (emoji/CJK stripped, smart-punctuation folded) so pdf-lib never throws. **Re-run the calibration script if the templates are ever replaced.**
- **PNG hero** (`raster.ts`): Discord shows a PDF as a non-previewing download card, so the publisher rasterizes each composed month PDF to a **PNG via `pdftoppm` at 150 DPI** (3000×1688, ~0.65 MB) and attaches **only the PNG** so Discord renders it inline (the PDF is dropped — cleaner cards; re-add it to the payload if print-quality downloads are wanted again). This is a **runtime** poppler dependency (installed at `/usr/bin`, on the systemd PATH); if it's ever missing, raster throws and the publisher falls back to attaching the PDF so the month still posts (`calendar.raster_failed` logged once).
- **ICS** (`ics.ts`): one VEVENT per master with RRULE for recurring series (never pre-expanded), a fixed-offset `VTIMEZONE America/Mexico_City` (-0600), stable UIDs (`chopperbot-cal-<id>@revolucionz`) so re-importing updates rather than duplicates, RFC-5545 escaping + 75-octet line folding. Per-occurrence exceptions map to standard iCal: a cancelled occurrence → `EXDATE` on the master VEVENT; a retimed occurrence → a second VEVENT with the same UID + `RECURRENCE-ID` (original anchor) and the new DTSTART/SUMMARY. (A downloaded `.ics` is a one-time import snapshot — there's no hosted webcal URL, so the copy refreshes on the single ICS message but members re-import to pick up changes.)
- **Publishing** (`publisher.ts`, `OutputChannelPublisher`): every mutation (plus bot startup and the month-rollover watcher, both via `CalendarCapability`) calls **`reconcile()`** — a single idempotent op that makes the output channel match the DB. reconcile renders each desired month (PDF + PNG hero, concurrently), edits its tracked message in place (`calendar_published`), **deletes** any tracked card no longer desired, and refreshes the single ICS message. Per month: one message = **PNG hero** (PDF only as a raster fallback). The ICS is a **single dedicated message**. Best-effort: failures never fail the DB mutation; the tool result carries a `published` summary (`posted`/`removed`) the model relays. `calendar_publish` just forces a `reconcile()` on demand.
- **The desired card set** is the pure, unit-tested `desiredMonthKeys(events, nowMs)` (exported from `publisher.ts`). The board is a **live board, not an archive**: the **current month always** (even with zero events — the caption reads "sin eventos por ahora"), plus every **FUTURE** month containing a **one-off** event, and **never a past month**. Two invariants it encodes:
  - A **recurring series never spawns future-month cards** (2026-06-21 bug: one weekly event blasted all 7 months / 8 messages). It shows on the current month's card, and reaches future months as they become current; meanwhile it's in the ICS.
  - **Past months are pruned** (changed 2026-08-03). Previously the set was "every month with a one-off + current month", so a past month with a one-off stayed desired *forever* — on 2026-08-03 the live board still showed June and July. "Current month always" also matters mechanically: it's what guarantees the rollover trigger below resolves.
- **Month-rollover auto-publish** (added 2026-08-03, `CalendarCapability`). `reconcile()` used to run **only** on a mutation or at boot, so a month rollover on a long-running process published nothing: the bot had been up since Jul 29 and on Aug 3 the board still showed June+July with no August card. `start()` now also arms a `setInterval` (`ROLLOVER_CHECK_MS`, 10 min — one SQLite read per tick) that calls `checkMonthRollover()`.
  - The trigger is the pure `monthPublishAction(currentMonthKey, isPublished)` and is deliberately **stateless — no "last rollover" timestamp and no migration**. Since the board always keeps a card for the current month, a **missing `pdf:<currentMonth>` row in `calendar_published` means "this month isn't published yet"**. Consequences that are tested: a restart can't double-post (the row lives in SQLite), and a failed publish leaves the row absent so the next tick retries by itself.
  - Rollover also **prunes the previous month's card** (same reconcile), so Sep 1 replaces the August card rather than stacking on it.
  - Boot logs `calendar.rollover_watch_started {check_every_min, current_month, verdict}` — the watcher is otherwise silent until a month actually turns, so this is the only way to confirm it's armed without waiting for the 1st. A rollover logs `calendar.rollover.publishing` then `calendar.rollover_reconcile`.
  - **Templates are finite (Jun–Dec 2026)**, so this is where they run out. If the current month has no template the watcher can't publish → `sendAdminAlert` to the config channel (once per process per month, `calendar.alert`). And after each successful rollover publish it checks the **next** month's template and alerts if it's missing — a month of warning to draw the Canva page, instead of a board that silently stops updating.
- **Daily same-day announcement** (added 2026-08-05, v1.8.0; `announce.ts` = pure policy, `announcer.ts` = orchestration, `match.ts` = matching, `discord-events.ts` = the Discord API, `announce-settings.ts` = settings resolution, migration **v7**). Every morning at `CALENDAR_ANNOUNCE_HOUR` (10:00 local) the bot posts today's events to a **third** channel — the community `📣│anuncios` (`CALENDAR_ANNOUNCE_CHANNEL_ID`, live: `1435843684628172953`) — in the community's own voice, with the **Discord scheduled-event link** so members can RSVP. Armed by a second `setInterval` in `start()` (`ANNOUNCE_CHECK_MS`, 5 min) and run once immediately at boot.
  - **Three channels now, three roles:** INPUT (routing table, where mods talk) → OUTPUT (`CALENDAR_OUTPUT_CHANNEL_ID`, month PDFs + ICS) → ANNOUNCE (`CALENDAR_ANNOUNCE_CHANNEL_ID`, the daily heads-up). All three seed-from-env-then-DB-wins; manage live with `config_calendar action:set_announce_channel` / `set_announce_mentions`.
  - **It's a window, not an alarm.** `announcementsDue()` (pure) = "today's local date, at/after the announce hour, not yet started, not in the ledger". So a boot at 11:00, a 5-min tick, and a mod booking a same-day event at 3pm all produce exactly ONE post — the SQLite ledger `calendar_announcements` decides, never the clock. An event that already started is skipped rather than announced late ("hoy a las 8pm" posted at 8:40 reads as broken).
  - **Matching the Discord event is the hard part, and it's a funnel** (`match.ts`, pure + tested): **stored link → deterministic score → the model**. Admins create the Discord events by hand in their own words ("Rosario Castellanos | Club de poesía" in the calendar vs "Club de Poesía: Rosario Castellanos" on Discord), so titles rarely match literally but the start time almost always does. Score = `0.6 × symmetric token-Dice(title) + 0.4 × time-closeness`, gated to a ±26 h window; auto-accept needs score ≥ 0.62 **and** a title score ≥ 0.34 **and** a clear runner-up margin. Time alone must never carry a match — two different activities in different rooms at 8pm is exactly how the community schedules. Ambiguous → the model arbitrates (`effort:'medium'`, Kimi) and is told "es mucho peor equivocarse que decir null"; its answer is verified against the candidate ids and nullish-string tokens are normalized (the same defence the IG classifier needed). The accepted link is **persisted** to `calendar_events.discord_event_id`, so matching costs at most one model call per event, ever — not one per day. A stale link (admin deleted the event) is detected and cleared, then re-matched.
  - **Model calls are gated to what's actually being announced.** `resolveTarget(..., { allowModel })` is true only for occurrences in `due`. Everything else in the window is inspected only for the nudge check, which needs "is there plausibly an event?" — answerable deterministically. Without this gate an unmatched event costs a model call **every 5 minutes forever** (~288/day; observed live on `Club de cine`). An ambiguous-but-unarbitrated target is flagged `maybeLinked` so the nudge stays quiet instead of nagging about an event that probably exists.
  - **Exactly-once posting is enforced against Discord, not just against the ledger — and it is PREVENTED, not only repaired** (prevention added 2026-08-11, v1.16.2). Everywhere else in this bot a duplicated send is a harmless repeated reply; here it's a duplicated @-ping to the whole server, so the send is defended twice over:
    - **Prevention — `nonce` + `enforceNonce` on the create.** `POST /channels/{id}/messages` is not idempotent by default, and `@discordjs/rest` defaults to `timeout: 15_000, retries: 3`: on this Pi's uplink the request regularly outlives 15 s **after Discord already created the message**, so the abort-and-retry lands a second (and third) copy. The payload now carries Discord's own idempotency key — the pure, length-bounded `announceNonce(eventId, occurrenceStartMs)` (`announce.ts`, base36, ≤25 chars, Discord's cap) plus `enforceNonce: true` — so a retried create **returns the existing message instead of making another**. Derived from the occurrence's identity rather than randomly, so it also collapses two *different* attempts at the same announcement (overlapping ticks, a restart mid-post); a deliberate repost (`ignoreLedger`) salts it with `nowMs` so it is not swallowed as a duplicate of the morning's post. Verified live against the real API: the same nonce sent twice deduped **text-only, multipart-with-attachment (the flyer path), and still after 60 s** — comfortably longer than the ~45 s retry burst.
    - **Repair — the sweep, now a backstop.** `sendExactlyOnce()` still notes the channel's newest message id, sends, then fetches what actually landed and **deletes its own duplicates, keeping the earliest**, covering anything the nonce doesn't (a copy created outside the dedup window). It also repairs the inverse case (send rejects but the message exists → adopt the orphan instead of re-announcing next tick).
    - **Why the sweep alone was not enough (2026-08-11 triage).** It runs *after* the copies exist, and **deleting a message does not retract its notification** — every landed copy had already pinged `Usuarix`. The live rate was far worse than the journal suggested, because admins were cleaning up too: `duplicatesRemoved` read 2 (Aug 6), 1 (Aug 8), 0 (Aug 11) — but the guild audit log showed `burbujamc` hand-deleting ChopperBot messages in the announce channel on Aug 5, 6 **and Aug 11 at 10:05:11, `count=2`, nine seconds before the bot's own sweep ran at 10:05:20**. So Aug 11 was a *triple* post that logged `duplicatesRemoved: 0`. Snowflake deltas between the copies — **14.8 s, 14.9 s, 29.9 s** — are exactly one and two REST timeouts, which is what identified the retry as the mechanism. **Lesson for triage: `duplicatesRemoved` is a lower bound; cross-check `fetchAuditLogs({type: MessageDelete})` before believing a clean journal.**
  - **The announce pass is serialized against itself** (`CalendarCapability.runAnnouncer`, added 2026-08-11). A pass reads the ledger at the start and writes it only after the model has written the text and Discord has accepted the post — observed live at **~5 minutes** (a 4 m 15 s model call plus a 45 s retrying send) against a **5-minute** tick, i.e. the next tick could start, see "not announced yet", and post the same thing again. An in-flight pass now makes the next tick a no-op (`calendar.announce_tick_skipped_busy`, debug) rather than a second announcement. The nonce would also catch this, but only inside Discord's dedup window; the guard is the deterministic half.
  - **The text is model-written, the mechanics are not.** The writer prompt carries condensed real posts by this community's admins as style anchors (the voice is the whole reason to use a model) and is **forbidden** from writing mentions or URLs — `appendEventLink` + `prefixMentions` add those deterministically, exactly like event_intake's mod ping. A failed or suspiciously short model reply falls back to `renderFallbackAnnouncement()`: an outage costs the message its *style*, never the heads-up.
  - **The announcement carries the flyer** (v1.9.0). When the linked Discord event has a cover image, the post attaches it (`files: [imageUrl]` — `DiscordScheduledEvent.imageUrl` via `coverImageURL()`, threaded through `MatchableDiscordEvent`), so the heads-up looks like the admins' manual announcements, which always paste the flyer. No banner → text-only, as before.
  - **Mentions default to the member role, not `@everyone`.** `CALENDAR_ANNOUNCE_MENTIONS` accepts role snowflakes and the literal token `everyone`; the live deploy pings `Usuarix` (`1436225305898389604`) — what admins use most. `allowedMentions.parse` is explicit, so `@everyone` can only fire when it was actually configured. The setting distinguishes **never configured** (SQL NULL → env seed applies) from **configured empty** (`[]` → ping nobody), so `set_announce_mentions ""` isn't undone by the next restart.
  - **Mod nudge for a missing Discord event.** Events today/tomorrow with no Discord event get ONE message in the calendar INPUT channel (found via the router; falls back to `sendAdminAlert`), pinging the approver roles — read from `event_intake`'s own setting so "who may approve" and "who gets nudged" can't drift. It deliberately passes `canMentionAny: false`: a role left unmentionable is admins saying "don't ping this one", and housekeeping must not override that (live: 5 approver roles, only 2 mentionable). One nudge per occurrence, tracked in the same ledger. Since **v1.16.0** each line carries the **`#id`** and the ask names it concretely ("respondan a este mensaje con *crea el evento de Discord del #28*") — the old text told mods to say `#<id>` while printing no id anywhere, a placeholder they couldn't resolve.
  - **Permissions — the thing that actually blocks this.** Reading Discord scheduled events needs no intent (plain REST via `guild.scheduledEvents.fetch()`), **but the list silently omits events tied to voice/stage channels the bot can't `ViewChannel`** — indistinguishable from "no event exists". Before `Gestionar eventos` was granted the bot saw **1 of 3** events (Asamblea-Z, Sala de Club de Poesía and Sala de Cineclub are all role-gated). Creating events needs `ManageEvents` too. `diagnoseEventAccess()` reports both, and `createScheduledEvent` returns a typed `missing_permission` carrying the Spanish fix rather than failing silently.

- **`calendar_sync_discord_event`** (mod tool, added 2026-08-05; grew a full lifecycle 2026-08-06, v1.9.0): creates the Discord scheduled event for a calendar row and links the two, so the announcement can carry a clickable RSVP. Idempotent (an already-linked live event is returned, never duplicated); for a series it schedules the **next occurrence** rather than translating our recurrence into Discord's. Venue resolution is forgiving: the free-text `location` is fuzzy-matched against voice/stage channels the bot can see (→ a Voice/Stage event with a join button); with NO location it now **infers the room from the event title** (`resolveVenue` — the room's significant phrase, stopwords like "sala/de" dropped, must appear contiguously in the title: "… | Club de poesía" → Sala de Club de Poesía; conservative on purpose, a wrong room is worse than none); else it becomes an `External` event with that text as its location (Discord requires an end time for those, so one is synthesized). Reaching Discord is injected as a `DiscordEventSyncer` (`createEventSyncer`), so the tool layer stays discord.js-free and the calendar prompt can offer it once after a create.
  - **The link is a LIFECYCLE, not a one-shot create** (the v1.9.0 core). `DiscordEventSyncer` also has `refresh(eventId)` and `remove(eventId)`, and `CalendarToolSource.handleUpdate`/`handleDelete` call them automatically (`propagateToDiscordEvent`): **editing a linked calendar event edits the Discord event** (title/description/time, plus the room only when one is positively resolved — an unresolvable location never strips a hand-picked room, and a refresh never touches a banner a mod set by hand), and **deleting a series deletes the Discord event** (remove runs BEFORE `store.delete`, because the link lives on the row). Occurrence-scope edits/deletes refresh the master (the Discord event reflects the next occurrence). Only real outcomes reach the tool payload (`discord_event: {action: 'updated'|'deleted', …}` or an `error` note) so the model can confirm "también actualicé el evento de Discord" — unlinked rows and no-op refreshes stay silent, and a Discord-side failure never fails the calendar op. This came from a live refusal (2026-08-05): a mod moved "Rosario Castellanos" and the bot could only say "edit the Discord one by hand".
  - **"Crea el evento" is ambiguous, and the fix was mostly context, not prompting** (v1.16.0, from the live 2026-08-10 exchange). An admin replied to the nudge above with *"crea el evento"* and the bot asked for a title and a start date — for an event it had itself just named. Three separate holes, each fixed where it actually was:
    1. **The framework threw the referent away.** `normalizeTurns` dropped leading assistant turns, and a nudge is always one → the model saw a bare `"crea el evento"` (`historyTurns: 1`, `toolCalls: 0`). It now folds them in as quoted context — see [framework.md](../framework.md) step 3. This was never a calendar bug; it silently affected every bot-initiated thread.
    2. **The snapshot didn't carry the state the question is about.** Each line of "Próximos eventos" now ends in `evento de Discord: ✅` / `❌ FALTA` (and `@ (sin sala)` when there's no location), so "which one is missing its Discord event" is answerable *before* any tool call, and the prompt can say "if exactly one is ❌, it's that one".
    3. **The prompt had no disambiguation rule.** A "Crea el evento a secas — cuál de los dos" section orders the search for a referent: quoted context → this conversation → the single ❌ in the snapshot; asking "¿qué evento?" is the last resort, and **never** ask for title + date for something already in the calendar. A genuinely new title + date is still a `calendar_create_event`.
  - **The roomless fallback is no longer silent** (v1.16.0). `resolveVenue` is conservative by design, so an event whose location and title name no room becomes an `External` event at "Revolución Z" — it exists, but no one gets a join button. Live, #29 was created that way and confirmed as if finished. `sync`/`refresh` now return an `EventVenue` (`voice`/`stage`/`external` + name), surfaced in the tool payload as `venue_kind`/`venue_name`/`needs_room`; the prompt makes the bot name the room it used, or say it found none and ask which sala it is — once. Answering stores the `location`, and the existing refresh propagation **moves the Discord event into that room**. That repair needs an `EXTERNAL → VOICE/STAGE` conversion, which Discord wants `entity_metadata: null` for and **discord.js's `edit()` silently drops** (its `create()` sends it — the asymmetry is in the library, not the API), so a rejected edit retries once through `client.rest.patch` with the documented body (`convertToVenue`, logged as `calendar.discord_events.convert_venue_failed` when even that fails).
  - **Cover image (banner) support.** The sync tool takes an optional `image_url`, validated against `allowedImageUrls` — exactly the image attachment URLs advertised in that turn's system prompt (`CapabilityTurnContext.attachments`, populated by `handlers.ts` from `listImageAttachments()`, so a hallucinated/injected URL is refused before any fetch). The syncer downloads it via `fetchDiscordCdnImage` (host allowlist = Discord CDN only, mime + 10 MB caps — SSRF guard) and sets it as the event cover (base64 data URI; works on create AND on an already-linked event, so "ponle esta portada" is the same call). A failed download never blocks the event itself. Since v1.19.1 the attachments prompt section says so explicitly (it works on an EXISTING event — the cover is replaced, the link unchanged): a mod attaching the flyer and saying "con esta imagen" should map straight to the sync call.
