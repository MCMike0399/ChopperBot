# Community assistant (general_chat profiles)

> Topic doc — part of the [CLAUDE.md](../../CLAUDE.md) router. Read it BEFORE working in this area, and keep it current in the same change as any behavior change (doc protocol ①/② in the index).

Upgraded 2026-08-06 (v1.10.0) from a thin intro+redirect prompt into the server's **personal assistant**, after the bot got a mod role and could suddenly be @-mentioned in every RevZ channel. It remains the same fallback slot: `handlers.ts` routes any mention in an unbound guild channel to `general_chat`, so the specialized capabilities are untouched — there was nothing new to bind and no routing change.

- **Guild profiles** (`general_chat/profile.ts`): a profile grounds the bot in one community, matched by `ctx.guildId`. Today only **Revolución Z** (`1435843683541979248`) has one; any other guild keeps the generic intro+redirect prompt (`renderGeneralChatPrompt`) with **no tools**. To profile another guild, add an entry to `PROFILES`.
- **The primer is curated, not dumped** — the anti-context-flooding rule. `REVZ_PRIMER` distills the server survey (see below), the Reglamento Interno and the Estatutos into ~500 words: identity, principles (Asamblea Popular, cero tolerancia, anti-Zionism per anexo 1.13, FUP, comités estatales), structure (comisiones, clubs, zonas), and a ~20-entry key-channel directory with `<#id>` tokens so replies can link channels natively. Never paste raw history or full statute text in there — every token rides every fallback turn in that guild.
- **Voice rules live in the prompt, learned from live failures.** The old generic prompt produced corporate deflections ("Soy un bot de Discord, no un agente de nada", "no tengo opiniones personales", "Si necesitas algo del servidor — aquí estoy") that the community read as _fed behavior_ ("es un agente", "gentrificaron al chopper"). The assistant prompt (`renderAssistantPrompt`) now forbids those closers outright and tells the model to opine from the Estatutos with arguments, mirror the channel's energy, and keep the playful "IA prole" persona the community actually likes. It also gets the current channel name (`resolveChannelName`) so tone can adapt (#cuidados ≠ #momos). If someone asks which model / IA it runs on, the prompt names the **single multimodal brain** (`textBrainDisplayName()`, currently DeepSeek V4.1 Flash, `deepseek-flash`) — one model that reads text **and** images — and it must not invent or name any other model.
- **Honest self-knowledge and the moderator workspace (v2.4.0).** At build time the bot snapshots its actual roles and effective Administrator/BanMembers/ModerateMembers/ManageMessages/ViewAuditLog permissions from `guild.members.me`, sorted and cached for 60 seconds. This stable block precedes per-turn clock/speaker data. Everyone outside the restricted workspace — including a moderator asking in a public channel — gets the truthful short version; only a verified moderator **inside the moderation workspace** sees role names, permission values, command syntax and limits. `ViewAuditLog` alone does not count as "tengo permisos de moderación". The prompt only mentions a ban request when the ban tool is actually attached. Implemented effects are code-verified explicit bans, timeouts, timeout removal and single-message deletion. The bot has no Administrator; it retains Moderación and per-channel managed-role overwrites. Join alerts are not offered: the team chose to keep the privileged GuildMembers intent off and may revisit it. No commands are relayed to other bots.
- **Partner mode** requires the configured moderation channel (default `1436206995140247652`) **and** moderation-tier authority rechecked live in a restricted destination. Its dedicated prompt embeds `SPANISH_VOICE_RULES`, uses sober Spanish/tuteo, consults audit/history for incidents, cites message links, distinguishes fact/interpretation/uncertainty, and drafts messages or reasons for humans to send. It does not redirect the team's work to tickets. Neither Gestión-only callers in that channel nor moderators in public get this mode or audit tools. `config_moderation` changes the shared framework setting live; it does not bind a new capability.
- **Partner-only audit tool** (`audit-tools.ts`): `server_audit_log` filters numeric `action_type`, `actor_id`, `target_id` and `before`. It reads one 50-slot page, ≤15k entry characters, up to three calls per turn. Common actions have Spanish labels; other types retain their numeric ID with a Spanish generic label. Approximate retention: 45 days. Results state scanned/complete/truncated/cursor. Audit entries have no direct Discord message URL: cite their ID/date and pair them with actual message links from history, never invent a link.
- **Live server-directory tools in profiled guilds** (added 2026-08-06, v1.12.0; `server-tools.ts`). `server_list_channels` + `server_channel_info` let the assistant answer about channels created AFTER the primer was written (live failure: a member asked about the new `#bienvenidx` and the bot could only shrug at the id). **The security rule: everything is filtered by what the ASKING MEMBER can view** (`guild.members.fetch(userId)` → `permissionsFor(member)`, plain REST — no privileged intent), never by the bot's own mod-role view, and a channel hidden from the member answers EXACTLY like one that doesn't exist. Member resolution fails closed. Name matching is emoji/accent-folded (`💬│General` → `general`); ambiguous queries return candidates, not a guess. The primer's curated list stays (it carries the _meaning_ of key channels); the prompt tells the model the list is not the full map and to consult the tools before saying "no sé". Gated per profile via `serverDirectoryTools`. Verify live: `npx tsx scripts/verify-server-directory.ts [query] [userId…]` (read-only; prints per-member visible-channel counts — admin ~117 vs member ~55 on 2026-08-06 — and the resolved query).
- **Read-only calendar tools in profiled guilds only.** `buildTurn` attaches `CalendarToolSource` with `include: [calendar_list_upcoming, calendar_search_events, calendar_get_event]` + `allowWrite: false` (the same restricted-bundle pattern as event_intake), reusing the calendar's tables via `memory.db()` — general_chat inits after CalendarCapability in `app.ts`, same as event_intake. Scoped to the profiled guild so other guilds' turns can't read RevZ's calendar.
- **Hoy/mañana is code, not UTC arithmetic (added 2026-08-25).** The assistant prompt used to inject only `UTC: ${now.toISOString()} (el servidor vive en hora CDMX, UTC-6)`. Live in `#general` at 11:14 CDMX on Tuesday 25, "choppy qué evento hay mañana" was answered **"Mañana (martes 25)"** — DeepSeek treated UTC-6 as "subtract a calendar day" even though UTC was already 17:14 the _same_ day, then echoed Cooperativas' `start_at_local` (Tue Aug 25, 8:00 PM). The calendar channel never hit this because it already carried `renderTemporalAwareness`. Both general_chat prompts now use that shared block (explicit **Hoy es …** / **Mañana es …** with the local `YYYY-MM-DD`), and list/search rows carry `when` (`hoy`/`mañana`/`después`) so the model does not recompute from `start_at_iso` (8pm CDMX = next UTC date). Covered by `src/capabilities/general_chat/__tests__/capability.test.ts` and `src/capabilities/calendar/__tests__/time.test.ts`.
- **Events are open — tickets are not the door (added 2026-08-25, v1.27.0).** Live in `#general` at 19:56 CDMX: "donde reservo we" was answered with **zero tool calls** as "abre un ticket en #ticket y pide el pase". The primer + capability snapshot had told the model that tickets were how you propose (and by extension attend) events. Reality, read as ChopperBot from Discord: `#ticket` topic is denuncias/soporte; proposing a círculo is `#formulario-circulos` (`1525358955751276544`); attending is free — Discord Eventos / the sala. Fixes: (1) primer + prompt name the three doors; (2) `event_intake` is omitted from the assistant snapshot so its "solicitudes por tickets" description cannot leak; (3) each turn injects a live how-to block (`howto.ts`) — ChopperBot re-reads those channel topics, still filtered to what the asking member can view; (4) `server_channel_info` returns the full topic + bot-embed instructions ("Comenzar formulario" vs "Crear Ticket"); (5) `server_list_discord_events` lists RSVP links; (6) calendar list/search/get carry `discord_event_url`. Verify: `npx vitest run src/capabilities/general_chat` plus the live `npx tsx scripts/verify-assistant.ts`.
- **Spanglish is a voice defect, not a joke (added 2026-08-25).** Live the same evening: "andas emocionado por el evento de hoy?!?!?1" → **"Estoy emoción-ed"** / "Suena va a estar" / "Tú já la tenías" (message `1541988518379921459`). The assistant prompt now says to mirror energy, not carelessness; the shared `SPANISH_VOICE_RULES` forbids English suffixes glued onto Spanish; `lintSpanish` has a `spanglish` rule so the next one hits `style.spanish_voice_drift` instead of waiting for a member to report it. The `when` payload is Spanish (`hoy`/`mañana`) so the tool result does not prime English. Covered by `src/lang/__tests__/spanish-style.test.ts` + the corpus entry.

- **Conversation history + moderation support (2026-10-04, v2.3.0).** Evidence first: the preceding 30 days yielded **90 journal turns (64 general_chat, 26 calendar)** and **16,839 available Discord messages across 189 active channels/threads**, including the main voice-channel chat. The review excluded personal workshop sessions and did not attempt to reconstruct deleted messages. In general chat, 42 detected triggers included 22 replies; the voice chat had 8 triggers, including 6 replies. The old ambient path skipped all replies. A staff trigger (`1554387856045113497`) had no text inside the old 10-minute window, while its earlier conversation spanned ~19 days. General-chat exchange `1554388812061479076` → `1554389139888279627` asked the bot to get another bot to sanction someone and insisted that the bot's moderator role authorized it: bot permissions must never substitute for the caller's authorization.
   - **Automatic context:** `gatherTurnContext` now reads up to **100 messages before the trigger, within 30 days of its timestamp, ≤32,000 serialized characters**, on mentions **and replies**. The 8-turn/16k reply chain remains. Context retains authors, UTC dates, reply IDs and message links in quoted JSON; other bots retain pagination slots but contribute no text. Each message is capped at 4,000 characters. Historical images are notes, not downloaded pixels. Thread title/opening post and direct-parent images remain.
   - **On-demand history:** profiled guilds with directory tools get `server_conversation_history` (`conversation-tools.ts`, backed by `discord/conversation.ts`). Default = current channel; optional exact channel ID, literal accent-insensitive phrase, author ID and `before` cursor. Each invocation scans up to **10 pages / 1,000 slots**, returning at most **100k serialized message characters**. Per turn: **20 pages / 300k characters**, shared with moderation review. Results state `complete`, `truncated`, `scanned`, and `next_before`; a busy channel's month can require multiple turns. No empty search is proof of absence, and no partial read is described as a complete month.
   - **Access is code:** every page refreshes the member, bot and channel, requiring **ViewChannel + ReadMessageHistory** for both. Private threads also require membership unless the caller has Administrator/ManageThreads. Unknown/hidden channels fail closed. Cross-channel reads ordinarily require a public source (`@everyone` can view/read its parent). A verified partner turn may additionally read restricted text/news sources only if **all destination viewers can view/read the source**, including individual overwrites and every possible role combination. Unresolvable principals fail closed. Audit output is protected by the same audience proof. An admin asking in public still cannot pull staff history into the reply; private-thread membership is unchanged. Delivery revalidates consumed restricted sources after the model finishes. History is not archived or backfilled into SQLite; subsequent reads reflect Discord edits, deletions and revoked permissions.
   - **Review:** callers passing the shared `isModTurn` gate get `server_moderation_review`, with a live authority recheck when invoked. It reads evidence through the same access gates and asks for citations, observed facts vs interpretations, uncertainty, desescalation and proportional recommendations. No automatic monitoring or sanctions. General summaries omit unnecessary names/intimate details; a concrete incident review identifies only the people needed for the facts.
   - **Ban:** `moderation-tools.ts` exposes `server_ban_member` **only** for a current moderator message matching a standalone command: `@ChopperBot banea a @persona por motivo` (real user mention; also `ban @persona [for reason]`). Exactly one target; optional reason. Questions, quotes, conditionals, bare names and “sí, hazlo” expose no ban tool. Target/reason are fixed in code; the model cannot substitute another target or delete messages. At effect time the executor re-fetches the original message (edited/deleted requests revoke authorization), rechecks live mod authority and channel access, then enforces caller/bot role hierarchy, bot BanMembers and target bannability. Owner, events-tier staff (mods + Gestión), bots and the caller are protected. Any edited or webhook trigger is rejected; persistent trigger/action/target reservations prevent replay across turns. The executor writes executed/refused outcomes to the framework trail; successful bans send a no-ping mod-log line with requesting actor and trigger link. A logging failure never replays the ban. Refusals remain in SQLite without a channel post; unconfirmed effects are labelled explicitly. `deleteMessageSeconds: 0`; no kick, automatic join action or delegation to other bots. Ordinary chat/review stays `low`; an explicit authorized sanction uses `high`.
   - **Proof:** typecheck + **111 files / 1,331 tests** + build passed; deployed service restarted active and logged `Discord client ready`. `verify-conversation-context.ts` drove the actual handler against Discord: **100 recent messages / 26,078 characters**, deeper **331 messages / 400 scanned slots**, and live moderator review. - **Workspace actions (v2.5.0):** `action-tools.ts` attaches only the requested tool to a live verified moderation partner. `timeout @persona 1h por motivo` / `silencia a @persona 30m por motivo` uses m/h/d, default 1h, maximum 7d. `quita el timeout a @persona` removes it. `borra este mensaje por motivo` requires a direct reply; `borra https://discord.com/channels/<guild>/<channel>/<message> por motivo` targets exactly one message in this guild. Parsing uses only `ctx.requestText` and the trigger's direct reply ID; questions, quotes, conditionals, jokes, bare names, bulk requests and implicit confirmations attach no action tool. The model cannot replace target/reason/duration. Effect-time checks re-fetch the trigger, reject edits/deletes/webhooks, recheck workspace/settings/live moderation and bot/caller access, and enforce both hierarchies. Owner, bots, requester and the wider events tier are protected. Delete additionally requires requester/bot ManageMessages on the target channel, refuses log channels and bot/webhook messages, and fails closed for private-thread evidence. Public threads prove their parent audience; forum parents are supported. One attempt plus a persistent reservation prevents replay. The delete REST request carries the requesting moderator in its audit reason. Trail actions `timeout`, `timeout_removed`, `message_deleted` finish as executed/refused. Mod-log reasons and deletion excerpts are flattened and stripped of links/markdown/mentions. Author ID/channel/UTC timestamp and ≤200 excerpt characters go only to the workspace, with audience checks before reading and again before delivery; tool results contain no excerpt. Failed logging never replays an effect.
- **Escalation from community channels** (`escalation-tools.ts`): serious current reports go to <#1436255397265670195>, and the model may invoke `server_escalate_report` with an alta/urgente severity interpretation and short summary. Obvious jokes expose no escalation tool. The executor re-fetches the current trigger, rejects edits/deletes/webhooks and invented targets, rechecks caller/bot source access, then reserves persistent capacity before sending. Reporter/channel/target/link are code-bound; ambient text cannot trigger it. The model-written summary is flattened to one quoted line (`«…»`) with newlines, markdown, links and mention tokens stripped, so member text steering the model cannot forge the code-set `Reportó:`/`Gravedad` lines or plant a link in the mods channel. **Private threads never escalate** (their audience is thread members, not the parent's). Caps: one reporter per 30 minutes, one source channel per 5 minutes, one note per cited target per 30 minutes, 20 **delivered** notes per guild per UTC day (refused/failed deliveries don't burn the daily cap); trigger+target dedup survives restart. This deliberately favours fewer notes when evidence is weak or a second report lands during cooldown; ticket guidance remains available. Alta notes stay silent; only urgente uses the configured moderation-role allowlist. RevZ pings only `1436055845392879778`; the trail records `escalated:ping_sent` when sent. Send failures remain unconfirmed and are not automatically retried.
- **Hard boundaries:** no invented server facts, no autonomous sanctions, and no model-selected pings. Public reports/appeals use tickets; the moderator workspace supports evidence and drafts directly. All sanctions require an independently gated current explicit moderator command; new actions additionally require the verified workspace. Its trail and bounded escalation notes are the added operational writes. The main handler never responds in the two log channels or to webhook authors: recon's 17 replies in `1436112159829397564` chained from webhook logger messages. This closes that loop without changing the context budgets or other Phase 5 paths.

## Moderation authority correction — v2.3.1

Review and explicit-ban availability and live requester rechecks now use the **moderation** tier, not the event approver list. The ban executor's protected-target check uses the wider **events** tier, so Gestión members are protected from bot-executed bans just like staff. Gestión (`1483694810253492235`) alone receives neither tool, while keeping event capabilities. Defaults are the four staff IDs in `mod-roles.ts`; bot callers fail even with Administrator. The authority split did not change the action syntax or sanction. Phase 1 suite: 1,334 tests; live read-only proof confirmed both Gestión-only members are denied moderation. No real sanctions were used.
