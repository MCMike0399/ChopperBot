# Event intake capability (ticket funnel)

> Topic doc — part of the [CLAUDE.md](../../CLAUDE.md) router. Read it BEFORE working in this area, and keep it current in the same change as any behavior change (doc protocol ①/② in the index).

Added 2026-07-12 (v1.3.0). Turns the **Ticket Tool** event-request funnel into calendar events. A member opens a ticket (a text channel in a category), Ticket Tool posts the request **form**, ChopperBot posts a normalized + conflict-checked **proposal**, and a **moderator** approves by talking to the bot in the ticket → the calendar event is created (and the month PDF/ICS auto-publish). Mods keep final say on acceptance and day/time; the requester cannot self-approve. Lives in `src/capabilities/event_intake/`. Inspired by the community's own words in the pilot ticket: _"chopperbot pueda coordinar con el involucradx y los mods; los mods son los que tienen la última palabra; pero que no tengan que usar el mismo canal de gestión."_

- **Passive, NOT routed — like file_scanner (the second exception to one-capability-per-channel).** Registered in `app.ts` but never in the routing table; `start()` attaches its own `client.on(Events.MessageCreate, …)` listener over a watched **category** set. `init()` needs no secret so it **never throws** (unlike file_scanner) — with no category configured it just idles. **Boot order matters:** it's placed AFTER `CalendarCapability` in `app.ts`'s `candidates` because it reuses the calendar's tables via `new CalendarStore(memory.db())` (which the calendar's migrations create).
- **No double-reply with the main handler.** The main mention handler would otherwise answer a mention in a ticket (routing miss → `general_chat`). Fix: a generic `claimedChannel?: (message) => boolean` on `HandlerDeps` (`handlers.ts`); the `MessageCreate` handler early-returns when it's true. `app.ts` wires it to the event_intake instance's own **`isClaimedChannel(message)`** (same 10 s watched-set cache the listener uses — one source of truth) and only when `registry.has('event_intake')`. Category resolution is `resolveCategoryId(channel)`: `channel.parentId` for a text channel, `channel.parent?.parentId` for a thread/forum post. The persisted routing table is left untouched (chosen over category-aware routing to avoid dead ephemeral channel ids + a `resolve()` signature change).
- **Two disjoint triggers** (`watcher.ts`, wrapped so it never throws into the gateway): the **ticket-bot form** (author = `EVENT_INTAKE_TICKET_BOT_ID`, default Ticket Tool `557628352828014614`) → one auto-proposal; a **human @-mentioning / replying to the bot** → the agent loop. The listener uses a NARROW bot filter (allow the ticket bot for form detection, ignore the bot's own posts, ignore other bots, handle humans) — it must NOT blanket-skip bots like file_scanner does, since the form IS bot-authored.
- **The form is an embed** (`parse.ts`, pure + unit-tested). Ticket Tool posts the answers in `embed.description` as ` **<pregunta>** ```<respuesta>``` ` pairs; `parseTicketForm` maps them by keyword (título/tema, día/fecha, hora, ponente, flyer→yes/no) tolerant of wording; the requester id is the mention in the welcome message (`extractRequesterId`, presentation-only). `buildHistory` stops the reply-walk at the foreign-bot form message, so the parsed form is **persisted and injected into the system prompt** every turn — it never reaches the model via history.
- **Guardrail — only EVENT tickets, never report/support tickets in the same category.** Two layers: (1) `isEventForm` requires a **título AND a día/hora** (a report form has a subject but no "¿qué día?"/"¿a qué hora?", so it won't match → no proposal); (2) the conversation path only engages a ticket it recognized as an event request — `resolveEventContext` returns the stored proposal row, else re-scans the ticket's history for the event form (`findEventFormInHistory`: pages backwards 100 messages at a time, up to 500, and a form found this way is **persisted on the spot** via `recordProposal` + `event_intake.form.recovered_from_history` — it was already missed live exactly once, so recognition must not keep depending on the window; the old single 25-message scan was buried by one evening of chatter and the guardrail then went silent on a REAL event ticket — live, ticket-0007, 2026-08-14), and if neither is found it **stays completely silent even when @-mentioned** (logs `event_intake.conversation.not_event_ticket`).
- **Mod ping — the approver roles are @-mentioned in the ticket** (added 2026-08-04, v1.6.0 + v1.7.0; `mentions.ts`, pure + tested). Live-test feedback: the proposal said "lxs mods pueden aprobarla" but pinged nobody, so a request sat unseen until someone wandered in; same for "¿alguien puede apoyar con el flyer?". Three moments, two of them deterministic (`appendModPing(text, mentions, kind)`):
   - **`kind:'proposal'`** — appended to every auto-proposal. The one message mods must not miss can't depend on the model remembering, so the proposal prompt explicitly forbids the model from writing `<@&…>`.
   - **`kind:'created'`** (v1.7.0) — appended to the confirmation when THAT turn actually created the event, and **exempt from the cooldown**: the approval is the outcome the whole ticket was waiting for and happens at most once per ticket, so it always rings even though the proposal ping fired minutes earlier. The tap is `calendarSource(..., { onCreated })` → a per-turn `createdEventId` (the same successful-create hook that flips the ticket row to `created`), so the tail can't fire on a turn that only _talked_ about creating.
   - **conversation** — the prompt hands the model the exact mention string to use _only_ when it needs mod action (flyer, day/time), and tells it NOT to mention on a confirmation (the `created` tail covers that).
   - **Pingability is the whole gotcha.** Discord only NOTIFIES a role mention when the role is `mentionable` or the author holds `MentionEveryone` — otherwise `<@&id>` still renders as a chip that rings nobody, which is worse than saying nothing. The live guild is exactly that trap: of the 5 `DEFAULT_MOD_ROLES`, only **🚓Moderación🚓** and **⭐Administrador⭐** are mentionable and the bot has **no MentionEveryone**. So `resolveModMentions()` emits `<@&id>` _only_ for roles it can really notify, lists the rest as `silent`, and — if NONE can be notified — falls back to naming the roles in plain text (no fake chip). `config_eventintake action:status` reports `mod_ping {pingable, silent, can_mention_any}` with the fix ("marca el rol como mencionable…"), and the watcher logs `event_intake.mentions.not_pingable` once per guild.
   - **Who gets pinged == who may approve, by construction:** `roles.ts` exposes one matcher (`matchModRoles`) behind both `isModByRole` and `resolveModMentions`, so the two can't drift. Name matching now also **strips decoration** (emoji/punctuation) — the community's roles are emoji-wrapped, so `set_mod_roles roles:"Moderación, Administrador"` used to match nothing and silently leave nobody able to approve.
   - **Anti-spam, two layers:** `allowedMentions` is now explicit on every ticket post (`{parse:['users'], roles:[…]}` — so @everyone/@here can never fire and an invented role id can never ping), model-written role mentions outside the resolved set are stripped (`sanitizeRoleMentions`), and a repeat ping in the same ticket inside `MOD_PING_COOLDOWN_MS` (10 min, in-memory per channel) still _renders_ but is dropped from `allowedMentions` — the model echoing an earlier mention out of conversation history can't re-page the mods. The `created` tail is the one deliberate exception. `event_intake.mod_ping` logs `{roles, notified, reason: 'created'|'requested'}`.
   - **Verify:** `npx vitest run src/capabilities/event_intake` (`mentions.test.ts` pure + `watcher-mentions.test.ts`, which asserts the actual posted payload: content + `allowedMentions.roles`, with `ask` mocked) and the read-only live `npx tsx scripts/verify-event-intake-mentions.ts [guildId] [--no-model]` — prints per-role 🔔/🔕 for the real guild, the exact tail appended to a proposal, and drives the REAL model on the flyer-help turn to check it emits the mention (posts nothing).
- **Mod-authority gating is enforced at TOOL AVAILABILITY** (a hard boundary, not just prompt): everyone gets the read-only calendar tools (`calendar_search_events`/`calendar_list_upcoming`/`calendar_get_event` for conflict checks), but the `MOD_TOOLS` bundle is added **only when the author is a mod** — a non-mod turn physically can't call it (`ask()` only advertises registered tools). `CalendarToolSource` grew an options bag `{ include?, allowWrite?, syncer? }` (allowlist `tools()` + hard-refuse gated writes in `handle()`) so this reuses the calendar's create + auto-publish with no duplication.
   - **`MOD_TOOLS` = create + update + delete + sync_discord_event + set_session_theme + publish** — i.e. **the same write surface the calendar channel gives a mod** (update and sync added 2026-08-05, v1.8.0; set_session_theme 2026-08-13, v1.19.1 — the weekly-club theme flow, so a ticket can also say "esta semana vemos X" without duplicating the series; **delete + publish 2026-08-14, v1.20.0**). `calendar_update_event` is there because of a real dead end in ticket-0005 (2026-08-04): a mod approved an event whose title had a typo, asked the bot to fix it, and the bot had to answer _"no tengo herramienta para editar títulos existentes"_ and hand a one-word change back to a human. Correcting what you just approved, in the ticket where you approved it, is part of approving.
   - **`calendar_delete_event` (cancel/delete) — added v1.20.0, after the same dead end one door over.** It used to be deliberately absent on the theory "fixing your own event is ticket work, wiping events off the shared calendar is not", and the prompt bounced people out: _"Eso no se hace desde el ticket: las cancelaciones/eliminaciones se gestionan en el canal de gestión del calendario"_ (live, ticket `1537711320307077182`, 2026-08-14). But the mod who may approve an event in a ticket is exactly the mod who may cancel it, and the redirect was a handoff, not a guardrail — the ticket's own contract is "**todo pasa aquí en el ticket**". Authority is unchanged and still enforced where it always was (mod-only tool availability + `allowWrite:false` re-refusing server-side); what changed is only _where_ a mod may exercise it. All three scopes work (`series` / `occurrence` "esta semana no hay" / `following`), the prompt carries the calendar's own safety rule (**confirm the exact event once, then delete with the id you already have**) and the ambiguous-scope question, and a whole-series delete propagates to the linked Discord event exactly as in the calendar channel (`discord_event.action: 'deleted'`; the prompt forbids claiming it when the payload doesn't carry it). `calendar_publish` came along for parity ("republica el calendario"); every mutation still auto-publishes.
      - **Ticket bookkeeping:** a successful **whole-series** delete of the ticket's OWN event (`created_event_id`) flips the row to the new `cancelled` status and NULLs `created_event_id` (`EventIntakeStore.markEventDeleted`, no migration — `status` is plain TEXT), so the missing-Discord-card repair and `recent_tickets` never chase a dead id. Occurrence/following scopes trim a series that still exists → the row is left alone, and deleting some _other_ event never touches the ticket. Journal: `event_intake.event_deleted`. Covered by `__tests__/watcher-delete.test.ts`.
   - **Agitprop flyer inbox (v1.23.0, hardened v1.23.1–v1.23.2).** When the form says the requester will **not** make the flyer (`flyerSelf=false`), the watcher opens a flyer job **immediately** after posting the proposal — not waiting for mod approval. A deterministic request **card** lands in the configured Agitprop channel (`1483639272413200606` live default; `EVENT_INTAKE_AGITPROP_CHANNEL_ID` / `config_eventintake action:set_agitprop_channel`), with a role ping for the Comisión de Agitprop (default role name `Agitprop`; `EVENT_INTAKE_AGITPROP_ROLES` / `set_agitprop_roles`). If the card cannot be posted (missing channel, fetch/send failure), the ticket gets an **`open_failed` notice**, `flyer_status` stays `none`, and `flyer_request` returns an **error** (it must not tell staff the job opened). Fulfillment: **reply to the card with the image** (no `@` needed). A later image reply **replaces** a previously delivered flyer (so a stub/verify PNG cannot permanently block the real design). Staff/mods may also upload the image in the ticket (no `@` when a job is open or already delivered) or drive the job from either surface via `flyer_request` / `flyer_update` / `flyer_cancel` (`FlyerToolSource` — Agitprop gets flyer tools only, never `calendar_create_event`). An Agitprop **image reply** is mirrored into the ticket; a **ticket-side upload is not re-mirrored** (the image is already there) and the ticket notice says it was uploaded in the ticket, not that Agitprop delivered it. A reply in Agitprop that **doesn't match a request card** does not fall through to "the sole open job" (that used to bind flyer tools to the wrong ticket); the no-reply fallback still requires **exactly one** open job (`openFlyerJobs(2)`). Pointers land on the ticket row (`flyer_*` columns, migration v2) and on the calendar event **plus any sibling rows sharing the same Discord event id** (`flyer_channel_id` + `flyer_image_message_id`, calendar migration v8), and set the Discord event cover when the event already exists. Cancel/edit on either side notifies the other; whole-series delete of the ticket's event auto-cancels an open flyer job. `syncDiscordEventFor()` prefers the stored flyer pointer over `findLatestTicketImage()` (which skips the bot's own posts). The Agitprop channel is claimed by `isClaimedChannel()` so `general_chat` stays out. Journal: `event_intake.flyer.*` / `event_intake.flyer.auto_open_failed`. Covered by `__tests__/flyer-card.test.ts`, `__tests__/flyer-tools.test.ts`, `__tests__/watcher-flyer.test.ts`, store v2 tests. Live: `npx tsx scripts/deliver-event-intake-flyer.ts <ticketChannelId> <imagePath>` (real image; `--inspect-only` dumps DB+Discord). The 1×1 `verify-event-intake-flyer.ts` **requires an explicit unused ticket** and refuses `status=created`.
   - **A ticket edit RE-CREATES a missing Discord card, deterministically (v1.19.1).** The calendar's update propagation only _refreshes_ a live link — and a ticket event whose original date passed has none (Discord completes the card; ticket-0006's Calibán reschedule was confirmed with "el evento de Discord se refleja solo" while nothing existed). Now: a successful `calendar_update_event`/`calendar_set_session_theme` is tapped (`onUpdated`), and when the edited event **is the ticket's own** (`created_event_id`) and the row is unlinked, the watcher runs the same `syncDiscordEventFor()` as at approval (flyer banner included) and appends the link. Restricted to the ticket's own event so a drive-by edit of an unrelated row never spawns cards from a ticket. The mod prompt states the honesty rule: no `discord_event` in the tool result → the Discord event doesn't exist or wasn't touched → never claim it "se refleja solo". Covered by `__tests__/watcher-update-sync.test.ts`.
   - **Approval also creates the Discord scheduled event** (v1.8.0) — **with the flyer as its cover since v1.9.0** (stored Agitprop pointer preferred since v1.23.0). `syncDiscordEventFor()` runs deterministically on a successful create (same `createdEventId` tap as the mod ping, so it can't fire on a turn that only _talked_ about creating) and appends the event link to the confirmation. Deterministic rather than model-driven for the same reason the ping is: this is the moment the whole ticket existed for, and "it's in the calendar but nobody can RSVP" is exactly the gap the daily announcement then has to apologise for. **The banner:** prefer the ticket/calendar **stored flyer pointer** (Agitprop delivery or staff upload); fall back to `findLatestTicketImage()` (newest human image in recent ticket history, skipping bot/ticket-bot posts). The URL rides `sync(eventId, { imageUrl })`, and the confirmation says "con la portada que compartieron" when it landed. The same URL is advertised in the mod conversation prompt and passed as the bundle's `allowedImageUrls`, so a mod can also (re)set the banner explicitly. **The sala (v1.28.0):** if they already named one in the ticket ("sala de eventos"), pass it as `location` — do not re-ask and do not leave it empty (live ticket-0007 named it; the bot still created an EXTERNAL Discord event). If they didn't and it isn't cine/poesía/asamblea, default **Sala de Eventos** (`resolveVenue` step 3). **Public `description`:** speaker and topic only — never flyer/Agitprop credits (those stay in the ticket; `publicEventDescription` also strips them from the Discord card and announcement writer). A missing `ManageEvents` permission degrades to a line naming the fix and asking the mods to create it by hand. Mod status (`mod-roles.ts`, pure + tested): a role in `EVENT_INTAKE_MOD_ROLES` (id snowflakes **or** names, accent/case-insensitive) OR Discord's `Administrator` permission; **fails CLOSED** if `message.member` can't be resolved (falls back to `guild.members.fetch`). **Default approver roles are the deterministic Moderador/Administrador/Administradora role IDS** hardcoded in `mod-roles.ts` `DEFAULT_MOD_ROLES` (ids, so a rename can't silently change who can approve). A successful create is tapped in the watcher to flip the ticket row to `created`.
- **Persistence** (`store.ts`, migrations v1–v2): single-row `event_intake_settings` (watched categories, mod roles, **Agitprop channel + roles**; seed-from-env-then-DB-wins) and `event_intake_tickets` (one row per ticket — dedup, parsed form, approval state, **`flyer_status` / request-card pointer / delivered-image pointer / notes**). Discord doesn't replay historical `MessageCreate`, so a restart won't re-propose; the row is idempotency insurance.
- **Admin surface** (config channel): `config_eventintake` — `status` (incl. mod + **Agitprop pingability**, open flyer job count), `list_categories`, `set_categories`, `set_mod_roles`, **`set_agitprop_channel`**, **`set_agitprop_roles`**, `recent_tickets` (incl. `flyer_status`). Agitprop channel changes take effect immediately; category changes within ~10 s.
- **Config** (all optional): `EVENT_INTAKE_TICKET_CATEGORY_IDS`, `EVENT_INTAKE_MOD_ROLES`, `EVENT_INTAKE_TICKET_BOT_ID`, **`EVENT_INTAKE_AGITPROP_CHANNEL_ID`**, **`EVENT_INTAKE_AGITPROP_ROLES`**.
- **Verify:** `npx vitest run src/capabilities/event_intake` (parse/store/roles/flyer — SQLite in-memory, Discord faked; flyer failure modes in `watcher-flyer.test.ts` + `flyer-tools.test.ts`), the **cancel/delete model smoke** `npx tsx scripts/verify-ticket-cancel.ts` (drives the REAL model with the ticket's mod prompt + the real tool bundle over an **in-memory** calendar — never the live DB, posts nothing; 3 scenes: cancel a whole event → `scope:"series"`, cancel one session → the model must ask the scope first, then confirm → `scope:"occurrence"`. It wires no publisher, so replies may say the calendar wasn't republished — that's the script, not the bot), the **read-only live smoke** `npx tsx scripts/verify-event-intake.ts [channelId]` (fetches a real ticket form, runs the detector/parser, then calls REAL Bedrock with the read-only calendar bundle to generate the proposal against the live calendar — posts nothing, creates nothing), the **real-image delivery** `npx tsx scripts/deliver-event-intake-flyer.ts <ticketChannelId> <imagePath> [--inspect-only]`, and the **1×1 live proof** `npx tsx scripts/verify-event-intake-flyer.ts <ticketChannelId> [--dry-run]` (**requires** an unused/proposed ticket — refuses `status=created` so it cannot overwrite a community flyer). Manual: open an event ticket → confirm ONE proposal; as a non-mod say "@ChopperBot créalo" (refuses/defers); as a mod "@ChopperBot créalo" (creates + publishes). Watch `journalctl --user -u chopperbot -f`.
