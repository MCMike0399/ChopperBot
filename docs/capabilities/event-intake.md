# Event intake capability (ticket funnel)

> Topic doc — part of the [CLAUDE.md](../../CLAUDE.md) router. Read it BEFORE working in this area, and keep it current in the same change as any behavior change (doc protocol ①/② in the index).


Added 2026-07-12 (v1.3.0). Turns the **Ticket Tool** event-request funnel into calendar events. A member opens a ticket (a text channel in a category), Ticket Tool posts the request **form**, ChopperBot posts a normalized + conflict-checked **proposal**, and a **moderator** approves by talking to the bot in the ticket → the calendar event is created (and the month PDF/ICS auto-publish). Mods keep final say on acceptance and day/time; the requester cannot self-approve. Lives in `src/capabilities/event_intake/`. Inspired by the community's own words in the pilot ticket: *"chopperbot pueda coordinar con el involucradx y los mods; los mods son los que tienen la última palabra; pero que no tengan que usar el mismo canal de gestión."*

- **Passive, NOT routed — like file_scanner (the second exception to one-capability-per-channel).** Registered in `app.ts` but never in the routing table; `start()` attaches its own `client.on(Events.MessageCreate, …)` listener over a watched **category** set. `init()` needs no secret so it **never throws** (unlike file_scanner) — with no category configured it just idles. **Boot order matters:** it's placed AFTER `CalendarCapability` in `app.ts`'s `candidates` because it reuses the calendar's tables via `new CalendarStore(memory.db())` (which the calendar's migrations create).
- **No double-reply with the main handler.** The main mention handler would otherwise answer a mention in a ticket (routing miss → `general_chat`). Fix: a generic `claimedChannel?: (message) => boolean` on `HandlerDeps` (`handlers.ts`); the `MessageCreate` handler early-returns when it's true. `app.ts` wires it to the event_intake instance's own **`isClaimedChannel(message)`** (same 10 s watched-set cache the listener uses — one source of truth) and only when `registry.has('event_intake')`. Category resolution is `resolveCategoryId(channel)`: `channel.parentId` for a text channel, `channel.parent?.parentId` for a thread/forum post. The persisted routing table is left untouched (chosen over category-aware routing to avoid dead ephemeral channel ids + a `resolve()` signature change).
- **Two disjoint triggers** (`watcher.ts`, wrapped so it never throws into the gateway): the **ticket-bot form** (author = `EVENT_INTAKE_TICKET_BOT_ID`, default Ticket Tool `557628352828014614`) → one auto-proposal; a **human @-mentioning / replying to the bot** → the agent loop. The listener uses a NARROW bot filter (allow the ticket bot for form detection, ignore the bot's own posts, ignore other bots, handle humans) — it must NOT blanket-skip bots like file_scanner does, since the form IS bot-authored.
- **The form is an embed** (`parse.ts`, pure + unit-tested). Ticket Tool posts the answers in `embed.description` as `` **<pregunta>** ```<respuesta>``` `` pairs; `parseTicketForm` maps them by keyword (título/tema, día/fecha, hora, ponente, flyer→yes/no) tolerant of wording; the requester id is the mention in the welcome message (`extractRequesterId`, presentation-only). `buildHistory` stops the reply-walk at the foreign-bot form message, so the parsed form is **persisted and injected into the system prompt** every turn — it never reaches the model via history.
- **Guardrail — only EVENT tickets, never report/support tickets in the same category.** Two layers: (1) `isEventForm` requires a **título AND a día/hora** (a report form has a subject but no "¿qué día?"/"¿a qué hora?", so it won't match → no proposal); (2) the conversation path only engages a ticket it recognized as an event request — `resolveEventContext` returns the stored proposal row, else re-scans recent history for the event form (`findEventFormInHistory`, handles bot-added-after-open / missed MessageCreate), and if neither is found it **stays completely silent even when @-mentioned** (logs `event_intake.conversation.not_event_ticket`).
- **Mod ping — the approver roles are @-mentioned in the ticket** (added 2026-08-04, v1.6.0 + v1.7.0; `mentions.ts`, pure + tested). Live-test feedback: the proposal said "lxs mods pueden aprobarla" but pinged nobody, so a request sat unseen until someone wandered in; same for "¿alguien puede apoyar con el flyer?". Three moments, two of them deterministic (`appendModPing(text, mentions, kind)`):
  - **`kind:'proposal'`** — appended to every auto-proposal. The one message mods must not miss can't depend on the model remembering, so the proposal prompt explicitly forbids the model from writing `<@&…>`.
  - **`kind:'created'`** (v1.7.0) — appended to the confirmation when THAT turn actually created the event, and **exempt from the cooldown**: the approval is the outcome the whole ticket was waiting for and happens at most once per ticket, so it always rings even though the proposal ping fired minutes earlier. The tap is `calendarSource(..., { onCreated })` → a per-turn `createdEventId` (the same successful-create hook that flips the ticket row to `created`), so the tail can't fire on a turn that only *talked* about creating.
  - **conversation** — the prompt hands the model the exact mention string to use *only* when it needs mod action (flyer, day/time), and tells it NOT to mention on a confirmation (the `created` tail covers that).
  - **Pingability is the whole gotcha.** Discord only NOTIFIES a role mention when the role is `mentionable` or the author holds `MentionEveryone` — otherwise `<@&id>` still renders as a chip that rings nobody, which is worse than saying nothing. The live guild is exactly that trap: of the 5 `DEFAULT_MOD_ROLES`, only **🚓Moderación🚓** and **⭐Administrador⭐** are mentionable and the bot has **no MentionEveryone**. So `resolveModMentions()` emits `<@&id>` *only* for roles it can really notify, lists the rest as `silent`, and — if NONE can be notified — falls back to naming the roles in plain text (no fake chip). `config_eventintake action:status` reports `mod_ping {pingable, silent, can_mention_any}` with the fix ("marca el rol como mencionable…"), and the watcher logs `event_intake.mentions.not_pingable` once per guild.
  - **Who gets pinged == who may approve, by construction:** `roles.ts` exposes one matcher (`matchModRoles`) behind both `isModByRole` and `resolveModMentions`, so the two can't drift. Name matching now also **strips decoration** (emoji/punctuation) — the community's roles are emoji-wrapped, so `set_mod_roles roles:"Moderación, Administrador"` used to match nothing and silently leave nobody able to approve.
  - **Anti-spam, two layers:** `allowedMentions` is now explicit on every ticket post (`{parse:['users'], roles:[…]}` — so @everyone/@here can never fire and an invented role id can never ping), model-written role mentions outside the resolved set are stripped (`sanitizeRoleMentions`), and a repeat ping in the same ticket inside `MOD_PING_COOLDOWN_MS` (10 min, in-memory per channel) still *renders* but is dropped from `allowedMentions` — the model echoing an earlier mention out of conversation history can't re-page the mods. The `created` tail is the one deliberate exception. `event_intake.mod_ping` logs `{roles, notified, reason: 'created'|'requested'}`.
  - **Verify:** `npx vitest run src/capabilities/event_intake` (`mentions.test.ts` pure + `watcher-mentions.test.ts`, which asserts the actual posted payload: content + `allowedMentions.roles`, with `ask` mocked) and the read-only live `npx tsx scripts/verify-event-intake-mentions.ts [guildId] [--no-model]` — prints per-role 🔔/🔕 for the real guild, the exact tail appended to a proposal, and drives the REAL model on the flyer-help turn to check it emits the mention (posts nothing).
- **Mod-authority gating is enforced at TOOL AVAILABILITY** (a hard boundary, not just prompt): everyone gets the read-only calendar tools (`calendar_search_events`/`calendar_list_upcoming`/`calendar_get_event` for conflict checks), but the `MOD_TOOLS` bundle is added **only when the author is a mod** — a non-mod turn physically can't call it (`ask()` only advertises registered tools). `CalendarToolSource` grew an options bag `{ include?, allowWrite?, syncer? }` (allowlist `tools()` + hard-refuse gated writes in `handle()`) so this reuses the calendar's create + auto-publish with no duplication.
  - **`MOD_TOOLS` = create + update + sync_discord_event + set_session_theme** (update and sync added 2026-08-05, v1.8.0; set_session_theme 2026-08-13, v1.19.1 — the weekly-club theme flow, so a ticket can also say "esta semana vemos X" without duplicating the series). `calendar_update_event` is there because of a real dead end in ticket-0005 (2026-08-04): a mod approved an event whose title had a typo, asked the bot to fix it, and the bot had to answer *"no tengo herramienta para editar títulos existentes"* and hand a one-word change back to a human. Correcting what you just approved, in the ticket where you approved it, is part of approving. **`calendar_delete_event` is still deliberately absent** — fixing your own event is ticket work, wiping events off the shared calendar is not; the prompt tells the model to send deletion requests to the calendar channel.
  - **A ticket edit RE-CREATES a missing Discord card, deterministically (v1.19.1).** The calendar's update propagation only *refreshes* a live link — and a ticket event whose original date passed has none (Discord completes the card; ticket-0006's Calibán reschedule was confirmed with "el evento de Discord se refleja solo" while nothing existed). Now: a successful `calendar_update_event`/`calendar_set_session_theme` is tapped (`onUpdated`), and when the edited event **is the ticket's own** (`created_event_id`) and the row is unlinked, the watcher runs the same `syncDiscordEventFor()` as at approval (flyer banner included) and appends the link. Restricted to the ticket's own event so a drive-by edit of an unrelated row never spawns cards from a ticket. The mod prompt states the honesty rule: no `discord_event` in the tool result → the Discord event doesn't exist or wasn't touched → never claim it "se refleja solo". Covered by `__tests__/watcher-update-sync.test.ts`.
  - **Approval also creates the Discord scheduled event** (v1.8.0) — **with the flyer as its cover since v1.9.0**. `syncDiscordEventFor()` runs deterministically on a successful create (same `createdEventId` tap as the mod ping, so it can't fire on a turn that only *talked* about creating) and appends the event link to the confirmation. Deterministic rather than model-driven for the same reason the ping is: this is the moment the whole ticket existed for, and "it's in the calendar but nobody can RSVP" is exactly the gap the daily announcement then has to apologise for. **The banner:** `findLatestTicketImage()` picks the newest image attachment anywhere in the ticket's recent history (skipping the bot's and the ticket bot's own posts) — requesters attach the flyer right after opening (the Calibán ticket pattern, 2026-08-05), and before v1.9.0 a mod had to re-upload it to the Discord event by hand. The URL rides `sync(eventId, { imageUrl })`, and the confirmation says "con la portada que compartieron" when it landed. The same URL is advertised in the mod conversation prompt and passed as the bundle's `allowedImageUrls`, so a mod can also (re)set the banner explicitly. The prompts now also ask **once** for the sala (the Ticket Tool form has no "where" question) — non-blocking, since venue inference from the title is the backstop. A missing `ManageEvents` permission degrades to a line naming the fix and asking the mods to create it by hand. Mod status (`mod-roles.ts`, pure + tested): a role in `EVENT_INTAKE_MOD_ROLES` (id snowflakes **or** names, accent/case-insensitive) OR Discord's `Administrator` permission; **fails CLOSED** if `message.member` can't be resolved (falls back to `guild.members.fetch`). **Default approver roles are the deterministic Moderador/Administrador/Administradora role IDS** hardcoded in `mod-roles.ts` `DEFAULT_MOD_ROLES` (ids, so a rename can't silently change who can approve). A successful create is tapped in the watcher to flip the ticket row to `created`.
- **Persistence** (`store.ts`, migration v1): single-row `event_intake_settings` (watched categories + mod roles; seed-from-env-then-DB-wins, mirroring `FileScannerStore`) and `event_intake_tickets` (one row per ticket — dedup so a form is proposed ONCE and survives restarts, plus the parsed form + approval state). Discord doesn't replay historical `MessageCreate`, so a restart won't re-propose; the row is idempotency insurance.
- **Admin surface** (config channel): `config_eventintake` (`src/capabilities/configuration/eventintake-admin-source.ts`, registered in `configuration/capability.ts`) — `status` (incl. the `mod_ping` pingability block, which is why this source now takes the Discord `client`), `list_categories`, `set_categories {channels}` (accepts category ids, `guild:<id>`, "este servidor", "todos"), `set_mod_roles {roles}` (names or ids), `recent_tickets`. Takes effect within ~10 s (no restart).
- **Config** (all optional): `EVENT_INTAKE_TICKET_CATEGORY_IDS` (seed the watched category set — the live deploy watches `1436254735677128714`), `EVENT_INTAKE_MOD_ROLES` (approver roles; empty → the default ids), `EVENT_INTAKE_TICKET_BOT_ID` (default Ticket Tool).
- **Verify:** `npx vitest run src/capabilities/event_intake` (parse/store/roles — pure, no network) and the **read-only live smoke** `npx tsx scripts/verify-event-intake.ts [channelId]` (fetches a real ticket form, runs the detector/parser, then calls REAL Bedrock with the read-only calendar bundle to generate the proposal against the live calendar — posts nothing, creates nothing). Manual: open an event ticket → confirm ONE proposal; as a non-mod say "@ChopperBot créalo" (refuses/defers); as a mod "@ChopperBot créalo" (creates + publishes). Watch `journalctl --user -u chopperbot -f`.
