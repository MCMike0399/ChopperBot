# Instagram monitor scheduler

> Topic doc — part of the [CLAUDE.md](../../CLAUDE.md) router. Read it BEFORE working in this area, and keep it current in the same change as any behavior change (doc protocol ①/② in the index).

`InstagramMonitorScheduler` ticks on a **jittered** interval around `DEFAULT_TICK_MS` (60 s × Uniform[0.8, 3.0] ≈ 48–180 s, measured from the _end_ of the previous tick), polling at most `ACCOUNTS_PER_TICK=1` due account per tick (`MAX_PUSHES_PER_ACCOUNT_PER_TICK_PER_CHANNEL=5`). A fixed `setInterval(60000)` used to land every poll on the same wall-clock second (observed 2026-08-18: a `:16`/`:27` metronome in the journal) — that's a classic bot tell, and the 15% random skip didn't hide it when several accounts were already due. Each account's poll interval is **adaptive** — learned from its own posting cadence (see "Adaptive polling & budget governor" below), not a flat 60 min; `DEFAULT_POLL_INTERVAL_MS` (60 min) now survives only as the scheduler's nominal/log value (the per-account cold-start fallback is 12 h). **First-ever poll for an account seeds the dedup anchor and does NOT backfill** — only posts strictly newer than the last seen IG post id are processed.

**One account per tick + jitter (anti-burst).** Polling is one account per tick (never a synchronized burst), and `store.dueAccounts()` adds a per-account jitter of up to `POLL_JITTER_FRACTION` (**75%**, now defined in `store.ts`) of **that account's own adaptive interval** to its next-due time, so accounts decorrelate and requests scatter irregularly across the window. This both looks less bot-like and reduces IP throttling.

**Anti-detection layers (see scheduler.ts / fetcher.ts).** Designed to survive IG automation detection on a _personal_ account (a banned account is catastrophic):

- **Quiet hours** **01:00–08:00** America/Mexico_City, with a deterministic per-day ±20-min jitter on each edge (`inQuietHours`) so the resume time isn't a fixed daily tell. **Test-isolation gotcha (fixed 2026-08-16):** `tickOnce()` reads the _real_ wall clock for this gate, so the scheduler test suite fails ~23 tests when run inside the window — `scheduler.test.ts` pins `Date` to local noon in a `beforeEach` (`toFake: ['Date']`; re-pinned per test because several tests manage their own clock and `useRealTimers()` in a `finally`).
- **~15% random whole-tick skips** (`tickSkipProbability`, set in `capability.ts`) plus the jittered tick delay above, so polling isn't a perfect metronome.
- **Per-poll randomness in `fetcher.ts`**: **always** HTML-warmup the profile page first (raised 50% → 80% on 2026-08-19, then 80% → 100% on 2026-09-07 — a 20% API-only tail is still a scraper signature, and the first resume poll after the Sep 2 kill-switch landed in that tail), a heavy-tailed 400–1500 ms gap (8% chance of a 2–7 s pause) between pk-resolve and the feed request, and a randomized feed `count` (10–16).
- **Chrome-shaped headers.** `IG_USER_AGENT` is sent on every API _and_ CDN request — set it to **match the browser the cookies were extracted from**. Client Hints (`sec-ch-ua` / `sec-ch-ua-mobile` / `sec-ch-ua-platform`) are derived from that UA (Chrome 120+ always sends them; a Chrome UA without them is a non-browser tell), plus `x-requested-with: XMLHttpRequest`. `x-ig-www-claim` is captured from `x-ig-set-www-claim` on any IG response (typically the HTML warmup) and forwarded on later XHRs. Extra `Set-Cookie` values (`rur`, etc.) are absorbed into the jar. **`csrftoken` and `sessionid` are also absorbed when IG rotates them** (the HTML warmup always Set-Cookies a fresh csrf); pinning the `.env` pair forever is what turned a 5-day pause into an HTML login shell. `ds_user_id` / `mid` / `ig_did` stay pinned.
- **CDN fetches use the same session.** Cover/carousel/video downloads go through the same HTTP/2 dispatcher with the same cookies, Referer and Client Hints — they used to be a second, dumber client (HTTP/1.1, UA only, no cookies).
- **Durable pk / username-feed cache (store migration v9, 2026-08-19).** `ig_pk` and `prefer_username_feed` persist on the account row so a restart doesn't re-hit `web_profile_info` for every handle, and doesn't re-arm the `laser.provider` 400 on the 5 broken accounts. The in-memory Set from 2026-08-16 was wiped on every deploy (15 restarts in 3 days → 25 identical 400s). **`prefer_username_feed` stays sticky until an operator force-polls / unpauses** — those are the only "try pk-resolve again" gestures. A 14-day auto-reprobe used to expire the flag; on **2026-09-02** that re-hit `web_profile_info` on the same 5 accounts, drew two HTTP 429s two hours apart, and tripped the kill-switch for five days. Do not re-introduce a TTL.

**Cadence retune after IG's "suspected automated behaviour" notice (2026-08-13).** Instagram served the polling account an automation-suspicion notice. Triage of the live DB + journal found no throttle, no checkpoint and no auth failure (`global_stop=0`, `requests_24h=82` under the then-120 budget, zero 429s) — i.e. IG flagged the _pattern_, not a rate ceiling. Two things in that pattern stood out, and both were fixed:

- **Volume + regularity were higher than the anti-detection story implied.** Four knobs were widened together, all in one direction (quieter, less regular, less total traffic): `IG_DAILY_REQUEST_BUDGET` default **120 → 90**, `POLL_JITTER_FRACTION` **0.5 → 0.75**, `TICK_SKIP_PROBABILITY` **0.08 → 0.15**, quiet hours **02–07 → 01–08**. The governor absorbs all four automatically — the headroom ceiling drops to `0.75 × 90 ≈ 67` projected calls/day, and because the jitter fraction feeds the same `expectedPollsPerDay` spacing model, the projection stays honest rather than silently under-counting. At deploy the governor re-solved `poll_stretch` **2.24 → 6.03** against the new ceiling.
- **A quarter of all traffic was deterministically-failing requests** — the `laser.provider` incident below. That is the single most bot-like thing in the journal (a client hammering an endpoint that has returned the identical hard error for weeks), and it was also pure waste.
- **Expected cost:** at stretch ≈6 nearly every account saturates the 12 h interval ceiling, so worst-case detection latency rises toward 12 h. **No posts are lost** — the feed window holds 10–16 items and the busiest account (~4.5 posts/day) accrues only ~2.3 per 12 h window. The cost is latency only, and it partly reverses on its own: once the 5 broken accounts auto-pause they leave the governor's projection, freeing budget that pulls stretch (and therefore latency) back down.

**Deterministic per-account failures auto-pause the account (store migration v8, added 2026-08-13).** Since **2026-07-18** IG had been answering the pk-resolve for 5 accounts (`contramascaras`, `yoxlas40horas`, `vozdelosdesaparecidospuebla`, `semillasderebeldia`, `manatimx`) with a deterministic `HTTP 400 {"message":"Asset asset://laser.provider/ig_business_category_subvertical has been deleted. You cannot use this schema"}`. **100% of their polls failed for ~4 weeks** (~16 wasted calls/day, ≈20% of realized spend) and the scheduler retried them forever, because the generic transient-failure path assumes retrying eventually helps. It doesn't here: the identical request fails identically until IG changes something server-side.

- `detectHardAccountBlock(status, body)` (`fetcher.ts`) matches **400-only** against `HARD_ACCOUNT_MARKERS` (`laser.provider`, `you cannot use this schema`) and raises **`InstagramHardAccountError`**. It's checked **after** `detectAuthBlock` and `detectRateLimit`, so a session or throttle signal always wins; every other 4xx/5xx stays on the generic transient path.
- The scheduler counts these on their **own** counter (`consecutive_hard_failures`, **v8**), logs `instagram_monitor.account_hard_failed` (with `reason` + `auto_paused`), and at **`HARD_PAUSE_THRESHOLD` (5)** `dueAccounts()` stops returning the account. `computeGovernorStretch()` excludes it too, so the freed budget goes to accounts that actually work. One alert fires at the crossing (`postAccountAutoPausedAlert`, `⏸️ cuenta auto-pausada`) — not per failure.
- **This counter is deliberately NOT cleared by `clearFailureBackoff()`** at restart, unlike the other two. A deterministic server-side error does not heal because _we_ rebooted, and clearing it would re-arm 5 failing polls per broken account on every boot. Recovery: `markPollSuccess` zeroes the counter, but note that path is only reachable _below_ the threshold — **once the gate trips the account never polls again on its own**, so auto-pause is terminal until an operator acts. The two operator paths are `config_instagram action:pause_account` with `paused:false` and `action:force_poll`; both explicitly reset the counter (they _are_ the "try it again" gesture). This is deliberate — the failure is an IG-side schema deletion, so a human should decide when to re-test — but it does mean **a silently-fixed IG bug leaves the account paused indefinitely**. If the 5 accounts matter, re-test one every few weeks; the auto-pause alert is the reminder to do so.
- Surfaced as `D` in the status-digest flag column and in `blocked`/`interestRank`/next-poll (`—`) alongside auth-blocked accounts. Journal vocabulary: `instagram_monitor.account_hard_failed`, `instagram_monitor.hard_pause_notify_failed`.
- **Why 5, and why it's not just "delete the accounts":** the threshold mirrors the auth gate, and at these accounts' ~2 polls/day it trips within ~2.5 days. Auto-pause (not removal) is right because the cause is a server-side IG schema deletion that may well be reverted — the accounts themselves are live and public, so an operator retry should be one command, not a re-add.
- **Incident closed 2026-08-16 via the feed-by-username fallback; stickiness made durable 2026-08-19 (v9).** All 5 accounts crossed `HARD_PAUSE_THRESHOLD` that morning (alerts 03:46–06:20 UTC). Root cause, corroborated by third-party scrapers hit the same weeks (cobalt #1579, OpenCLI #2234, an Apify actor): IG deleted the server-side schema asset `ig_business_category_subvertical`, and the `web_profile_info` render path for **business-category profiles** still references it — hence deterministic 400s for exactly those accounts. The fetcher now catches `InstagramHardAccountError` from `resolvePk` and retries via the **username-keyed feed endpoint** `feed/user/{username}/username/`, which never touches `web_profile_info` (verified live against `@manatimx` pre-deploy: 12 posts, pinned-first ordering intact). On success the decision is **sticky in SQLite** (`prefer_username_feed`, migration v9) so later polls _and later processes_ skip the doomed pk-resolve. The flag **does not auto-expire** — a 14-day TTL used to re-probe `web_profile_info` "in case IG restored the schema"; on 2026-09-02 that re-probe 429'd twice and tripped the kill-switch. Only `force_poll` / unpause re-probe (they _are_ the "try it again" gesture). The 2026-08-16 in-memory Set was wiped on every deploy — after the fallback shipped, 15 restarts in 3 days still produced 25 identical `laser.provider` 400s, which is the same hammering-a-dead-endpoint pattern the Aug 13 retune was trying to kill. Fallback failure semantics: auth/rate-limit/hard signals propagate unchanged; any _other_ fallback failure re-throws the original hard error, so the account stays on the auto-pause path instead of downgrading to infinite transient retries. Journal vocabulary: `instagram_monitor.fetch.pk_resolve_hard_failed`, `instagram_monitor.fetch.feed_by_username_engaged`. **Recovery:** accounts stay hard-paused (counter=5) until the operator `force_poll`s/unpauses them — with the fallback live that poll succeeds and `markPollSuccess` zeroes the counter. Expect one bounded catch-up burst per account (≤ `MAX_PUSHES_PER_ACCOUNT_PER_TICK_PER_CHANNEL` recent posts per bound channel) on that first poll, from the frozen anchor.

**Adaptive polling & budget governor (store migrations v6 + v7, added 2026-05-29).** A flat 60-min cadence starved the 120-request budget across many accounts, round-robining it equally so a 6-day-cadence account got the same share as a 2-hour one. Now each account's interval is **learned from its own `posted_at` history** and the budget is spent where posts actually happen. Detection _latency_ varies, not coverage (the feed returns 10–16 items, so a longer interval can't miss posts unless an account posts >~10× within it — only the most active accounts, which get the shortest intervals).

- `computeCadenceInterval()` (in `store.ts`, pure + unit-tested) takes an account's distinct recent post times (**deduped across channels** — `seen_posts` is per-channel, so the query `GROUP BY ig_post_id` or the median halves) and returns `interval = clamp(median_inter-post_gap × 0.5, 45 min, 12 h)`, with a recency-decay stretch toward MAX once an account goes quiet, and a coverage clamp. (The ceiling was raised 6 h → 12 h on 2026-05-30: live data showed the 6 h cap was clamping genuinely-rare accounts — e.g. `semillasderebeldia` ~20 h median gap wants ~10 h, `revueltasperiodico` ~26 h wants ~13 h — to roughly half their natural interval, wasting the request budget the active accounts need. Per-account interval is purely a budget lever; IG rate-limits on the _session's_ aggregate rate, not per-account, so a longer ceiling carries no extra ban risk.) It returns `null` (→ cold-start) until there are ≥ `CADENCE_MIN_SAMPLES` (5) posts spanning ≥ `CADENCE_MIN_SPAN_MS` (**24 h**) — `MIN_SAMPLES` rejects tiny bursts; the 24 h span rejects a single-afternoon flurry while still accepting a real multi-day cadence (a 26-post/2.9-day account would be wrongly rejected at a 3-day threshold).
- **Cold start** (`CADENCE_COLD_START_INTERVAL_MS` = 12 h, kept == MAX): accounts without a trusted cadence poll slowly _on purpose_ — few posts ⇒ empirically a rare poster, so we don't burn budget on unknowns; they speed up automatically as history accrues. (This is why the default fallback is 12 h, not the old 60 min. Polling slowly does NOT slow learning — cadence is learned from detected posts, and a 12 h interval can't miss a rare account's posts since the feed window holds 10–16.)
- The interval is cached on `instagram_monitor_accounts` (`poll_interval_ms`, `posts_per_day`, `cadence_updated_at`; **v6**) and read by `dueAccounts()` via `effectiveBaseIntervalMs()` = `(poll_interval_ms ?? cold-start) × poll_stretch`, clamped to MAX. The failure-backoff cap is decoupled to `min(base × 2^failures, max(MAX_BACKOFF_MS, base))` — `MAX_BACKOFF_MS` stays 6 h while the cadence ceiling is now 12 h, so this `max(…)` guard genuinely binds: a 12 h-cadence account with failures still polls every ~12 h, not exponentially slower.
- **Budget governor** (`computeGovernorStretch()`): a single global `poll_stretch` (runtime row, **v7**) raised above 1.0 so the **realized** projected daily requests stay ≤ `IG_DAILY_REQUEST_BUDGET × CADENCE_BUDGET_HEADROOM` (**0.75**). It is **clamp-aware** (fixed 2026-05-30): because `interval × stretch` saturates at the 12 h ceiling, an already-maxed account contributes a fixed request rate the stretch can't reduce — so the old `projected / ceiling` closed form under-corrected whenever accounts sat at the clamp, letting realized spend overshoot. The governor now binary-searches the smallest `stretch` whose _realized_ (post-clamp) projection `Σ expectedPollsPerDay(min(interval × stretch, MAX)) × callsPerPoll` meets the ceiling; one multiplier preserves the active-vs-rare allocation, and the hard budget gate stays the backstop. It is also **quiet-aware per account** (fixed 2026-06-12, was residual #1): `expectedPollsPerDay()` in `store.ts` models each account as `min(DAY/spacing, (DAY−quietWindow)/spacing + 1)` — quiet hours only _time-shift_ a long-interval account's polls (a 12 h-ceiling account polls ~2×/day regardless), so the old uniform `activeFraction` (≈0.73) under-projected every clamped account. With 7 of 18 accounts clamped, the model said 60 polls/day while the journal showed 70 (+17%), and realized spend sat at **106/120** — only ~~14 requests of margin, which a restart's pk-resolve burst (~~+18 calls) would have blown through. `spacing` also includes the correct jitter expectation: `pollJitterMs` re-rolls Uniform[0, `POLL_JITTER_FRACTION` × interval) **every tick**, so the expected extra delay is the first-passage time ≈ `sqrt(π/2 × J × tick)` (at the current 0.75 fraction: ~10 % at 2 h, ~4 % at 12 h — it was ~8 %/~3 % at the old 0.5), NOT J/2. The random tick-skip is deliberately _not_ in the model (a skipped tick delays a due poll by one tick; it never drops one). `callsPerPoll` is **measured, not guessed** (changed 2026-05-31): the scheduler keeps a rolling-24 h count of _polls_ (`pollTimestamps`, mirroring `requestTimestamps`) and feeds the governor `requests ÷ polls`, clamped to `[1, 3]`, falling back to `CALLS_PER_POLL_FALLBACK` (**1.7**) until `CALLS_PER_POLL_MIN_SAMPLES` (20) polls accrue. The old hardcoded **1.5** systematically _under-projected_ — live realized is **~1.7** (warmup fires a hair over 50 %, pk occasionally re-resolves), so the governor set too low a stretch and realized spend overshot the headroom target (112/120 instead of the intended ~~90). The self-calibrating value also tracks any future drift in warmup/pk behavior, and is surfaced as `calls_per_poll` on the `instagram_monitor.cadence_sweep` log line. The 25 % headroom now only absorbs the restart pk-resolve burst (~~+1 call/account in-window for 24 h — ~18 calls at the 2026-06-12 fleet size) + `callsPerPoll` measurement lag: the polls-projection gap that used to eat it (realized ~65–70/day vs modeled ~60) was closed by the quiet-aware `expectedPollsPerDay` model (2026-06-12, below).
- **Recompute triggers:** (1) the per-account _cadence interval_ is recomputed opportunistically right after a poll detects new posts (single account, in `processAccount`) and in a once-per-`CADENCE_TTL_MS` (24 h) sweep over all accounts (`recomputeAllCadence`); (2) the global `poll_stretch` is recomputed **every tick** from the _current_ cached intervals (`recomputeGovernorStretch`, decoupled from the 24 h sweep on 2026-06-02 — see below). Both run from the tick's `finally` block, **even while polling is paused** (pure SQLite, no IG calls) — recomputing cadence + stretch is exactly what lets a budget-pinned monitor shrink its intervals and recover. Log lines: `instagram_monitor.cadence_sweep` (daily: `swept` + `stretch` + `projected` + `calls_per_poll`) and `instagram_monitor.stretch_update` (per-tick, emitted only on a ≥10 % stretch change to avoid journal spam).
- **The stretch must be recomputed continuously, not once per day (fixed 2026-06-02).** Originally `poll_stretch` was refreshed only in the 24 h cadence sweep. But per-account intervals shrink _throughout the day_ — active accounts tighten as they post (opportunistic recompute) — and the sweep is locked to whatever wall-clock hour the bot last restarted. On a Pi that restarted at noon, the sweep snapshotted stretch at the daily _activity low_ (overnight quiet + morning lull), then the afternoon/evening posting surge tightened intervals and realized spend climbed straight to the **120/120 hard cap** (observed 2026-06-02: noon sweep set `stretch=2.087`/`projected=90`, but the live-correct stretch by 15:00 was ≈**2.67**; realized hit 120 and soft-paused ~20 min repeatedly from ~14:00 on). Per-account _cadence_ recompute can stay daily (rare-account cadences move slowly; active ones get the opportunistic refresh), but the _governor stretch_ — a pure function of the current cached intervals + measured `callsPerPoll` — is now recomputed every tick so it tracks the intra-day activity cycle. The hard budget gate stays the backstop; this just keeps the monitor from leaning on it.

Net effect on the real 14-account deployment, with a correction logged after a full day of live data:

- **Per-account adaptation works as designed.** A day after the 12 h ceiling shipped, the rare accounts had converged to their true intervals (`revueltasperiodico` → 12 h, `semillasderebeldia` → ~9.4 h, `gentrificacionentuidioma` → ~7.6 h, `revolucionzmexico` cold-start → ~9.8 h) and accounts that turned out _more_ active than the snapshot tightened (`un_altavoz` cold-start → 81 min once it showed ~5.5 posts/day, `antigentrificacion.cdmx` 120 → 51 min). All 14 with zero failures.
- **But the predicted budget convergence did NOT materialize the way the 2026-05-30 snapshot implied.** That snapshot predicted `poll_stretch` ≈2.0 → **≈1.1** and realized spend → **~90 calls/day**. In reality, a day later `poll_stretch` settled at **~2.1** (it _rose_) and realized spend was **~112/120** — because (a) overall account activity rose above the static snapshot (the budget freed by rare accounts was immediately consumed by the newly-active ones), and (b) the governor's hardcoded `callsPerPoll = 1.5` under-counted the real ~1.7, so it set too low a stretch. Both push realized up. The system never tripped `budget_exhausted` (the 25 % headroom absorbed the overshoot) but ran with only ~8 requests of margin to the hard cap instead of the intended ~30.
- **The 2026-05-31 fix** (self-calibrating `callsPerPoll`, above) closes (b): the governor now projects against the measured ~1.7, raises stretch enough to pull realized back toward the headroom target, and restores real margin to the hard cap. (a) is not a bug — it's the model correctly spending the budget where the activity is; it just means `poll_stretch` is a _dynamic_ function of the live account mix, not a number that settles at a documented constant.
- **2026-06-12 (quiet-aware `expectedPollsPerDay`) — validation pending.** At deploy (18 accounts, 7 ceiling-clamped) the governor jumped stretch 2.46 → **3.48** with `calls_per_poll` at the 1.7 fallback (restart wiped the measurement window; it should relax toward ~1.5 within hours as 20+ polls accrue, letting stretch ease too). **Check after ≥24 h uptime:** `requests_24h` should read **~85–95** (was 106) and realized polls/day should match the model within ~±5 % (see the polls-bias check below). If realized spend still sits >100 with the journal showing no model bias, the gap is `callsPerPoll` lag (residual #2) or fleet growth — NOT a reason to re-add an `activeFraction`-style fudge. If the polls-bias check itself shows >10 % bias again, something new is unmodeled: measure first, then extend `expectedPollsPerDay`, don't tune constants blind.

The takeaway for future readers: **trust the live DB + `cadence_sweep` log over any hardcoded "expected" stretch/spend number in this doc** — those are snapshots of a moving target. The invariants that _do_ hold: per-account intervals track each account's own cadence (clamped to [45 min, 12 h]), and the governor holds _realized_ spend under `0.75 × budget` plus a now-accurate headroom.

**Observing the cadence/governor (do this before changing anything).** The whole system is a feedback loop over live data, so _measure first_. The exact research workflow:

- **Realized spend & current stretch:** `sqlite3 data/chopperbot.db 'SELECT poll_stretch, requests_24h, global_stop, budget_pause_until FROM instagram_monitor_runtime;'`. `requests_24h` is the rolling-24 h IG-call count; since the 2026-08-13 retune it should sit **~67–80/day** (headroom target `0.75 × 90 ≈ 67`, +residual) and should **not** repeatedly tap `IG_DAILY_REQUEST_BUDGET` (now **90**). Note this resets to 0 on every restart (in-memory window) — read it after the bot has been up ≥24 h for a true figure.
- **Per-account cadence vs reality:** compare each account's _cached_ interval to its _actual_ posting rate. Cached: `SELECT username, round(poll_interval_ms/60000.0,1) AS interval_min, round(posts_per_day,2) ppd, paused FROM instagram_monitor_accounts ORDER BY poll_interval_ms;`. Actual (last 60 d, deduped across channels): `WITH p AS (SELECT account_username u, ig_post_id, MAX(posted_at) t FROM instagram_monitor_seen_posts WHERE posted_at>=(strftime('%s','now')*1000-60*86400000) GROUP BY 1,2) SELECT u, count(*) n, round(count(*)*1.0/NULLIF((MAX(t)-MIN(t))/86400000.0,0),2) ppd FROM p GROUP BY u ORDER BY ppd DESC;`. Cached `ppd` should ≈ actual `ppd`; a large gap means the cadence estimate is stale or the trust gate is rejecting real history.
- **Intra-day activity curve** (why the once-daily snapshot failed): `SELECT strftime('%H:00',detected_at/1000,'unixepoch','localtime') h, count(DISTINCT ig_post_id) n FROM instagram_monitor_seen_posts WHERE detected_at>=(strftime('%s','now')*1000-36*3600000) GROUP BY 1;`. Expect a quiet morning and an afternoon/evening surge — the stretch should rise/fall with it (watch `instagram_monitor.stretch_update`).
- **Governor trail in the journal:** `journalctl --user -u chopperbot -o cat | grep -E 'cadence_sweep|stretch_update|budget_exhausted'`. `cadence_sweep` is the daily per-account recompute (carries `stretch`/`projected`/`calls_per_poll`); `stretch_update` is the per-tick governor move (≥10 % changes only). `projected` is always ≈ the headroom ceiling **at the moment it logged** — the value is correct, what used to go stale was _how often_ it was recomputed.
- **Polls-bias check (the diagnostic that found the 2026-06-12 fix).** Compare _realized_ polls/day against what the governor _modeled_: realized = `journalctl --user -u chopperbot --since "-24 hours" -o cat --no-pager | grep -c '"msg":"instagram_monitor.fetch.ok"'`; modeled = `projected ÷ calls_per_poll` from the latest `stretch_update`/`cadence_sweep` line. Because the stretch is re-solved every tick to hold the instantaneous projection at the headroom ceiling, **any persistent realized-vs-modeled gap is pure model bias** (intra-day drift can't explain it). Pre-fix this read 70 vs 60 (+17 %); healthy is within ±5 %. Cross-check spend the same way: `requests_24h ÷ realized polls` should ≈ the logged `calls_per_poll` — if it does, the poll _count_ model is what's off, not the per-poll cost (that's exactly how the 2026-06-12 diagnosis isolated the quiet-hours term).

**Resuming after a long outage — three silent states that all look like an empty channel (learned the hard way, 2026-09-10).** After the Sep 2–10 outage the monitor was `active (running)`, logging green `browser.fetch.ok` on every poll, and `#noticias` still sat **empty for ~11 hours**. Nothing in Discord distinguishes these states, and all three look identical to a human staring at the channel:

1. **Kill-switch engaged** (`instagram_monitor_runtime.global_stop = 1`). `tickOnce()` returns before `dueAccounts()`, so nothing is ever polled. Journal: `instagram_monitor.tick.global_stop` (rate-limited to 1/30 min). Check: `SELECT global_stop, stop_reason FROM instagram_monitor_runtime;`
2. **Forward-only seeding** (`instagram_monitor_accounts.last_post_id IS NULL`). A NULL anchor is the _first-ever poll_ branch — `processAccount` records the anchor and returns **without pushing anything** (`instagram_monitor.first_poll_seed`). That is the correct way to "skip the backlog", but it means every poll is a successful no-op. **A NULL anchor will never deliver a single post, no matter how long you wait.**
3. **Cadence decay.** After a long outage every account's learned interval has stretched toward the 12 h ceiling, so a just-seeded account is not due again for up to 12 h. A freshly seeded fleet therefore pushes nothing until roughly the next day _while polling normally_.

Two more delays that are easy to misdiagnose:

- **The resume drip is armed at scheduler _start_, not at resume.** `start()` sets `lastPollAttemptAtMs = Date.now()`, so the first poll after a restart waits the full `RESUME_DRIP_GAP_MS` (10 min) even if the kill-switch is cleared a minute later. Journal: `instagram_monitor.tick.resume_drip` (carries `sinceLastPollMs`).
- **`requests_24h` resets to 0 on every restart** (in-memory window). "0 requests" does not mean "not polling" — read `heartbeat_at` for liveness.

**To deliver a window of recent posts you must set a TIME-CUTOFF anchor; a NULL anchor does the opposite.** One statement, all accounts:

```sql
UPDATE instagram_monitor_accounts
   SET last_post_id = '',                                          -- NOT NULL: skips the seed branch;
                                                                   -- absent from the window → time gate applies
       last_post_at = (strftime('%s','now')*1000 - 12*3600000),    -- the window (here: 12 h)
       last_polled_at = NULL;                                      -- make every account immediately due
```

`last_post_id = ''` is deliberately odd and load-bearing: `NULL` takes the `first_poll_seed` branch (pushes nothing), whereas a non-NULL value **absent from the returned window** falls through to `ordered.filter(p => p.takenAtMs > last_post_at)` — the strict capture-time gate — and pushes everything newer than the cutoff. Expect one `instagram_monitor.anchor_missing.time_gated` per account; that warning is the recipe working. The fan-out still honours `MAX_PUSHES_PER_ACCOUNT_PER_TICK_PER_CHANNEL` (5), and because the drip returns one account per tick, a fleet-wide window backfill lands gradually over ≈10 min × account count rather than as a burst.

The per-tick recompute (2026-06-02) re-reads it every minute, which mitigates this, but it's still a backward-looking estimate. Warmup is now **always on** (2026-09-07, was 0.8), so steady-state is warmup + feed ≈ **2.0** (pk cached). Trust the live `calls_per_poll` log, not this prose.
3. **Account count drift:** prose counts go stale fast (14 → 15 → 18 → **21** as of 2026-08-19). Don't trust the count in prose — `SELECT count(*) FROM instagram_monitor_accounts;`.
4. ~~TLS / JA3 fingerprint (the remaining ceiling)~~ — **CLOSED 2026-09-10 by `IG_FETCH_MODE=browser`.** This residual predicted the API path's ceiling exactly: application-layer headers could claim Macintosh Chrome 148 while the ClientHello came from Node/OpenSSL on Linux ARM. Instagram evidently began enforcing that on 2026-09-02 (see the fetch-path section above). Driving a real Chromium removes the mismatch outright — the TLS stack, headers and www-claim are all genuinely the browser's. Note the remaining edge is now *inverted*: the browser is Linux/ARM Chromium while `IG_USER_AGENT` claims macOS Chrome 151 (kept, because the cookies were minted there and it is what the Pi has been validated with). If IG ever tightens again, the next lever is dropping the UA spoof to advertise the browser's real platform.
5. **Host pairing.** HTML warmup stays on `www.instagram.com/<handle>/`. JSON stays on `i.instagram.com/api/v1/…`. Do **not** treat an i.instagram.com HTML 404 as `require_login` (false-tripped the kill-switch on 2026-09-07 while www warmup still showed the same `.env` session logged in). Do **not** chain extra hosts after an HTML feed — that burst 429'd `web_profile_info` the same afternoon. HTTP 429 wins even when the body is HTML. An HTML body on any JSON API (`InstagramHtmlFeedError`) cools the **whole fleet for 6 h** (`instagram_monitor.html_feed`) without counting as a 429 trip and without treating the cookies as dead. Real session death is still `require_login` JSON / checkpoint / a www warmup that itself serves `not-logged-in`. If every JSON endpoint still returns HTML after that cooldown, the cookies need a browser refresh — don't retry harder.

**Guardrails / circuit breaker — the bot STOPS instead of escalating into a ban.** State lives in the `instagram_monitor_runtime` table (store migration **v5**, a single row id=1) so it survives restarts; `clearFailureBackoff()` deliberately never touches it.

- **429 / throttle** → `InstagramRateLimitError` → global in-memory cooldown (base **6 h**, ×2 per throttle in a **24 h** window, cap 12 h); halts ALL polling. **Three** throttles in 24 h trip the persistent kill-switch. The old 2 h / trip-at-2 policy meant the first poll after the cooldown was a second 429 that killed the monitor (2026-09-02: `@semillasderebeldia` then `@vozdelosdesaparecidospuebla`, both `web_profile_info` re-probes). A 429 on pk-resolve still does **not** fall through to username-feed — retrying another endpoint while throttled is the ban path.
- **HTML on a JSON API** → `InstagramHtmlFeedError` → the same 6 h global cooldown, **no** 429 count and **no** kill-switch. Observed 2026-09-07: www warmup logged-in, every `i.instagram.com` JSON call returned the SPA HTML shell; chaining www / `web_profile_info` then 429'd. Journal: `instagram_monitor.html_feed`.
- **Persistent kill-switch (`global_stop`)** — manual-resume-only. Trips on a SESSION-level auth failure (`require_login`/checkpoint/challenge — see below) or a third throttle in 24 h, fires `postCircuitBrokenAlert` to the config channel, and **stays stopped across restarts** until an operator runs `config_instagram action:resume_monitor confirm:true`. `tickOnce()` reads the row first and returns early while stopped (`instagram_monitor.tick.global_stop`, logged at most once per 30 min — it used to warn every tick). If the journal shows only `rate_limited` / `circuit_broken` and **no** `auth.expired`, the existing `.env` cookies are still the ones to use — don't rotate them just to clear the breaker.
- **Resume drip** (`RESUME_DRIP_STALE_MS` 6 h / `RESUME_DRIP_GAP_MS` 10 min, production only). After a long outage every account is due at once. Catching them up on the normal ~1–3 min tick is a request burst. While any unpaused account was last polled ≥6 h ago, polls are spaced 10 min apart (first poll after resume always goes through). Journal: `instagram_monitor.tick.resume_drip`. Tests leave both knobs at 0 so they can fire two ticks back-to-back.
- **Session vs account-specific auth failures.** `InstagramAuthError.sessionLevel` is true only for `require_login`/checkpoint/challenge/consent (the cookies/account are flagged → halt everything + trip). A **bare 401/403 on one handle** (private/restricted/blocked-relative-to-your-account, or transient) is logged `instagram_monitor.account_auth_failed` and only bumps that account's `consecutive_auth_failures` → it auto-pauses at `AUTH_PAUSE_THRESHOLD` (5) via `dueAccounts()` while the other accounts keep polling. **Do not** treat a per-account 401 as session death — that would stop the whole monitor over one bad handle.
- **Deterministic per-account failures** (`InstagramHardAccountError`, e.g. the `laser.provider` 400) get a **third**, independent counter and their own auto-pause at `HARD_PAUSE_THRESHOLD` (5) — see "Deterministic per-account failures auto-pause the account" above. Neither session-level nor auth-class: the session is fine, the request is simply futile.
- **Daily request budget** `IG_DAILY_REQUEST_BUDGET` (default **90**, lowered from 120 on 2026-08-13) — a rolling-24 h ceiling on outbound IG HTTP calls (the scheduler counts them via `fetcher.observeRequests`); on hit, polling soft-pauses (auto-recovers as the window drains) + one alert (`postBudgetExhaustedAlert`), and `postResumedAlert` fires once on recovery. One poll ≈ **2.0 calls steady-state** after the 2026-09-07 always-on warmup (HTML profile + feed; pk is persisted in SQLite as of v9, so restarts no longer add a resolve burst). This figure is **measured live**, not assumed — see the `callsPerPoll` discussion under the budget governor. The adaptive **budget governor** (above) keeps the steady-state projection below this ceiling, so it should rarely trip.
- **Admin visibility**: `config_instagram action:status` reports kill-switch state/reason, active cooldowns, 24 h request count, paused/blocked counts (auth **and** deterministic-failure auto-pauses, flagged `A`/`D` in the digest table), an `adaptive` block (accounts with a learned cadence + the governor `poll_stretch`), and a `digest_preview` (the exact daily-digest text). `action:digest_now` returns that digest on demand; `action:list` now includes each account's `poll_interval_min` / `posts_per_day`. The scheduler mirrors its in-memory cooldowns into the runtime row once per tick (`writeHeartbeat`) so the (DB-only) admin tool can see them.

**Pinned-post ordering gotcha.** Instagram returns _pinned_ posts first, out of chronological order. The scheduler sorts fetched posts by `takenAtMs` before the dedup walk and anchor advance — otherwise a pinned (old) post sitting at array index 0 would freeze detection (the walk would hit the anchor immediately and never see newer posts below the pins).

**Anchor-missing gotcha (the dedup anchor is `(id, takenAtMs)`, not just an id).** The walk down to the anchor id assumes the anchor post is still in the returned window. IG sometimes returns a _stale or paginated_ window that **omits** the anchor post (eventual consistency, or the post was deleted). The old code then treated the entire returned batch as "new" and **backfilled weeks-old posts**, and `markPollSuccess` moved the anchor _backward_ to that batch's older newest — re-arming the backfill every poll. The fix: each account also stores `last_post_at` (the anchor's `takenAtMs`, added in store migration v3, backfilled from `MAX(seen_posts.posted_at)`). When the anchor id is present we still slice above it (preserving pinned handling); when it's **absent** we fall back to a strict capture-time gate (`takenAtMs > last_post_at`), and the anchor is only ever advanced _forward_ in time. Watch for `instagram_monitor.anchor_missing.time_gated` (a stale window was rejected) and `…anchor_missing.reseed` (a legacy row with no recorded `last_post_at` re-seeding once).

**Undecided-classification gotcha (fixed 2026-08-11) — a transient LLM failure used to discard a post permanently.** `classifyPost` returns `failClassification(...)` when its call throws (`ask_failed: …`) or its reply won't parse (`parse_error`). That shape carries `relevant: false`, and the scheduler treated it as a _verdict_: it wrote the post to `seen_posts` with `pushed=0`, after which `hasSeen` blocked it on every later poll — and the account anchor had already advanced past it, so it was never reconsidered. One provider blip therefore ate the post silently. Measured cost before the fix: **114 distinct posts lost to `ask_failed` + 37 to `parse_error`, ~5.6% of the 2698 ever seen** (1 of them during a provider hard-500 outage that day). The fix gives `Classification` an explicit **`undecided?: true`** flag, and the scheduler now:

- **doesn't record** an undecided post, and **holds the dedup anchor at the post below it** (`instagram_monitor.anchor_held_for_retry`), so the next poll sees it as new and re-classifies it. Rewinding the anchor is safe _because_ per-channel `seen_posts` + the early skip below stop already-settled posts from re-pushing.
- **skips the cover fetch and the LLM call entirely when every bound channel has already seen a post** — this is what makes a held anchor cheap, since a retry poll re-walks everything above the stuck post. (The cover and the relevance/type/date decision are **one** `effort: 'low'` multimodal call on the single `deepseek-flash` backend, so "the cover fetch" and "the LLM call" are one round trip, never a two-stage read-then-decide — see [docs/llm.md](../llm.md).)
- **fails closed past `UNDECIDED_RETRY_HORIZON_MS` (24 h from IG capture time)** — logs `instagram_monitor.undecided.gave_up`, records the post, advances the anchor. A capture-age bound rather than an attempt counter, so no migration; 24 h ≈ 24 retries at the hourly cadence, which covers any realistic outage while guaranteeing one permanently-undecidable post can't wedge the account forever.
  Journal vocabulary: `…undecided.retry_queued` (will retry), `…undecided.gave_up` (horizon passed), `…anchor_held_for_retry` (anchor deliberately not advanced). To find posts lost to the old behavior: `SELECT COUNT(DISTINCT ig_post_id) FROM instagram_monitor_seen_posts WHERE classification_json LIKE '%ask_failed%' OR classification_json LIKE '%parse_error%';` — those rows are **not** retroactively recovered by the fix.

**Changing the watch list is mod-only, and a card can never ping (added 2026-08-13).** Two holes closed together, because they chained:

- `monitor_add_account` / `remove` / `pause` / `force_poll` had **no authorization at all** — anyone who could @-mention the bot in a bound channel edited the _global_ list. `buildTurn` now passes `isMod` (`isModTurn()`, approver role or Administrator — see docs/framework.md) into `InstagramMonitorToolSource`: for a non-mod the four mutating tools are **filtered out of the payload** and `handle()` refuses them anyway (`instagram_monitor.tool_denied`). Read tools stay open, and the preamble gains a paragraph so the bot _explains_ the refusal instead of inventing a reason for a tool it can't see. Tests: `__tests__/source-authz.test.ts`.
- `publishPost` now sends with **`allowedMentions: { parse: [] }`** — stricter than the bot-wide users-only default. A card's text is model output written from a caption on somebody else's Instagram account, i.e. attacker-controlled input this bot republishes unread to every bound channel; with Administrator, `@everyone` in a caption would have rung the server. The chain was: add your own account → post a caption → mass ping.

**Accounts are global** (one row per username, `instagram_monitor_accounts.UNIQUE(username)`). On every detection cycle the scheduler reads the live router for the list of channels currently bound to `instagram_monitor` and **fans out each new post to every bound channel** with per-channel dedup via `instagram_monitor_seen_posts (ig_post_id, channel_id)`. Consequences:

- A newly-bound channel sees no backfill — its `seen_posts` rows start empty and the global `last_post_id` anchor is already current.
- If no channels are bound when a poll fires, the anchor still advances; no posts are classified or recorded as seen.
- Pause / remove / force-poll affect every bound channel.

Posts are pushed in chronological order even though the IG endpoint returns newest-first.

The bot fetches **direct** from the host's residential IP — there is no longer any fetch indirection. (A former `INSTAGRAM_RELAY_LAMBDA_ARN` AWS Lambda relay was removed on 2026-05-30: Instagram blocks all AWS datacenter IP ranges, so rotating within the Lambda pool never helped, and it was unused.) Direct mode requires the spoofed `sec-fetch-*` headers in `fetcher.ts` because Node's undici sends `sec-fetch-site: cross-site` by default and IG rejects it with a 400.

**Fetch path: headless Chromium is primary since 2026-09-10 (`IG_FETCH_MODE=browser`, the default).** Instagram retired the HTTP read path on **2026-09-02** — the exact date the monitor went blind (last successful poll 12:36:56, last push 12:37:02; the following 8 days were an `html_feed` → 6 h cooldown → fail loop). What the API fetcher needs is gone:

- `i.instagram.com/api/v1/feed/user/{pk}/` → **302 → `https://i.instagram.com/` → 404** `not-logged-in` shell.
- `i.instagram.com/api/v1/users/web_profile_info/` → **429 on the first request of a fresh session**, independent of account, cookie age and IP.
- Protocol is not the discriminator: `--http2` and `--http1.1` return identical results, and the same responses come from two unrelated networks (a Mac on 187.190.238.125, the Pi on 187.189.87.54).
- Host/UA pairing is not it either: `i.instagram.com` + the web app-id `936619743392459` is a mismatched pair (yt-dlp #17278), but dropping the app-id and sending a Threads UA yields `403 login_required` / `logout_reason: 37` — a web session is simply not accepted on that host.
- **Cookies are not the problem.** A freshly minted session is provably valid: the profile page returns 200, is _not_ `not-logged-in`, and contains the viewer id; `www.instagram.com/api/v1/users/{pk}/info/` returns real JSON. Everything that still answers is an _info_ route — every timeline route (`feed/user/{pk}`, `feed/user/{username}/username`, `usernameinfo`, `clips/user`, `POST /api/graphql` with the real `doc_id` `39535953862670189` plus a harvested `x-ig-www-claim`) serves the SPA shell or 302s.
- Corroborated by third parties hitting the same wall: instaloader #2726, gallery-dl #8714/#8978, yt-dlp #17278 (which marks its profile extractor `_WORKING = False`).

So the monitor now drives **Chromium over CDP** (`browser-fetcher.ts`, `playwright-core`; auto-resolves newest Playwright-cached chromium → system chromium → macOS Chrome, overridable with `IG_BROWSER_EXECUTABLE_PATH`) and **reads the profile page's own XHR** — `data.xdt_api__v1__feed__user_timeline_graphql_connection` off `https://www.instagram.com/graphql/query`. Nothing is spoofed at the HTTP layer: the browser produces its own TLS fingerprint, headers and www-claim, which is precisely what the API path could not fake. The HTML-warmup-then-XHR shape becomes genuine instead of imitated, and pk-resolution disappears entirely (we navigate by handle), so the `laser.provider` / `prefer_username_feed` machinery is bypassed rather than exercised.

Three details that are load-bearing and easy to break:

- **`igPostId` is the bare `node.pk`, never `node.id`.** `node.id` is `"{pk}_{owner}"`, and the owner half belongs to the **co-author** on collaboration posts (observed: `…_59707196430` on a post surfacing in `@revueltasperiodico`'s timeline). The retired API path derived the bare pk by splitting `item.id`; all pre-existing `instagram_monitor_seen_posts` rows are bare. Switching to `node.id` would make every post look unseen and re-push the whole feed.
- **One browser poll ≠ one API call.** A page load issues dozens of sub-resource requests; counting them individually would blow the 90/day budget on the first poll. The fetcher charges `BROWSER_REQUESTS_PER_POLL = 2` — the legacy path's measured `callsPerPoll` — so the governor's headroom projection and the tuned daily budget keep meaning what they meant. Changing that constant silently changes how much traffic the fleet is allowed. (The budget unit is therefore still "legacy API calls", not page loads.)
- **The browser is reused across polls, not relaunched per poll**, and is torn down after 5 min idle so an idle bot doesn't hold renderer processes; polls are serialised behind one queue.

Failure semantics: a page that renders the `not-logged-in` shell (or lands on `/accounts/login`) throws `InstagramAuthError` and trips the kill-switch exactly as before; a page that merely produced no timeline payload throws a plain error and stays on the transient-retry path. Logs: `instagram_monitor.browser.launched`, `instagram_monitor.browser.fetch.ok`. Tests: `__tests__/browser-fetcher.test.ts` covers the payload contract off a captured fixture — including the `pk` vs `id` rule — so the mapper is verifiable without a browser.

**Rollback:** `IG_FETCH_MODE=api` restores the old `DirectInstagramFetcher`. It stays wired (and is always constructed, because the CDN cover fetch borrows its `cdnHeaders()`) but cannot fetch posts while IG keeps the routes closed.

**Two fetch modes in `DirectInstagramFetcher`:**

- **Anonymous** (no `IG_SESSIONID`): hits the public `web_profile_info` GraphQL endpoint. Returns timeline media but is heavily IP-throttled (frequent `401 require_login`).
- **Authenticated** (`IG_SESSIONID` + `IG_CSRFTOKEN` + `IG_DS_USER_ID` set, optional `IG_MID`/`IG_DID`): far higher rate limits. **Gotcha:** authed `web_profile_info` returns an _empty_ timeline, so auth mode does a two-step fetch — resolve the account's numeric pk via `web_profile_info` (cached per handle), then read the private `feed/user/{pk}` endpoint (different REST item shape, parsed by `parseUserFeedBody`). If pk resolution hard-fails (`InstagramHardAccountError`), auth mode falls back to the username-keyed `feed/user/{username}/username/` endpoint (see "Deterministic per-account failures" above). The bare post id is recovered from the string `item.id` (`"{pk}_{owner}"`), not the numeric `item.pk` (which exceeds `Number.MAX_SAFE_INTEGER` and loses precision); this keeps dedup anchors consistent with the old GraphQL ids. The deployment now uses a **personal** IG account (the throwaway was flagged after ~4 days), which is why the guardrails above (hard stop on real signals, UA matching the cookie source, low/irregular volume) exist — automated polling always carries some ban risk.

**Session expiry → Discord alert.** A SESSION-level auth failure (`require_login` body, or checkpoint/challenge) throws `InstagramAuthError` with `sessionLevel=true`; the scheduler logs `instagram_monitor.auth.expired`, posts `postAuthExpiredAlert` to the config channel (rate-limited 1/6 h), and trips the kill-switch. To recover: clear any challenge in the IG app, refresh `IG_SESSIONID`/`IG_CSRFTOKEN`/`IG_DS_USER_ID` (+`IG_MID`/`IG_DID`) in `.env` from the **same browser** as `IG_USER_AGENT`, `pnpm run build && systemctl --user restart chopperbot.service`, then `config_instagram action:resume_monitor confirm:true`. **Do not rotate cookies for a throttle trip** (`IG throttled N× within …h`) — that is not session death; resume with the same `.env` tokens after the code/path that caused the 429s is fixed. (The old macOS launchd watcher that turned the log line into a Sosumi notification does not exist on the Pi — the bot now alerts Discord directly.)

**Resume alert + daily status digest (config channel).** Two operator-facing signals sit alongside the pause alerts:

- `postResumedAlert` (`✅ sondeo REANUDADO`) fires once when polling resumes after an **abnormal** pause — budget window drained, rate-limit cooldown elapsed, or the kill-switch cleared. The scheduler tracks one `lastBlockReason` set at each abnormal gate (NOT quiet-hours/random-skip, which are normal and leave it untouched) and emits at the proceed-point, debounced (`MIN_PAUSE_FOR_RESUME_MS` 10 min + `RESUME_ALERT_COOLDOWN_MS` 30 min) so a flapping budget can't spam. Seeded from `global_stop` in `start()` so a kill-switch cleared after a restart still alerts once. Log: `instagram_monitor.tick.resumed`.
- A **daily status digest** posts at `STATUS_DIGEST_HOUR` (21:00 America/Mexico_City) from the tick's `finally` block (so it runs regardless of the gates above), once per local day (`instagram_monitor_runtime.last_digest_at`, stamped _after_ a successful send so a failed send — e.g. a restart landing in the digest hour before Discord is reachable — retries next tick). `formatStatusDigest()` (`format.ts`, shared with the admin `status`/`digest_now` so they can't drift) renders overall state, 24 h budget/headroom, governor stretch, and a per-account table (cadence, effective interval, last-post age, next-poll ETA, flags), truncated under Discord's 2000-char limit. This revives the role of the decommissioned macOS 21:00 daily-summary.
