# Workshop capability (private LLM sessions)

> Topic doc — part of the [CLAUDE.md](../../CLAUDE.md) router. Read it BEFORE working in this area, and keep it current in the same change as any behavior change (doc protocol ①/② in the index).


Added 2026-08-06 (v1.11.0). The "Escuela/trabajo" experience: a member reacts 🎓 to the bot's **welcome message** in `#bienvenidx` (`WORKSHOP_WELCOME_CHANNEL_ID`, live `1534976853910229082`) and the bot creates a **private text channel** under the Workshop **category** (`WORKSHOP_CATEGORY_ID`, live `1534988650327310387`) visible only to that member + the bot (admins bypass overwrites). Inside, the bot answers **every message** — no @mention — like a web LLM chat. Lives in `src/capabilities/workshop/`.

- **Passive, NOT routed** (third exception to one-capability-per-channel). Registered in `app.ts` but never in the routing table; `start()` attaches its own listeners: `MessageCreate` (session chat), `MessageReactionAdd` (onboarding), `InteractionCreate` (panel buttons), `ChannelDelete` (bookkeeping when a session channel is deleted by hand). The main handler stays out via the shared `claimedChannel` guard (`isSessionChannel()`, 10 s TTL cache invalidated on session create/close). Needs no secret → `init()` never throws; unconfigured it idles. **Requires the `GuildMessageReactions` intent + `Reaction`/`User` partials** (added to `discord/client.ts` — not privileged, no portal toggle needed) and `MessageContent` (session chat is unmentioned messages).
- **Onboarding**: `ensureWelcomeMessage()` runs at `start()` — posts the welcome message (and self-reacts 🎓) if the stored `welcome_message_id` is missing/deleted, stores the id. The reaction handler checks message id + emoji, fetches partials, enforces `WORKSHOP_MAX_SESSIONS_PER_USER` (2 — over-limit → DM with links, fallback auto-deleting notice in the welcome channel), creates the channel (`taller-<user>[-n]`) with deny-@everyone overwrites, posts the intro + a **pinned panel** with buttons (🧹 Limpiar / 🔒 Cerrar → confirm pair), records the session row, and **removes the member's reaction** so the button stays clean and re-clickable.
- **Chat turns**: channel-based history (`history.ts` — last 50 msgs → ≤20 turns/16k chars, skips the panel, foreign bots and anything ≤ `context_cleared_at`; **no reply-chains needed**), runs on the same shared `TurnQueue` + status reactions as the main handler. Every user attachment is **downloaded into the workspace** (`uploads/`, ≤25 MB, sanitized names — `sanitizeFileName` preserves the extension even when a long name needs truncating; a 5.4 MB Federici book PDF landed extensionless before v1.13.0) so Python can process it; images additionally ride the turn for vision (Nova).
- **History hygiene — operational bot messages are NEVER history** (v1.12.0, `isNoiseAssistantMessage`). Fallbacks (`EMPTY_RESPONSE_FALLBACK`, `CONTENT_FILTER_FALLBACK`, `GENERIC_ERROR_REPLY`, `QUEUE_BUSY_REPLY` — now exported for this), `-# ` status lines, the VirusTotal card, and panel/goodbye lines are filtered from the model's context. **Why (live 2026-08-06):** two genuine "No pude generar una respuesta…" fallbacks in a session's history taught Kimi to answer the user's repeated question with that exact string (1 iteration, 0 tools, verbatim echo) — a self-perpetuating failure that outlived the fix for the original error. Only BOT copies are noise; a user typing the same text is kept.
- **Context compaction per session** (v1.12.0, `compact.ts` + migration **v2**: `summary`/`summary_covers_until` on the session row). `buildChannelHistory` now also returns the turns that overflowed the live window; after the reply posts, `compactSession` (fire-and-forget, one per channel, effort `medium`) folds them + the previous summary into a ≤1800-char running summary whose watermark advances `sinceMs` (history starts at `max(context_cleared_at, summary_covers_until)`), and the prompt injects it as "Resumen de lo trabajado antes". A cleared/closed session or a stale watermark discards the result; "limpiar" wipes the summary too (borrón total).
- **MinIO (2 TB HDD) is the primary durable file store; Discord is the fallback** (added 2026-08-07, v1.14.0; migration **v3** adds `workshop_files.storage_key`). A MinIO server runs in Docker on the Pi (`/srv/seafile/minio`, S3 API `127.0.0.1:9500`, console on the tailnet IP `:9501`, bucket `chopperbot`); the bot authenticates with a bucket-scoped service account (`MINIO_*` env vars). The glue lives in `workshop/storage.ts` (`uploadToStorage` / `restoreFromStorage` / `deleteSessionObjects`, all best-effort — a down MinIO degrades to Discord-only, never breaks a turn): uploads and `workshop_send_file` deliverables are `put` under `workshop/<channelId>/<relPath>` after `recordFile`; `rehydrate()` tries MinIO FIRST (log field `source: minio|discord`) and falls back to the Discord carrier; closing a session (or the GC orphan sweep) also `deletePrefix`es its objects, so close semantics stay "everything is gone" on BOTH stores. Storage disabled (no keys) → the pre-MinIO behavior below, unchanged. Existing files were backfilled with `scripts/migrate-workshop-to-minio.ts` (idempotent; re-run it if rows with NULL `storage_key` ever appear); verify the wiring with `npx tsx scripts/verify-minio-storage.ts`. Journal: `workshop.storage_uploaded`, `workshop.storage_put_failed`, `workshop.storage_get_failed`, `workshop.storage_objects_deleted`, `storage.configured`. **Matching gotcha surfaced by the migration:** Discord normalizes attachment filenames (trailing dots/spaces stripped), so carrier matching uses `attachmentNameMatches()` (raw + sanitized + trailing-dot-folded) — a file recorded as `…2011.` comes back named `…2011`.
- **Discord is the fallback durable file store; the Pi workspace is a cache** (v1.12.0, migration v2 table `workshop_files`). Every delivered file (`workshop_send_file` → the sent message id) and every saved upload (the user's message id) is recorded in a manifest; **`rehydrate()` re-downloads missing local files at turn start by re-fetching the carrying message** (message fetch mints a fresh CDN url — stored urls expire, ids don't; Unknown Message 10008 drops the record, network errors keep it). Consequences wired in: **the purge ("limpiar") skips messages with attachments** (they're the archive — "tus archivos se conservan" is literal), close deletes the manifest + the local dir (the channel, i.e. the store, is gone), and an hourly **`gcSweep()`** drops local copies of archived files in sessions idle >6 h (48 h TTL for unarchived intermediates, which are recomputable from archived uploads) and removes workspaces of no-longer-active sessions. Journal: `workshop.rehydrated`, `workshop.compacted`, `workshop.gc`. **"Limpiar" also consolidates the files into ONE 📁 message** (v1.13.0, `archive.ts`): after the purge, `archiveSessionFiles()` rehydrates any GC'd locals, re-posts every manifest file in a single grouped message (📥 uploads vs 🛠️ generated, ≤10 attachments/message), re-points the manifest at the new message and deletes the now-redundant old carriers — a file is only deleted from its old message AFTER landing on the new one (a failed send leaves duplication, never loss), and files over the send cap keep their original carrier, listed in a "siguen en su mensaje original" section. Empty manifest → no message. Journal: `workshop.files_archived` / `workshop.files_archive_failed`.
- **Sandboxed code execution** (`sandbox.ts`) — the security boundary is **bubblewrap** (`/usr/bin/bwrap`, present on the Pi): `--unshare-all` (NO network), only `/usr` + `/etc` (ro), the venv (ro at `/opt/venv`) and the **session workspace** (rw at `/workspace`) are mounted — `.env`, the DB and other sessions' files are simply not in the mount tree (live-tested: `NETWORK-BLOCKED`, `HOME-HIDDEN` in `sandbox.test.ts`, which runs the real bwrap and is skipped on hosts without it). rlimits via `ulimit` (-v 1.5 GB, -t CPU, -f 1 GiB/file — **one option per `ulimit` call since v1.13.0**: `/bin/sh` is dash, and a combined `ulimit -v … -t … -f …` fails with "too many arguments", which silently dropped ALL the limits) + Node-side wall-clock SIGKILL (`WORKSHOP_PY_TIMEOUT_S`, 60). **No bwrap → the tool refuses** (never runs user code unsandboxed). `buildBwrapArgs` is pure and unit-tested as the security contract (no `/home` mount, exactly one rw bind).
- **Skills venv**: `data/workshop/venv` (~320 MB, built by `scripts/setup-workshop-venv.sh`) with openpyxl, python-docx, python-pptx, reportlab, matplotlib, numpy, pandas, pillow, **pypdf** and **pdfplumber** (added v1.13.0 — text with layout + **table extraction**, the [Anthropic `pdf` skill](https://github.com/anthropics/skills/blob/main/skills/pdf/SKILL.md)'s recommended reader; no OCR/qpdf on the Pi, so scanned PDFs are answered with "no hay OCR, pide versión con texto"). Missing venv → degrades to system python3 (stdlib only, prompt says so). `MPLCONFIGDIR`/`XDG_CACHE_HOME` point at the sandbox tmpfs so matplotlib works. **PDF reading recipe** (prompt, distilled from that skill): `pdfinfo` first → `pdftotext -layout` (page ranges `-f/-l`; poppler is available INSIDE the sandbox because /usr is mounted) → `pdfplumber` for tables/layout → `pypdf` for metadata/merge/split/rotate/encrypt. **Long documents are processed IN BATCHES, not one turn** (v1.13.0 — the 408-page Federici book failure): the old "2–4 Python runs and a delivered file" guidance was WRONG for summarization (a summary needs the text to pass through the model, and the whole book — ~900k chars — can't fit). The prompt now teaches: one prep script (extract + split into `capitulos/` + print the index), **1–3 chapters per turn**, write each section into the deliverable, send the partial file, say exactly where you stopped and ask for a "sigue"; and ALWAYS continue from existing workspace files instead of re-extracting (the turn-3 failure mode was 10 no-op python runs re-reading what turn 1 had already split). Pure transformations (tables, format converts, merge/split) still go all-Python with no text through the conversation.
- **Live status line UX** (added v1.12.0, `src/discord/status-message.ts`). Workshop turns show ONE Discord subtext message (`-# 🐍 Ejecutando código · paso 3 · 45s`) that is **edited in place** as the turn progresses (throttled ≥1.5 s between edits; a 10 s ticker keeps the elapsed time moving through long Kimi requests) and finally **morphs into the reply itself** (`finishAsReply` edits the first chunk over the status line — no delete/send flicker). Aborted turns delete the line; failed turns edit it into the Spanish error. The ⏳ queued reaction still covers the pre-start wait; public mention-gated channels keep the plain reaction set (an extra bot message per turn would be noise there). Tool→label mapping (`toolLabel`) and the line composer (`composeStatusText`) are pure + tested.
- **Degenerate-output guard + per-turn context budget** (v1.12.0, the third live failure of the same session). At **147k input tokens** — reached by reading chapter files at 16k chars each — Kimi *lost the tool-call protocol* and emitted its own scaffolding as visible content ("Use the tool. Done. Now. `{"name": "workshop_read_file", …}`"), which shipped to the member's taller as ~8 chunked messages. Three independent guards now exist: (1) `isDegenerateOutput()` in `llm/client.ts` (narrow: a raw `<tool_call>`/`{"name":…,"arguments":…}` envelope, or ≥5 scaffolding tells) discards such text as if it were empty → the existing retry runs, then a **tools-free forcing pass** with an explicit "responde en prosa, sin herramientas" nudge (removing the tools is exactly what un-sticks the protocol confusion), and a still-degenerate result falls back to the Spanish message; (2) `WorkshopToolSource` enforces `TURN_PAYLOAD_BUDGET_CHARS` (45k) across a turn's tool payloads, with `workshop_read_file` defaulting to 6k and hard-capped at 20k — over budget the tool refuses and tells the model to process with Python instead; (3) `MAX_REPLY_CHUNKS` bounds the damage of anything that still slips through. The prompt states the expectation for a whole book: ~2–4 Python runs and a delivered file, not ten file reads.
- **Kimi output budget** (`KIMI_MAX_OUTPUT_TOKENS`, default 16384; added v1.12.0). K2.7 Thinking's `reasoning_content` counts against `max_tokens`, so the shared 4096 starved complex turns — live: the levrouge session's "te armo un documento Word…" reply was a `stopReason: 'length'` truncation and the promised docx never got created. The Kimi path (both loop and forcing pass) now rides this dedicated budget (endpoint probed OK at ≥24k; the coding subscription is flat-rate so bigger outputs cost nothing); Bedrock keeps `MAX_OUTPUT_TOKENS`. The workshop prompt also now forbids announcing future work ("el archivo se crea EN ESTA MISMA VUELTA") and teaches the incremental big-text workflow (never read a whole book into context via `workshop_read_file`; extract with Python).
- **Interrupt semantics** (added v1.12.0, same incident: the member wrote "nooo" mid-loop and it queued behind ~2 more minutes of thrash). A NEW message from the session owner **aborts the channel's older pending/running turn**: `ask()` grew `shouldAbort?: () => boolean`, checked between model requests and between tool calls (never mid-tool — a write is never half-applied), throwing `TurnAbortedError` (logged `agent_turn_aborted`); the watcher flips a per-channel flag (`turnAborts`) on each new owner message and the superseded turn exits silently (`workshop.turn_interrupted`, reaction cleaned, no reply, deferred actions skipped) while the new turn — behind it in the FIFO queue — answers with full history including whatever the aborted turn's tools already left in the workspace. Web-LLM interrupt behavior, deliberately scoped to workshop only (in public mention-gated channels a new message is usually a DIFFERENT user's question, not an interruption).
- **Tools** (`tools.ts`): `workshop_run_python` (returns stdout/stderr capped head+tail at ~6k chars + a `files_changed` diff of the workspace), `workshop_write_file`/`read_file`/`list_files` (all traversal-guarded by `safeJoin`), `workshop_send_file` (uploads a workspace file ≤9.5 MB to the channel), `workshop_rename_session`, `workshop_clear_session`, `workshop_close_session` (requires `confirm:true`). **Send/clear/close are deferred intents** executed by the watcher AFTER the reply posts (`SessionActions`) — deleting messages or the channel mid-agent-loop would break the reply itself. Clear = `context_cleared_at` now + bulk-purge after (keeps pins/panel, <14-day Discord limit); close = goodbye → 5 s → channel delete → row `closed` (workspace dir is kept on disk).
- **Persistence** (`store.ts`, migration v1): single-row `workshop_settings` (welcome channel/message, category, emoji — env seeds on first boot, DB wins after) + `workshop_sessions` (one row per channel; `context_cleared_at`, `panel_message_id`, status active/closed).
- **Admin surface** (config channel): `config_workshop` — `status` (settings, session counts, sandbox/venv availability), `list_sessions`, `close_session {channel_id}`, `set_channels`, `set_emoji`, `repost_welcome`. Close/repost act on the LIVE capability via `configCap.attachWorkshopAdmin()` (wired in `app.ts`).
- **Verify:** `npx vitest run src/capabilities/workshop` (store/workspace/sandbox-args/tools/history/names/archive + the live-bwrap integration tests) and the read-only `npx tsx scripts/verify-workshop.ts` (prints DB settings, the welcome message state, and a ✅/❌ permission checklist for the welcome channel + category: needs ManageMessages in welcome, ManageChannels+ManageRoles in the category). Journal: `workshop.welcome.posted`, `workshop.session_created`, `workshop.turn`, `workshop.python_run`, `workshop.file_sent`, `workshop.files_archived`, `workshop.session_closed`.
