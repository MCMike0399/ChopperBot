# Workshop capability (private LLM sessions)

> Topic doc — part of the [CLAUDE.md](../../CLAUDE.md) router. Read it BEFORE working in this area, and keep it current in the same change as any behavior change (doc protocol ①/② in the index).

Added 2026-08-06 (v1.11.0). The "Escuela/trabajo" experience: a member reacts 🎓 to the bot's **welcome message** in `#bienvenidx` (`WORKSHOP_WELCOME_CHANNEL_ID`, live `1534976853910229082`) and the bot creates a **private text channel** under the Workshop **category** (`WORKSHOP_CATEGORY_ID`, live `1534988650327310387`) visible only to that member + the bot (admins bypass overwrites). Inside, the bot answers **every message** — no @mention — like a web LLM chat. Lives in `src/capabilities/workshop/`.

- **Passive, NOT routed** (third exception to one-capability-per-channel). Registered in `app.ts` but never in the routing table; `start()` attaches its own listeners: `MessageCreate` (session chat), `MessageReactionAdd` (onboarding), `InteractionCreate` (panel buttons), `ChannelDelete` (bookkeeping when a session channel is deleted by hand). The main handler stays out via the shared `claimedChannel` guard (`isSessionChannel()`, 10 s TTL cache invalidated on session create/close). Needs no secret → `init()` never throws; unconfigured it idles. **Requires the `GuildMessageReactions` intent + `Reaction`/`User` partials** (added to `discord/client.ts` — not privileged, no portal toggle needed) and `MessageContent` (session chat is unmentioned messages).
- **Onboarding**: `ensureWelcomeMessage()` runs at `start()` — posts the welcome message (and self-reacts 🎓) if the stored `welcome_message_id` is missing/deleted, stores the id. If the stored message is still there but the copy drifted (e.g. naming the live text brain), it **edits in place** instead of posting a duplicate (`workshop.welcome.updated`). The reaction handler checks message id + emoji, fetches partials, enforces `WORKSHOP_MAX_SESSIONS_PER_USER` (2 — over-limit → DM with links, fallback auto-deleting notice in the welcome channel), creates the channel (`taller-<user>[-n]`) with deny-@everyone overwrites, posts the intro + a **pinned panel** with buttons (🧹 Limpiar / 🔒 Cerrar → confirm pair), records the session row, and **removes the member's reaction** so the button stays clean and re-clickable. The welcome copy names the live text brain (`textBrainDisplayName()`, currently **DeepSeek V4 Flash**).
- **Chat turns**: channel-based history (`history.ts` — last 50 msgs → ≤20 turns/16k chars, skips the panel, foreign bots and anything ≤ `context_cleared_at`; **no reply-chains needed**), runs on the same shared `TurnQueue` + status reactions as the main handler. Every user attachment is **downloaded into the workspace** (`uploads/`, ≤25 MB, sanitized names — `sanitizeFileName` preserves the extension even when a long name needs truncating; a 5.4 MB Federici book PDF landed extensionless before v1.13.0) so Python can process it; images additionally ride the turn for vision (Nova).
- **History hygiene — operational bot messages are NEVER history** (v1.12.0, `isNoiseAssistantMessage`). Fallbacks (`EMPTY_RESPONSE_FALLBACK`, `CONTENT_FILTER_FALLBACK`, `GENERIC_ERROR_REPLY`, `QUEUE_BUSY_REPLY` — now exported for this), `-# ` status lines, the VirusTotal card, and panel/goodbye lines are filtered from the model's context. **Why (live 2026-08-06):** two genuine "No pude generar una respuesta…" fallbacks in a session's history taught Kimi to answer the user's repeated question with that exact string (1 iteration, 0 tools, verbatim echo) — a self-perpetuating failure that outlived the fix for the original error. Only BOT copies are noise; a user typing the same text is kept.
- **Context compaction per session** (v1.12.0, `compact.ts` + migration **v2**: `summary`/`summary_covers_until` on the session row). `buildChannelHistory` now also returns the turns that overflowed the live window; after the reply posts, `compactSession` (fire-and-forget, one per channel, effort `medium`) folds them + the previous summary into a ≤1800-char running summary whose watermark advances `sinceMs` (history starts at `max(context_cleared_at, summary_covers_until)`), and the prompt injects it as "Resumen de lo trabajado antes". A cleared/closed session or a stale watermark discards the result; "limpiar" wipes the summary too (borrón total).
- **MinIO (1 TB SSD) is the primary durable file store; Discord is the fallback** (added 2026-08-07, v1.14.0; migration **v3** adds `workshop_files.storage_key`). A MinIO server runs in Docker on the Pi (**`/srv/minio`**, S3 API `127.0.0.1:9500`, console on the tailnet IP `:9501`, bucket `chopperbot`); the bot authenticates with a bucket-scoped service account (`MINIO_*` env vars). **Moved off the 2 TB HDD to the SSD on 2026-08-10** (`/srv/seafile/minio` → `/srv/minio`, both the data dir _and_ the compose stack) so the workshop file store no longer depends on the external disk. Two things had to move with it: (1) the `RequiresMountsFor=/srv/seafile` drop-in on `docker.service` was dropped — it made the whole Docker engine, hence MinIO, refuse to start without the HDD; the guard it provided now sits on Seafile's own bind mounts in `/srv/seafile/compose/seafile-server.yml`, declared in **long syntax with `create_host_path: false`** so a missing HDD makes _those_ containers refuse to start instead of silently binding an empty dir (short syntax auto-creates it — verified both ways: `compose up` and restart-policy `docker start` both fail, and the daemon does not recreate the host path). MinIO's own bind carries the same flag. (2) `.minio.sys` must be copied with the data (`rsync -aHAX`) — it holds the bucket metadata and the IAM policy, so a whole-dir copy needs no re-provisioning and no `.env` change. The glue lives in `workshop/storage.ts` (`uploadToStorage` / `restoreFromStorage` / `deleteSessionObjects`, all best-effort — a down MinIO degrades to Discord-only, never breaks a turn): uploads and `workshop_send_file` deliverables are `put` under `workshop/<channelId>/<relPath>` after `recordFile`; `rehydrate()` tries MinIO FIRST (log field `source: minio|discord`) and falls back to the Discord carrier; closing a session (or the GC orphan sweep) also `deletePrefix`es its objects, so close semantics stay "everything is gone" on BOTH stores. Storage disabled (no keys) → the pre-MinIO behavior below, unchanged. Existing files were backfilled with `scripts/migrate-workshop-to-minio.ts` (idempotent); since 2026-08-11 rows with NULL `storage_key` **self-heal**: the watcher's hourly maintenance (`storageBackfill()`, plus one pass ~60 s after boot) re-uploads them from the local cache or the Discord carrier (journal: `workshop.storage_backfill`), and the systemd unit's `ExecStartPre` waits for MinIO at boot so the race window mostly doesn't happen (see docs/deployment.md). Verify the wiring with `npx tsx scripts/verify-minio-storage.ts`. Journal: `workshop.storage_uploaded`, `workshop.storage_put_failed`, `workshop.storage_get_failed`, `workshop.storage_objects_deleted`, `storage.configured`. **Matching gotcha surfaced by the migration:** Discord normalizes attachment filenames (trailing dots/spaces stripped), so carrier matching uses `attachmentNameMatches()` (raw + sanitized + trailing-dot-folded) — a file recorded as `…2011.` comes back named `…2011`. **Second gotcha, and the reason this store fails SILENTLY: the `chopperbot` identity is MinIO-side state that the repo cannot restore.** Surfaced 2026-08-10 during the SSD move: the user had vanished from MinIO IAM (`config/iam/users/` empty) while its `chopperbot-workshop` policy survived orphaned, so every call 403'd and the workshop had been running **Discord-only since 2026-08-08 22:40** — visible only as `storage.minio.ensure_failed` + `workshop.storage_unavailable` in the journal, because best-effort degradation is by design and never surfaces to a member or an admin alert. Fix (no `.env` change — the bot's key is still valid): `mc admin user add local chopperbot <MINIO_SECRET_KEY>` then `mc admin policy attach local chopperbot-workshop --user chopperbot`. **Run `npx tsx scripts/verify-minio-storage.ts` after any MinIO/Docker/disk work** — a green `put/get` is the only cheap proof the primary store is actually primary. A row can also keep a `storage_key` whose object is gone (`setStorageKey` only runs after a successful `put`, so the key was once real); those files still rehydrate from their Discord carrier, and re-uploading means `UPDATE workshop_files SET storage_key=NULL` for the row and re-running `scripts/migrate-workshop-to-minio.ts`.
- **Discord is the fallback durable file store; the Pi workspace is a cache** (v1.12.0, migration v2 table `workshop_files`). Every delivered file (`workshop_send_file` → the sent message id) and every saved upload (the user's message id) is recorded in a manifest; **`rehydrate()` re-downloads missing local files at turn start by re-fetching the carrying message** (message fetch mints a fresh CDN url — stored urls expire, ids don't; Unknown Message 10008 drops the record, network errors keep it). Consequences wired in: **the purge ("limpiar") skips messages with attachments** (they're the archive — "tus archivos se conservan" is literal), close deletes the manifest + the local dir (the channel, i.e. the store, is gone), and an hourly **`gcSweep()`** drops local copies of archived files in sessions idle >6 h (48 h TTL for unarchived intermediates, which are recomputable from archived uploads) and removes workspaces of no-longer-active sessions. Journal: `workshop.rehydrated`, `workshop.compacted`, `workshop.gc`. **"Limpiar" also consolidates the files into ONE 📁 message** (v1.13.0, `archive.ts`): after the purge, `archiveSessionFiles()` rehydrates any GC'd locals, re-posts every manifest file in a single grouped message (📥 uploads vs 🛠️ generated, ≤10 attachments/message), re-points the manifest at the new message and deletes the now-redundant old carriers — a file is only deleted from its old message AFTER landing on the new one (a failed send leaves duplication, never loss), and files over the send cap keep their original carrier, listed in a "siguen en su mensaje original" section. Empty manifest → no message. Journal: `workshop.files_archived` / `workshop.files_archive_failed`.
- **Symlink containment in the file tools — the sandbox's blind spot (fixed 2026-08-13, `workspace.ts`).** bwrap confines the _python_; it does nothing about the **Node side**, and `safeJoin` only ever reasoned about the path _string_. Sandboxed code can't read `/home`, but it can write `os.symlink('../../../../.env', '/workspace/loot.pdf')` inside its own mount — and then `workshop_send_file loot.pdf` runs in the BOT process, where `readFileSync` follows the link and mails `DISCORD_TOKEN` / `KIMI_API_KEY` / the Bedrock keys to a member's Discord channel; `workshop_write_file` through a link to `dist/index.js` is code execution as the bot on the next restart. No jailbreak required — "run this Python" is the advertised feature. Three layers now: (1) `assertNoSymlink()` walks **every component** below the workspace root with `lstat` and refuses any symlink, wherever it points (a flat ban: symlinks have no legitimate use in a session workspace, and resolve-then-recheck invites clever relative targets); `SessionWorkspace.absolute()` = `safeJoin` + that walk, so docindex and the file tools inherit the boundary. (2) The actual open uses **`O_NOFOLLOW`** (`ELOOP` → the same `PathEscapeError`), closing the check-then-open race the kernel is the only place to close. (3) `runPython` **rm -rf's `.workshop` before recreating it** and writes the staged script with `wx` — recursive `mkdir` happily accepts an existing symlink-to-dir, so a previous run could have aimed the _next_ run's script write anywhere the bot can write. Symlinks were already invisible to `list()` (`Dirent.isFile()` is false for them), so the model is never even offered one. Real-fs tests in `__tests__/workspace.test.ts` cover file links, directory-component links, links pointing back inside, and that ordinary files still round-trip.
- **Sandboxed code execution** (`sandbox.ts`) — the security boundary is **bubblewrap** (`/usr/bin/bwrap`, present on the Pi): `--unshare-all` (NO network), only `/usr` + `/etc` (ro), the venv (ro at `/opt/venv`) and the **session workspace** (rw at `/workspace`) are mounted — `.env`, the DB and other sessions' files are simply not in the mount tree (live-tested: `NETWORK-BLOCKED`, `HOME-HIDDEN` in `sandbox.test.ts`, which runs the real bwrap and is skipped on hosts without it). rlimits via `ulimit` (-v 1.5 GB, -t CPU, -f 1 GiB/file — **one option per `ulimit` call since v1.13.0**: `/bin/sh` is dash, and a combined `ulimit -v … -t … -f …` fails with "too many arguments", which silently dropped ALL the limits) + Node-side wall-clock SIGKILL (`WORKSHOP_PY_TIMEOUT_S`, 60). **No bwrap → the tool refuses** (never runs user code unsandboxed). `buildBwrapArgs` is pure and unit-tested as the security contract (no `/home` mount, exactly one rw bind).
- **Skills venv**: `data/workshop/venv` (~320 MB, built by `scripts/setup-workshop-venv.sh`) with openpyxl, python-docx, python-pptx, reportlab, matplotlib, numpy, pandas, pillow, **pypdf** and **pdfplumber** (added v1.13.0 — text with layout + **table extraction**, the [Anthropic `pdf` skill](https://github.com/anthropics/skills/blob/main/skills/pdf/SKILL.md)'s recommended reader; no OCR/qpdf on the Pi, so scanned PDFs are answered with "no hay OCR, pide versión con texto"). Missing venv → degrades to system python3 (stdlib only, prompt says so). `MPLCONFIGDIR`/`XDG_CACHE_HOME` point at the sandbox tmpfs so matplotlib works. Python PDF manipulation (tables → `pdfplumber`, metadata/merge/split → `pypdf`, `pdftotext -layout` to a file) stays in the prompt; **reading/summarizing/QA over long documents goes through the document index below**, not through raw extraction.
- **Document index — the big-document skill (v1.17.0, `docindex.ts`).** The durable fix for the 408-page Federici failure (v1.13.0's batching prompt helped, but the model still improvised the extraction each session and one full pass could still flood the context, 147k input tokens live 2026-08-06). A canned, **sandboxed** Python pass (built by `buildIndexerScript`, run through the same `runPython`/bwrap path as user code) extracts PDF (`pdftotext -layout`, pages split on form feeds) / DOCX (python-docx) / TXT/MD once into `.docindex/<slug>-<hash>/` — `meta.json` (source identity + outline) + `chunks.jsonl` (~1800-char page-aware chunks, heading detection: Capítulo/Chapter/Sección… prefixes or ALL-CAPS lines). Three tools ride it: **`workshop_doc_index {path}`** (build or reuse — freshness = source `bytes:mtime` key, so re-calling is free), **`workshop_doc_search {path, query}`** (pure-TS lexical retrieval in `searchChunks`: idf-weighted, accent-insensitive token overlap + phrase bonus, stopword-filtered; top-k excerpts with page refs), **`workshop_doc_read {path, from_page, to_page}`** (bounded page-range read, 12k/call cap). All three charge the turn payload budget; search/read auto-build the index when missing. `.docindex` is a HIDDEN_PREFIX (never in listings/deliverables; `.workshop` couldn't be reused — it's wiped after every python run) and dies with the workspace on close/GC. Scanned PDFs → clean Spanish error (`sin_texto_extraible`). The prompt's long-document strategy is now: index once → puntual questions via search (cite pages) → summaries via read, 1–3 chapters per turn, deliver partial + "sigue". **Measured on the real Federici book (Pi, 2026-08-11): 409 pages / 895k chars → 351 chunks in 0.7 s; search 68 ms**; live e2e (`scripts/e2e-workshop-doc.ts`, real Kimi turn): index + 3 searches → page-cited answer, zero raw full-document reads. Probe offline with `npx tsx scripts/probe-doc-index.ts <file|minio:channel/relPath> "query"`.
- **Live status line UX** (v1.12.0 `status-message.ts`; abstracted v1.17.0 into `src/discord/presenter.ts`). The conversation style is now a **`TurnPresenter`** the turn pipeline drives blindly (`onQueued`/`begin`/`onPhase`/`deliver`/`fail`/`discard`): the workshop uses `WorkshopTurnPresenter` — ⏳ while queued, then ONE Discord subtext message (`-# 🐍 Ejecutando código · paso 3 · 45s`) **edited in place** (throttled ≥1.5 s; a 10 s ticker keeps the elapsed time moving; typing heartbeat at 5 s) that finally **morphs into the reply itself** (no delete/send flicker). Aborted turns delete the line; failed turns edit it into the Spanish error; a pre-start failure (queue busy) replies plainly with ❌. Public channels use `ReactionTurnPresenter` (reactions + typing ONLY — see docs/framework.md; the v1.12.0 slow-turn escalation to a status line in public channels was REMOVED in v1.17.0 by user directive: the rich status belongs to talleres, public stays quiet). Doc tools have their own labels (📚 Indexando / 🔎 Buscando / 📖 Leyendo el documento). `toolLabel` + `composeStatusText` stay pure + tested; presenters are tested against a fake message op-log (`presenter.test.ts`).
- **Degenerate-output guard + per-turn context budget** (v1.12.0, the third live failure of the same session). At **147k input tokens** — reached by reading chapter files at 16k chars each — Kimi _lost the tool-call protocol_ and emitted its own scaffolding as visible content ("Use the tool. Done. Now. `{"name": "workshop_read_file", …}`"), which shipped to the member's taller as ~8 chunked messages. Three independent guards now exist: (1) `isDegenerateOutput()` in `llm/client.ts` (narrow: a raw `<tool_call>`/`{"name":…,"arguments":…}` envelope, or ≥5 scaffolding tells) discards such text as if it were empty → the existing retry runs, then a **tools-free forcing pass** with an explicit "responde en prosa, sin herramientas" nudge (removing the tools is exactly what un-sticks the protocol confusion), and a still-degenerate result falls back to the Spanish message; (2) `WorkshopToolSource` enforces `TURN_PAYLOAD_BUDGET_CHARS` (45k) across a turn's tool payloads, with `workshop_read_file` defaulting to 6k and hard-capped at 20k — over budget the tool refuses and tells the model to process with Python instead; (3) `MAX_REPLY_CHUNKS` bounds the damage of anything that still slips through. The prompt states the expectation for a whole book: ~2–4 Python runs and a delivered file, not ten file reads.
- **Kimi output budget** (`KIMI_MAX_OUTPUT_TOKENS`, default 16384; added v1.12.0). K2.7 Thinking's `reasoning_content` counts against `max_tokens`, so the shared 4096 starved complex turns — live: the levrouge session's "te armo un documento Word…" reply was a `stopReason: 'length'` truncation and the promised docx never got created. The Kimi path (both loop and forcing pass) now rides this dedicated budget (endpoint probed OK at ≥24k; the coding subscription is flat-rate so bigger outputs cost nothing); Bedrock keeps `MAX_OUTPUT_TOKENS`. The workshop prompt also now forbids announcing future work ("el archivo se crea EN ESTA MISMA VUELTA") and teaches the incremental big-text workflow (never read a whole book into context via `workshop_read_file`; extract with Python). **Empty `length` on DeepSeek `high` (2026-09-02, v1.28.2):** a taller research turn (`investiga y anota la referencia de la población…`) ran thinking-on, spent 3 × 16384 output tokens on reasoning with **0 tools and 0 visible text**, and the member got the empty fallback. The empty-retry now disables thinking after a `length` miss and the forcing pass also runs for `length` — the retry an hour later (same prompt) answered because thinking happened to emit text that time. See [docs/llm.md](../llm.md).
- **Interrupt semantics** (added v1.12.0, same incident: the member wrote "nooo" mid-loop and it queued behind ~2 more minutes of thrash). A NEW message from the session owner **aborts the channel's older pending/running turn**: `ask()` grew `shouldAbort?: () => boolean`, checked between model requests and between tool calls (never mid-tool — a write is never half-applied), throwing `TurnAbortedError` (logged `agent_turn_aborted`); the watcher flips a per-channel flag (`turnAborts`) on each new owner message and the superseded turn exits silently (`workshop.turn_interrupted`, reaction cleaned, no reply, deferred actions skipped) while the new turn — behind it in the FIFO queue — answers with full history including whatever the aborted turn's tools already left in the workspace. Web-LLM interrupt behavior, deliberately scoped to workshop only (in public mention-gated channels a new message is usually a DIFFERENT user's question, not an interruption).
- **Tools** (`tools.ts`): `workshop_run_python` (returns stdout/stderr capped head+tail at ~6k chars + a `files_changed` diff of the workspace), `workshop_write_file`/`read_file` (traversal-guarded by `safeJoin`), `workshop_doc_index`/`doc_search`/`doc_read` (the document-index skill — see its bullet), `workshop_list_files` (also reports each file's delivery state — see the ledger bullet), `workshop_send_file` (uploads a workspace file ≤9.5 MB to the channel), `workshop_rename_session`, `workshop_clear_session`, `workshop_close_session` (requires `confirm:true`). **Send/clear/close are deferred intents** executed by the watcher AFTER the reply posts (`SessionActions`) — deleting messages or the channel mid-agent-loop would break the reply itself. Clear = `context_cleared_at` now + bulk-purge after (keeps pins/panel, <14-day Discord limit); close = goodbye → 5 s → channel delete → row `closed` (workspace dir is kept on disk).
- **Delivery ledger + auto-delivery safety net + assistant tone** (v1.15.0, the 2026-08-09 estatutos incident: the model generated a corrected .docx/.pdf, ended the turn WITHOUT `workshop_send_file`, then spent six messages insisting "ya te lo envié, kbron" — the files never left the workspace, and the model had NO way to know). Three layers: (1) **the model can see delivery state** — the prompt's workspace listing marks each file `📥 subido por el usuario` / `✅ ya entregado` / `⚠️ NO entregado` (deliverable extensions only, `isDeliverablePath`; .txt intermediates stay plain so the listing doesn't cry wolf) and `workshop_list_files` returns `tipo`/`entregado` per file + `pendientes_de_entrega` (the manifest is the ledger: a file counts as delivered once `recordFile` ran on send, and uploads count as delivered by definition); (2) **prompt rules** — never claim a delivery that didn't happen (only ✅ or your own `workshop_send_file` call counts), and on "no me llegó" verify with `list_files` and (re)send IN THE SAME TURN; the Kimi forcing-pass nudge also forbids claiming un-executed sends (docs/llm.md); (3) **auto-net** — after each reply the watcher diffs the workspace against a turn-start mtime snapshot (`listUndeliveredDeliverables` in `workspace.ts`: deliverable extension, created/rewritten this turn, not queued, not already manifested, ≤9.5 MB) and attaches what the model forgot (`workshop.file_auto_send`, skipped on session close). **Tone:** the persona is now explicitly a warm, patient, RESPECTFUL assistant — never mirrors insults/vulgar slang back (the same session earned a "No inultes chopperbot"), and on user frustration it acknowledges + verifies + fixes instead of insisting. **Triage/repair scripts:** `scripts/dump-workshop-channel.ts` (read-only conversation dump), `scripts/preview-workshop-prompt.ts` (render the exact prompt the next turn will get, ledger included), `scripts/workshop-deliver-file.ts` (re-deliver a workspace file as the bot, keeping the manifest + MinIO invariants).
- **Persistence** (`store.ts`, migration v1): single-row `workshop_settings` (welcome channel/message, category, emoji — env seeds on first boot, DB wins after) + `workshop_sessions` (one row per channel; `context_cleared_at`, `panel_message_id`, status active/closed).
- **Admin surface** (config channel): `config_workshop` — `status` (settings, session counts, sandbox/venv availability), `list_sessions`, `close_session {channel_id}`, `set_channels`, `set_emoji`, `repost_welcome`. Close/repost act on the LIVE capability via `configCap.attachWorkshopAdmin()` (wired in `app.ts`).
