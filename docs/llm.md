# LLM client (`src/llm/client.ts`)

> Topic doc — part of the [CLAUDE.md](../CLAUDE.md) router. Read it BEFORE working in this area, and keep it current in the same change as any behavior change (doc protocol ①/② in the index).

**Dual backend, chosen per turn (repointed 2026-07-13).** The **text brain** — **every** text domain: Discord chat, calendar/config tool-calling, event-intake proposals, and the IG classifier's actual relevance/type/date **decision** — runs on **DeepSeek V4-Flash** (live since 2026-08-13; Moonshot Kimi 2.7 Thinking before that) via the OpenAI-compatible chat-completions API (the `openai` SDK). **Bedrock (Amazon Nova Lite) is used ONLY for images**, because neither text brain can see. (The IG classifier is **two-stage** since 2026-07-15 — Nova only _reads_ the flyer, the text brain _decides_; see the effort-tier bullet below.) `ask()` picks the backend by this rule: **effort `low` → Bedrock/Nova Lite** (the vision tier — IG transcription, or a caller that wants pixels in / text out with no tool loop); **a turn carrying an image at `high`/`medium` → TWO-STAGE** (Nova transcribes, the text brain runs the tool loop — same pattern as the IG classifier, made generic 2026-09-03); **everything else (all text) → the selected text brain**. (This reversed the 2026-06-23 all-Bedrock migration for the whole text brain, keeping only vision on Bedrock — user directive: "medium and high are the text brain; Nova is only `low`; use it only for images.") The two loops live side by side in `client.ts` as `askKimi()` / `askBedrock()`; both report to `llmHealth` via `observedCompletion` and log an `agent_turn` line carrying `backend` (`kimi`|`deepseek`|`bedrock`) + `model` + `effort`. Since 2026-08-10 the text brain is a **selectable slot** (`LLM_TEXT_BACKEND=kimi|deepseek|bedrock`) rather than hardcoded Kimi — see the first bullet below. The images-only rule for Nova is unchanged and unchangeable: neither text brain can see. A failed transcription still strips the pixels (so we don't recurse) and the text brain answers from the user's words.

- **The text brain is a selectable slot (`LLM_TEXT_BACKEND`, 2026-08-10).** `kimi` (default) and `deepseek` both speak the same OpenAI chat-completions wire shape, so **`askKimi()` serves either** — `src/config.ts` resolves the selector into one `textBackend` object (`{provider, apiKey, baseUrl, modelId, userAgent, maxOutputTokens, maxConcurrent}`) and the loop reads only that. Switching providers is one env var, no code change; the `agent_turn` log line carries the real `backend` (`kimi`|`deepseek`|`bedrock`), so the journal stays truthful. `bedrock` remains the third option for AWS-native deploys. Adding another OpenAI-compatible provider means adding a branch to the resolver, not to the loop.
   - **DeepSeek is the live text brain since 2026-08-13, permanently** (`LLM_TEXT_BACKEND=deepseek`). The Kimi coding subscription **exhausted its billing-cycle quota ~10 days before the sub's 2026-08-23 end**: `/models` still answered `200`, but every `/chat/completions` returned **`403 {"type":"access_terminated_error"}` — "You've reached your usage limit for this billing cycle… purchase extra usage or upgrade your plan"**. That is a different signature from the 08-11 provider outage below and worth telling apart: **08-11 = 500 on _every_ route including `/models`** (provider down); **08-13 = 200 on `/models`, 403 only on completions** (our quota). In both cases a deliberately invalid key still returns a clean `401`, so the 401 probe distinguishes "bad credentials" from either failure. Quota is not something retries or a health watchdog can clear, so this simply brought the already-planned 2026-08-23 cutover forward — **do not flip back to `kimi`**; the sub lapses on 08-23 anyway. Recovery was **`.env` one-liner + `systemctl --user restart chopperbot.service`, no rebuild** (the selector is read at boot; `dist/` was untouched). Verified after the cutover: `scripts/text-backend-trial.ts` on the live path, plus `npx vitest run src/__tests__/config.test.ts src/llm` green. Note the Zod default is still `kimi`, so a **wiped or re-seeded `.env` now lands on a dead backend** — `LLM_TEXT_BACKEND=deepseek` must be set explicitly.
   - **Kimi was the live text brain from 2026-08-11 ~15:00 CST until the 08-13 quota exhaustion above** (`LLM_TEXT_BACKEND=kimi`). Timeline of that day: at 12:27 CST the Kimi-For-Coding endpoint went hard-500 on every route — `/chat/completions` for every model id _and_ `/models` — while a deliberately invalid key still got a clean `401`, proving the failure was provider-side rather than credentials or quota. Every text turn died (chat, calendar, workshop, event-intake, config console) and members got the generic Spanish error reply; Nova-backed image turns and the IG classifier's stage 1 kept working throughout, which is the signature to look for. 5xx classifies as `transient` so turns _were_ retried, but the retries hit the same dead endpoint. Emergency recovery was `LLM_TEXT_BACKEND=deepseek` + restart (v1.16.1). **Moonshot recovered within ~3 h**: probed 200 on `/models` + a live completion, then the full trial battery on the kimi path scored **8/8 tool-calling, voice 2/2, 0 leaks, 0/4 refusals, 13.8 s/turn** — so the brain went back to Kimi (the flat-rate coding subscription is already paid through its 2026-08-23 end; DeepSeek is metered). **Standing plan: on 2026-08-23, when the Kimi subscription lapses, set `LLM_TEXT_BACKEND=deepseek` permanently** — the key is already in `.env` and the cutover is proven (see the trial bullet below). Either direction remains a one-line `.env` change + restart.
   - **Why DeepSeek was the chosen replacement.** `scripts/text-backend-trial.ts` ran the same battery against both (2 runs each, 2026-08-10): **DeepSeek V4-Flash 7/8 tool battery, voice 2/2, 0 leaks, 9.1 s/turn** vs **Kimi 6/8, voice 2/2, 0 leaks, 33.5 s/turn**; a later 1-run check through the `LLM_TEXT_BACKEND=deepseek` path scored **4/4 at 7.3 s/turn**. The cutover run (2026-08-11, 2 runs, live `.env`) was the best yet: **tool-calling 8/8, voice 2/2, 0 leaks, 0/4 refusals, 8.2 s/turn** — including the `create` scene, which fails intermittently on **both** backends and is a pre-existing weakness rather than a DeepSeek regression, so don't read a single green `create` as it being fixed. Cost at measured volume (~11.1M in / 1.8M out per month): **≈$2/month worst case** on V4-Flash ($0.14/M in, $0.28/M out), less with cache — a repeated stable prefix hit **98%** (`prompt_cache_hit_tokens`), and cache-hit input bills at $0.0028/M.
   - **Pricing, and the 2026-08-16 repricing (read before doing any cost math here).** Per [DeepSeek's pricing page](https://api-docs.deepseek.com/quick_start/pricing/), USD per 1M tokens. **Through 2026-08-15:** Flash `$0.0028` cache-hit / `$0.14` cache-miss in / `$0.28` out; Pro `$0.003625` / `$0.435` / `$0.87` — i.e. **Pro is 3.1× Flash** on both miss-input and output. **From 2026-08-16 DeepSeek moves to peak/off-peak billing and raises rates**, off-peak being half of peak: Flash `$0.22`/`$0.44` miss-in and `$0.66`/`$1.32` out (off/peak); Pro `$0.66`/`$1.32` and `$1.98`/`$3.96`. That is **~3.1× the current input and ~4.7× the current output price for Flash**, so the "≈$2/month" figure above becomes **≈$3.6/month off-peak, ≈$7.3/month at peak** at the same ~11.1M in / 1.8M out volume. **Peak is 01:00–04:00 and 06:00–10:00 UTC** = **19:00–22:00 and 00:00–04:00 CST** — note the first window is exactly RevZ's evening Discord activity, so a real share of turns will bill at peak. Cache matters much more after the change: a stable system-prompt prefix hit **98%** in testing, and cache-hit input stays ~30× below miss.
   - **DeepSeek does NOT refuse RevZ-shaped political prompts** (0/4 refusals across repeated runs, where the content-filter ladder exists precisely because Moonshot 400s some of them). It _deflects in-band_ instead — the Tiananmen control answered "no he podido encontrar información sobre ese tema" with **HTTP 200**. Consequence: on `deepseek` the content-filter → Nova recovery ladder essentially never fires. No admin pages, no English error string, but also no Nova second opinion on CN-sensitive topics.
   - **Nova cannot be consolidated away.** DeepSeek V4 has **no vision on either tier** — `image_url` is rejected with `400 unknown variant 'image_url', expected 'text'` at the deserialization layer on both `deepseek-v4-flash` and `deepseek-v4-pro` (probed 2026-08-10, `scripts/probe-deepseek-api.ts` §8). Image turns and the IG classifier's stage 1 stay on Nova Lite regardless of the text backend.
   - **The Responses API is deliberately NOT used.** DeepSeek's Responses surface silently ignores `previous_response_id`, `conversation`, `store`, `background` and `metadata`, and takes no image/file input — so the server-side conversation state that would justify it does not exist, while ChopperBot rebuilds its window from Discord every turn anyway (`buildHistory`). Migrating would mean rewriting the agent loop for zero gain, and the silent-ignore behavior would make a future mistaken reliance on `store` fail quietly. Verified working but rejected: `scripts/probe-deepseek-api.ts` §§1–4.

Unit: `npx vitest run src/__tests__/config.test.ts`.
   - **A dev script that drives a mod-gated capability MUST pass `isAdministrator: true` into `buildTurn` (2026-08-13) — otherwise it grades the auth gate, not the model.** The privileged-capability gate added that day (`isModTurn`, fail-closed) reads `memberRoles`/`isAdministrator` off the turn context, and a synthetic ctx has neither, so `userTag: 'mod'` is a display name that grants nothing. The calendar then hands back the **3-tool read-only bundle instead of the full one** (8 tools that day; 9 since `calendar_set_session_theme` shipped later on 2026-08-13) (no `calendar_create_event` at all), and the battery reads **2/8 on every backend** — indistinguishable from a backend regression, except that the `dedup` scene still "passes" because doing nothing also fails to duplicate. Fixed in `text-backend-trial.ts`, `model-competition.ts`, `calendar-bedrock-smoke.ts` and `config-health-smoke.ts` (the console returns the unauthorized prompt and **zero** tools, so that smoke was asserting the deny path). Post-fix: **4/4 tool-calling, voice 1/1, 0 leaks, 0/4 refusals, 7.2 s/turn**. Two related harness traps found the same way, both of which read as model regressions: (1) a scene must pass the **capability's declared tier** (`effort: bundle.effort`, or `'medium'` for the general_chat voice scene, which declares none) — `ask()`'s own default is `'high'`, so an omitted tier silently measures thinking-on for turns production runs thinking-off; (2) **never put `\b` around an accented word** in a scorer regex — `\b` is ASCII-only in JS and the `u` flag does not change it, so `/\baquí\b/` can _never_ match and the voice check had quietly degenerated into a 3-keyword ASCII test that scored a flawless reply 0 for writing "server" instead of "servidor".
- **Effort tiers select a THINKING MODE, not a model (changed 2026-08-13).** There is **one text model — `deepseek-v4-flash` — for every text turn**; `ask()`'s `effort?: 'high' | 'medium' | 'low'` now maps to DeepSeek's `thinking` switch: **`high` → `thinking: {type:'enabled'}`** (reason before acting), **`medium` → `thinking: {type:'disabled'}`** (answer directly), **`low` → Nova Lite** (vision only, unchanged and unchangeable — no text brain can see). `textBackend.supportsThinkingSwitch` gates it, so a **kimi** deployment never receives the param (Moonshot 400s on unexpected params, as it already does for `temperature`) and the tier is a no-op there.
   - **Why not a bigger model for `high`.** V4-Pro was wired to `high` and removed the same day. Same script, same scenes, 2 runs each (`scripts/text-backend-trial.ts`): **Pro 7/8 tool-calling at 10.5 s/turn vs Flash 7/8 at 7.1 s** — identical accuracy, ~48% slower, **3.1× the price**; both missed the same `create` scene that fails intermittently on every backend. Don't reintroduce a model tier without re-measuring.
   - **What the switch is actually worth** (`scripts/probe-deepseek-thinking.ts`, v4-flash, 3 reps/variant): `type:'disabled'` → **0 reasoning tokens, 95 output tokens, 1.34 s**; thinking on → **111 reasoning, 207 output, 1.89 s**. That is a **~2.2× cut in billed output tokens and ~30% lower latency**, and tool-calling still succeeded **3/3** with thinking off. Reasoning tokens bill at the **output** rate, so on the post-2026-08-16 pricing this is the single biggest cost lever available — bigger than the model choice.
   - **`reasoning_effort` is NOT honoured on Flash — never send it.** Across the same reps, `low` produced _more_ reasoning than `high` (423 vs 149 mean), `max` landed between them, and a deliberately invalid value (`"banana"`) returned **200** and scored mid-pack. It is silently ignored in both the top-level and `thinking.reasoning_effort` spellings. A knob that never errors and never works is worse than none; only `thinking.type` is wired.
   - **Who gets `high`.** A capability declares its tier via `CapabilityTurnBundle.effort`; `discord/handlers.ts` passes `turn.effort ?? 'medium'`, so **the channel default is `medium`/thinking-off** (it used to be `high` for every channel turn). `high` is reserved for **multi-turn tool loops where a wrong call writes state**: **calendar** (search → create/update → sync), the **config console** (7 tool sources, mutates live config), **workshop** (the longest loop in the bot) and **event_intake** (the proposal a mod approves into a real event). Everything conversational — **general_chat**, the IG classifier decision, the announcer, workshop compaction — runs thinking-off, and that is essentially all the volume.
   - **Unit:** `npx vitest run src/llm/__tests__/effort-tier.test.ts src/__tests__/config.test.ts`. The test file pins the DeepSeek backend via `vi.hoisted()` **and asserts it did** — the first version gated on the live provider and silently skipped the two assertions that mattered.
   - Historical (2026-07-13 → 2026-08-13): `high` and `medium` were **both** the single text model, and the tier only distinguished text from the vision path. Since 2026-09-03 the overriding rule is **Nova reads, the text brain acts**: effort `low` is still a pure Nova call (`askBedrock` + `BEDROCK_MODEL_LOW`); every other image turn transcribes first. Usage today: **chat + calendar + event-intake = high**; **IG classifier = two-stage** (see below). The old `scripts/effort-experiment.ts` finding still holds — **vision text-reading is not a model differentiator** (Sonnet/Haiku/Nova all read a dense Spanish flyer perfectly) — so Nova Lite is a fine, cheap vision reader.
   - **IG classifier is two-stage (`classifyPost`, changed 2026-07-15) — Nova reads, Kimi decides.** Previously the classifier made ONE `ask()` call with the flyer cover attached, which (per the images-always-Nova routing) sent the _entire_ relevance/type/date decision to Nova Lite. Nova is a weak decider — it intermittently emitted the JSON schema wrong (e.g. the field value `"when": "null"` as a **string**, which the parser kept and `renderText` printed as a literal `Cuándo: null` on the card). Now: **stage 1** — if the post has a cover, `transcribeFlyer()` calls Nova Lite (`effort:'low'`, image attached) to _transcribe the visible flyer text only_; **stage 2** — `classifyPost` calls Kimi (`effort:'medium'`, text-only) with the caption **+ the transcription inlined** to make the decision. A failed/empty transcription is non-fatal (Kimi classifies caption-only), preserving the "never do worse than caption-only" guarantee — a post is never dropped for a bad cover. Defence in depth: `parseClassificationReply` also normalizes nullish string tokens (`null`/`none`/`n/a`/`sin fecha`/… accent+case-insensitive) → real `null` for `when`/`where` and `''` for `title`/`summary`, and the classifier system prompt explicitly says to emit JSON `null`, never the string. The scheduler logs one `instagram_monitor.classified` line per post (account, shortcode, media_type, had_cover, relevant, type, when, where, tags, reason) so a data-quality regression is visible in the journal without querying SQLite.
- **Kimi (`askKimi`).** OpenAI chat-completions loop: `system`+turns → `chat.completions.create`, `tool_calls` → run handlers → one `role:'tool'` message per result → repeat to `MAX_TOOL_ITERATIONS`, then a forcing pass **without `tools`**. **Thinking-mode gotcha:** every assistant turn (incl. `tool_calls` turns) returns `reasoning_content`, and the gateway **rejects follow-up requests that don't echo it back** — so the assistant turn is pushed back into history _with_ its `reasoning_content`. **No `temperature`** is sent: the kimi-for-coding endpoint 400s on any value except 1. **UA gate:** the coding endpoint 403s requests whose `User-Agent` isn't a known coding agent ("Kimi For Coding is currently only available for Coding Agents…"); `KIMI_USER_AGENT` defaults to `claude-cli/1.0.0`, which is empirically on the allowlist. Config: `KIMI_API_KEY` (required), `KIMI_BASE_URL` (default `https://api.kimi.com/coding/v1`), `KIMI_MODEL_ID` (default `kimi-for-coding` = K2.7 Thinking; use `kimi-k2-thinking` on the plain platform API `https://api.moonshot.ai/v1`). **Empty-content retry (2026-08-06):** K2.7 Thinking occasionally spends every output token on `reasoning_content` and returns empty `content` with `finish_reason: 'stop'` — observed live when two mentions overlapped, and the user got the old English fallback as the reply. `askKimi` now drops the empty assistant echo and retries the same convo up to `MAX_EMPTY_RESPONSE_RETRIES` (2) times; if it still comes back empty, the reply is the shared Spanish `EMPTY_RESPONSE_FALLBACK` ("No pude generar una respuesta esta vez…"), which the Bedrock path now uses too. Covered by `src/llm/__tests__/kimi-retry.test.ts`. **Length-cap + thinking (2026-09-02, v1.28.2):** DeepSeek `high` can spend the entire `max_tokens` budget on reasoning and return empty `content` with `finish_reason: 'length'` — live workshop turn: 3 iterations, 0 tools, 49151 output tokens (= 3 × 16384), member got the fallback. The empty retry now **disables thinking** after a `length` miss, and the forcing pass also runs on `length` (it used to only run for `tool_calls` / degenerate). Covered by `kimi-retry.test.ts` + `effort-tier.test.ts`. **Forcing-pass hardening (2026-08-06, v1.13.0):** the tools-free forcing pass now ALWAYS carries the prose nudge (previously only for degenerate output) and gets **one bounded retry** — live, a workshop whole-book summary burned all 10 iterations on tool calls and the forcing pass still came back `finish_reason: 'tool_calls'` (Kimi keeps calling tools from history even with none advertised), so the user got the empty fallback. Covered by `src/llm/__tests__/kimi-forcing.test.ts`. **Anti-hallucination clause (2026-08-09, v1.15.0):** the nudge now also forbids claiming sends/actions that weren't executed this turn — a cap-reached workshop turn replied "te envío el archivo corregido" with NO file attached (the docx didn't even exist yet), and the member chased it for six messages. If something stayed pending (e.g. a generated file that never got sent), the forced answer must say so explicitly and suggest the next step.
- **Content-filter recovery in `ask()` (added 2026-08-06) — the ONE sanctioned exception to "Nova is images-only".** When Moonshot's risk filter refuses a text turn (see the `content_filter` bullet under "LLM health"), `askKimi` rethrows it as a `ContentFilterRejection` and `recoverFromContentFilter()` runs a three-step ladder: **retry Kimi once → `askBedrock` (Nova Lite) → the Spanish `CONTENT_FILTER_FALLBACK`** ("El filtro del proveedor del modelo bloqueó esa pregunta…"). The retry comes first because the filter is **probabilistic, not a verdict on the text** — the prompt that broke live answered normally on replay minutes later, as did the same question about Israel (`scripts/probe-content-filter.ts` demonstrates both). Nova comes second because refusing this community's actual subject matter is worse than answering it in a weaker voice; it fires rarely enough (2 rejections on day 1 of general_chat v1.10.0) that the metered cost stays a rounding error — so this does **not** reopen Nova for text generally, and nothing else should route text there.
   - **The hard constraint: never retry after a tool has run.** Both recovery legs restart the agent loop from scratch, so a rejection that arrives _after_ `calendar_create_event` executed would create the event twice. `ContentFilterRejection` carries `toolCallsExecuted` (read at throw time) and a non-zero count skips straight to the Spanish message (`llm.content_filter.no_retry_after_tools`). A rejection on the first request — the common case — has executed nothing.

Live: `npx tsx scripts/probe-content-filter.ts [--bedrock]` (fires candidate prompts at the real gateway to see what it currently refuses — the filter's behavior drifts, so re-probe rather than trusting a past result) and `npx tsx scripts/simulate-content-filter.ts` (stands a local always-400 server in for the Kimi endpoint via `KIMI_BASE_URL` and asserts the whole shipped ladder: 2 upstream hits, a **real** Nova answer, and `degraded=false`). - **The generic turn-failure reply is Spanish** (`GENERIC_ERROR_REPLY` in `discord/handlers.ts`): "Se me atravesó un error al responder eso…". It replaced a hardcoded English `Sorry, I hit an error answering that — check the logs.` that shipped to a community channel during the 2026-08-06 incident. Anything user-facing in that catch block lands in front of members, not operators — no English, no log instructions.
- **Bedrock vision model** (`BEDROCK_MODEL_LOW`, default `us.amazon.nova-lite-v1:0` via the **us cross-region inference profile**) — the single, images-only model. Nova is enabled by default for the account (no model-access request needed, unlike Claude/Qwen). `BEDROCK_MODEL_ID` (Sonnet 4.6) is now **legacy** — off every hot path, kept only for the dev smoke/bake-off scripts and an all-Bedrock rollback. (`BEDROCK_MODEL_MEDIUM` was removed 2026-07-13 — medium is Kimi now.) Historical bake-off context (2026-06-23, `scripts/model-competition.ts`): for the _text/calendar_ path Sonnet was cleanest and Nova corrupted recurring edits + leaked `<thinking>` — which is exactly why the text brain is now Kimi, not Nova; Nova is only trusted for the vision _reading_ task where it's reliable.
   - **Why images don't just use the Kimi key too (investigated 2026-07-14 — don't re-investigate).** Two hard blockers, both verified: (1) the coding endpoint the text brain uses (`api.kimi.com/coding/v1`, `kimi-for-coding`) **does not expose image input via the API at all** — the "watch a screen recording/clip" feature the kimi-code CLI advertises is client-side only, not an API capability. (2) Kimi's vision models (`kimi-k2.5`, `moonshot-v1-*-vision-preview`, even `kimi-k2.7-code`) live only on the **Open Platform** (`api.moonshot.ai/v1`), and the deployment's `sk-kimi-…` coding-plan key is **rejected there with `401 Invalid Authentication`** (tested live against 3 vision models × both regions on 2026-07-14). The `sk-kimi-` prefix = a Kimi-For-Coding _subscription_ key, scoped to the coding endpoint; the Open Platform is a separate, pay-per-token product needing a distinct `sk-…` key. So "one key for everything" is impossible today. **Nova Lite stays because it's also just cheaper:** at the real live load (~37 IG-classifier image calls/day — now the two-stage _transcription_ call, ~2.6k input + a few hundred output tokens each; the classifier is essentially the _entire_ Nova load — chat-with-image turns are ~0) Nova costs **≈ $0.22/month** (the two-stage split's added stage-2 *text* call rides the flat Kimi coding subscription, so it adds no metered cost) ($0.06/$0.24 per Mtok; the logged `agent_turn` `inputTokens` already includes the image, so no separate image-token math). The same volume on `kimi-k2.5` vision ($0.60/$3.00 per Mtok) would run **≈ $2.30/month (~10×)** _and_ add a second key + metered billing — purely to delete a 22-cent AWS line item. Verdict: keep Nova for images.
- **Auth is an IAM access-key pair**: `ACCESS_KEY_ID` + `SECRET_ACCESS_KEY` (+ optional `AWS_SESSION_TOKEN`), region `AWS_REGION` (default us-east-1). The var names are deliberately **un-prefixed** (not `AWS_ACCESS_KEY_ID`) so they don't collide with an ambient AWS CLI credential on the host. The IAM principal needs `bedrock:InvokeModel` on both the foundation-model ARN **and** the inference-profile ARN (a cross-region profile routes to us-east-1/2 + us-west-2, so the foundation-model resource must be region-wildcarded). The live deployment authenticates as an IAM user in the **operator's personal AWS account** — deliberately NOT the shared/work account — whose inline policy grants that on the `amazon.nova-*` (plus the legacy `anthropic.claude-*`) foundation models and their `us.`/`global.` inference profiles, so Nova Lite is already permitted (verified live 2026-07-13). A missing permission surfaces as `AccessDeniedException` (403) — `classifyLlmError` treats it as deterministic and pages the config channel on the first failure. Kimi errors carry the HTTP status on `.status` (OpenAI SDK) and are classified the same way. (Account IDs, ARNs and access keys live only in `.env` — never in this repo.)
- **No `temperature` sent.** The client passes only `inferenceConfig.maxTokens` (= `MAX_OUTPUT_TOKENS`); sampling params are left at the model default.
- **Tool loop contract.** On `stopReason === 'tool_use'`, the assistant turn (with its `toolUse` blocks) is echoed back into history verbatim — Converse requires the originating `toolUse` block be present for the matching `toolResult` to validate — then one **user** turn carrying one `toolResult` block per call is appended. **Forcing pass (fixed 2026-09-03, v1.28.2):** the OpenAI-style trick of re-sending **without `toolConfig`** is **illegal on Converse** whenever history still has `toolUse`/`toolResult` blocks — AWS 400s `"The toolConfig field must be defined when using toolUse and toolResult content blocks."` Live: calendar channel, flyer attached, Nova looped `calendar_draft_announcement` 10× (3 real publishes), forcing pass 400'd, member got the empty fallback, health watchdog paged a false "error de configuración". The pass now **flattens** those blocks into text (`flattenBedrockMessagesForForcing`), omits `toolConfig` (now legal), carries the same prose nudge as Kimi, and gets one bounded retry. Covered by `src/llm/__tests__/bedrock-forcing.test.ts`. **Empty-content retry (2026-08-13, v1.18.1):** Nova sometimes closes a tool loop with `stopReason: 'end_turn'` and **no text block at all** once the tool results land — observed live on a calendar image turn that created + synced + published the event (all six tools succeeded) and the member still got the `EMPTY_RESPONSE_FALLBACK`. `askBedrock` now mirrors the Kimi path: the empty assistant echo is dropped and the same convo is retried up to `MAX_EMPTY_RESPONSE_RETRIES` (2) times before the fallback. A retry that re-emits an identical tool call is served from the per-turn `toolCache`, so the retry itself can never double a write. Covered by `src/llm/__tests__/bedrock-retry.test.ts`.
- **Image turns are two-stage (2026-09-03, v1.28.2) — generic, not just the IG classifier.** Before this, `ask()` sent **the whole turn** (calendar tools, workshop Python, …) to Nova Lite the moment an image was attached. Nova is a weak tool-caller: the calendar flyer turn above is the proof. Now: **stage 1** Nova transcribes/describes (`effort:'low'`, no tools); **stage 2** the selected text brain runs the original tools with the transcription inlined and the pixels stripped. Effort `low` stays a pure vision call (the IG classifier's stage 1 is unchanged). A failed/empty transcription still strips the attachments — otherwise `ask()` would recurse — and the text brain answers from the user's words. Covered by `src/llm/__tests__/client.test.ts`.
- **`<thinking>` strip + image fixtures gotcha:** `extractText()` strips any `<thinking>…</thinking>` a model inlines into the visible reply (Nova leaks it; Claude doesn't) so raw reasoning never reaches Discord. Bedrock also rejects degenerate 1×1 images ("may not meet the required format"); real IG flyer covers are full-size and fine — the smoke test synthesizes a real 64×64 PNG for the vision check.

## Image attachments (vision input, `src/attachments/`)

The bot accepts **images only** — `resolveAttachments()` drops anything that isn't `png`/`jpeg`/`gif`/`webp` (detected by content-type first, then file extension) with a `Unsupported attachment type, skipping` warning. It is called in `handlers.ts` _before_ `buildTurn()` and attaches the resolved images to the user `Turn`. Caps (config): `MAX_ATTACHMENT_COUNT` (5 — extras silently ignored) and `MAX_ATTACHMENT_BYTES` (10 MB — oversize skipped); downloads have a 30 s abort timeout and a failed download is logged, not fatal. `ImageAttachable` is provider-neutral (just `bytes`/`mimeType`/`format`); in `llm/client.ts`, `buildMessage()` emits a Converse content array (a `{ text }` block + one `{ image: { format, source: { bytes } } }` block per image) **when attachments are present**, else a single `{ text }` block. Attachments ride only the _current_ user turn; history turns reconstructed by `buildHistory()` carry text only. On a `high`/`medium` turn they never reach the text brain as pixels: `inlineImageTranscriptions()` asks Nova first and inlines the description (journal: `llm.vision_inlined` / `llm.vision_transcribe_failed`).
