# Framework internals

> Topic doc — part of the [CLAUDE.md](../CLAUDE.md) router. Read it BEFORE working in this area, and keep it current in the same change as any behavior change (doc protocol ①/② in the index).

The cross-cutting machinery every capability rides on: boot, the per-turn pipeline, tool composition, persistence, routing.

## Boot sequence (`src/app.ts`)

1. Open shared SQLite at `data/chopperbot.db` (WAL, FK on).
2. Migrate the framework `users` directory and moderation settings/trail (reserved capability id `__framework__`; moderation tables use the `framework_` prefix).
3. Instantiate the candidate capabilities, call `init()` on each **before Discord login**. A capability that throws is skipped; the bot continues with the rest.
4. Load channel→capability bindings: env-var seed → DB (via `ConfigurationCapability.bootStore()`) → build router.
5. Construct the Discord client, register handlers, `client.login()`.
6. Call each capability's optional `start()` for background work (instagram_monitor's scheduler starts here).

**Lazy deps gotcha:** `CapabilityInitDeps` exposes `getDiscordClient`, `getRegistry`, `getRouter`, `getUserDirectory` as **getters that throw if called during `init()`**. They are only safe to invoke at `buildTurn()` time (post-bootstrap). This is by design — capabilities that need them (configuration) capture the getters in `init()` and call them later.

## Per-turn flow (`src/discord/handlers.ts` → `src/llm/client.ts`)

0b. **Conversation styles — `TurnPresenter` (v1.17.0, `src/discord/presenter.ts`).** How progress and the reply reach the user is a per-surface presenter the pipeline drives blindly (`onQueued`/`begin`/`onPhase`/`deliver`/`fail`/`discard`). Two styles ship: **public channels → `ReactionTurnPresenter`** — status reactions on the user's message + the native typing indicator (refreshed every **5 s**, kept alive until the first reply chunk actually posts — at 8 s a busy Pi event loop let Discord's ~10 s indicator lapse mid-turn and a member read it as "se trabó", live 2026-08-06) and **no extra bot messages, ever** (the v1.12.0 20 s escalation to a status line was removed 2026-08-11 by user directive — the rich status belongs to talleres); the reply is a normal Discord reply so `buildHistory`'s reply-chain walk keeps working, with a channel-send fallback if the user's message is gone. **Workshop sessions → `WorkshopTurnPresenter`** — the live status line that morphs into the reply (see docs/capabilities/workshop.md). `chunkBotReply` still caps a reply at `MAX_REPLY_CHUNKS` (5) with a Spanish truncation note. Presenters are tested against a fake-message op log (`src/discord/__tests__/presenter.test.ts`).

0. **Turn queue + status reactions (added 2026-08-06, v1.11.0).** Every message-driven turn (main handler AND workshop sessions — one shared `TurnQueue` built in `app.ts`) runs through `src/discord/turn-queue.ts`: strict **FIFO per channel** (a queued turn builds its history only when it starts, so it sees the previous reply) and at most `MAX_CONCURRENT_TURNS` (3) executing across channels; a >5-deep channel backlog gets the polite `QUEUE_BUSY_REPLY`. Separately, `DEEPSEEK_MAX_CONCURRENT` (default **3**) gates concurrent LLM HTTP _requests_ inside `llm/client.ts` (`gate.ts` semaphore, FIFO with atomic slot handoff) — requests, not whole turns, so two agent loops interleave. This is the fix for the live 2026-08-05 failure where two overlapping mentions made one turn return empty content; it used to be `1` because the retired Kimi coding endpoint degraded under overlap, and `3` is a Pi-protection knob, not a provider limit (DeepSeek's own concurrency ceiling is 2500). Progress is shown as a **status reaction** on the user's message (`status-reactions.ts`, replaces the old single 🔍): ⏳ queued → 🤔 thinking → 🛠️ tool running → removed on success / ❌ kept on failure, driven by the `onPhase` callback `ask()` now accepts.
1. Message arrives. The main handler never responds to webhook authors or in the known log channels `1436112159829397564` / `1436110972602417253`, even when mentioned or bound. Otherwise it responds only if addressed in an authorized channel: a real @-mention, a reply to one of its own messages, or — since **v1.17.1** — the **plain-text form `@ChopperBot`** (bot username or its guild nickname, case-insensitive, the `@` required, name must not continue into a longer word). Copy-pasting a mention from another message pastes it as literal text with no mention entity (`message.mentions` stays empty), so members "mentioning" the bot that way got silently ignored — live 2026-08-11 in the general channel ("wtff"). `stripBotMention` strips the plain-text form too (pass `message.guild` so the nickname is known); a bare `chopperbot` without `@` still does NOT trigger — that's someone talking _about_ the bot.
2. `userDirectory.upsert()` registers the Discord user (lazy, idempotent — bumps `last_seen_at`).
3. `buildHistory()` walks the reply chain backward (max 8 turns / 16k chars), strips the `_…sigue ↓_` continuation footer from bot turns, and reverses to chronological order. `normalizeTurns()` then merges consecutive same-role turns and — since **v1.16.0** — **folds** any _leading_ assistant turns into the first user turn as a quoted `[Contexto — mensaje anterior de ChopperBot…]` block instead of dropping them. That drop was silently fatal for **bot-initiated** threads: the calendar's "falta crear el evento de Discord" nudge, the daily announcement and admin alerts all speak first, so a mod replying to one produced a window whose only history turn was that bot message — deleted, leaving the model a context-free `"crea el evento"`. Live 2026-08-10 (`historyTurns: 1`, `toolCalls: 0`): the bot answered its own nudge about event #29 with "¿qué evento quieres crear?" and asked for a title and a date it had itself just published. The API constraint is only that the sequence _start_ with a user turn — that never required destroying content.
   3b. **Turn authority (added 2026-08-13).** `resolveAuthority()` snapshots WHO is asking — the author's guild roles (`memberRoles`) + whether they hold Discord's Administrator permission — onto `CapabilityTurnContext`. Roles come from the MESSAGE_CREATE partial member (no privileged GuildMembers intent: the ids resolve against the role cache the Guilds intent already fills; `message.member` missing → one `members.fetch`, and a failure leaves `memberRoles` **undefined**). Capabilities read it through one of **two tiers** in `src/capabilities/mod-authority.ts` (since v2.3.1, see [Authority tiers](#authority-tiers--v231-2026-10-04)): **`isModTurn(db, ctx)`** = moderation (console, IG mutations, review, bans) and **`isEventTurn(db, ctx)`** = events (calendar writes, ticket approval, flyers, event pings, minutas). Both **fail closed**: `undefined` roles is "not a mod", never "no roles, therefore fine"; bot authors never pass. `isModCaller` in `mod-roles.ts` is the pure gate underneath.
   3c. **Turn context beyond the words (added 2026-09-23, v2.2.0; `src/discord/turn-context.ts`).** From the general_chat audit (525 turns, ~24k channel messages read back), the handler now builds the user turn as more than `message.content`: `composeUserText()` resolves `<@id>` to `@Name`, adds `[sticker: …]` / `[adjuntó un archivo que no puedes abrir aquí: x.pdf]` notes, and turns an **image-only** mention into `(mandó una imagen sin texto)` — the old `if (!userText) return` ran _before_ attachments were looked at, so a sticker- or image-only mention got no reply at all. The **replied-to message's images** ride the live user turn (history stays text-only, and DeepSeek 400s on images in assistant turns), labelled by `parentImagesLabel()` and added to `ctx.attachments` so the calendar can use a flyer a mod replies to as a Discord cover; REST re-signs the CDN URL on fetch, so an old parent's image still downloads. A capability that sets **`channelContext = true`** (today only general_chat) also gets the thread title + opening post (`renderThreadContext`) and ambient messages. The original ≤10-message/10-min/2k non-reply window was replaced by step 3d below. `ctx.userDisplayName` carries the asker's server name. `Answering question` includes `channelId` and `contextBlocks`. Tests: `src/discord/__tests__/turn-context.test.ts`.
   3d. **Wider conversation context (2026-10-04, v2.3.0; `src/discord/conversation.ts`).** Opted-in turns, **including replies**, get ≤100 preceding messages within 30 days of the trigger, capped at **32k serialized characters**. Quoted JSON retains author, UTC date, reply ID and URL; historical images remain text notes. Reads require fresh caller/bot ViewChannel + ReadMessageHistory; private-thread membership is checked. Fetch failure loses ambient context, never the turn. General_chat adds paginated read/search tools with shared 20-page/300k-character per-turn limits and explicit coverage/cursors; restricted history stays within its own channel, except in the verified moderation workspace under the audience-containment proof below. Ambient text remains untrusted and cannot authorize writes: `ctx.requestText` and `ctx.messageId` carry **only the current trigger**, independently from the augmented user turn. General_chat's sole sanction is a ban bound to a standalone current mod command, with original-message/live-authority/hierarchy rechecks at effect time (see [general-chat.md](capabilities/general-chat.md)); calendar/config still do not opt in. Serious current member reports may additionally send a bounded escalation note to the moderation workspace; ambient/history text cannot authorize that send. Logs: `conversation.recent_context`, `conversation.history_read`, `conversation.history_failed`, `moderation.member_banned`, `moderation.ban_refused`. Tests: `src/discord/__tests__/conversation.test.ts` + general_chat tool tests.
4. `capability.buildTurn(ctx)` returns `{ system, tools }` for _this_ message. Capabilities decide whether to rebuild every turn (calendar embeds an upcoming-events snapshot, configuration embeds current time) or cache. **Privileged capabilities gate here, by omitting tools from the payload** rather than by asking the model to behave: configuration → zero tools for a non-mod, calendar → read-only slice, instagram_monitor → the mutating `monitor_*` tools removed (each also re-checks at the point of effect). A tool the model was never handed cannot be jailbroken into existence; a prompt rule can. Who passes today: `npx tsx scripts/verify-mod-authority.ts`.
5. `ask({ system, messages, tools })` drives a multi-turn agent loop on the **single** `deepseek-flash` backend (natively multimodal, so an image simply rides the same request as the tools). `effort` picks how hard that one model thinks: `low` (thinking disabled) for the IG classifier, the calendar announcer, minutas and workshop compaction; `high` for calendar, event_intake and the config console **and as the default when a capability declares nothing**; `max` for workshop turns only. `medium` still parses as a legacy alias for `high`. `general_chat` declares `low` for chat/history/reviews and the generic branch; only a current explicit authorized moderator ban uses `high`. Within a single `ask()` call, identical `(toolName, JSON-stable-input)` tool calls are deduplicated from a per-turn cache (only successful results are cached).
6. If the loop runs out of iterations while still emitting tool_calls, a final **forcing pass** extracts a text answer by re-sending **without `tools`** plus a prose nudge, with one bounded retry. The pass also runs when a thinking turn hits `finish_reason: 'length'` with empty content (thinking ate the budget; live 2026-09-02 workshop), and thinking is disabled for that retry. **History:** the deleted Bedrock Converse loop needed a `flattenBedrockMessagesForForcing()` workaround — omitting `toolConfig` while history still carried `toolUse`/`toolResult` was a ValidationException (live 2026-09-03) — and a pre-v4.1 tools-free pass could also be defeated by a model that kept calling tools from history. Neither applies to the OpenAI-compatible wire shape, and the per-turn tool cache still makes a re-emitted identical write call harmless.
7. Long replies are split by `chunkBotReply()` — markdown code fences are preserved across chunk boundaries (closed with ``` and reopened with the same language tag); non-tail chunks get the `_…sigue ↓_` footer so users know to reply to the last message.

## Mentions — the bot-wide policy (added 2026-08-13)

`createClient()` sets **`allowedMentions: { parse: ['users'], repliedUser: true }`**. Without it discord.js omits `allowed_mentions` entirely and Discord parses **every** mention class in whatever the model wrote — and since the bot was granted **Administrator** in the guild, every role is pingable, so one successful jailbreak (or one hostile Instagram caption echoed into a card) would ring the whole server. The rule against mass pings previously existed only as a sentence in `general_chat`'s preamble: a promise, not a gate.

Two consequences to keep in mind when writing a new send:

- **A message-level `allowedMentions` REPLACES the client default; it does not merge.** So `{ repliedUser: false }` alone silently re-opens @everyone. Anything that passes its own policy must respell the safe parts — `presenter.ts` (`SEND_MENTIONS`) and `admin-alert.ts` do.
- **Legitimate role pings opt in by id**, never by `parse: ['roles']`: the calendar announcement + mod nudge and event_intake's mod ping pass `roles: [...]` allowlists built by `resolveModMentions`. `sendAdminAlert(client, lines, tag, roleIds)` takes that allowlist for the nudge's fallback path. The Instagram publisher goes the other way — `parse: []`, nothing in an attacker-authored card may ping at all.

## Moderation workspace and evidence (v2.4.0)

`framework_moderation_settings` is per guild. For RevZ, absent configuration defaults `moderation_channel_id` to `1436206995140247652`; escalation ping IDs default to `[]`. `config_moderation` changes these live; it accepts restricted text/news destinations, rejects log channels, and verifies the requesting moderator again at execution. This workspace remains a variant of general_chat in an **unbound** channel, not a new capability or binding.

At `buildTurn`, profiled general_chat injects `BotSelfKnowledge`: roles and effective Administrator/BanMembers/ModerateMembers/ManageMessages/ViewAuditLog from `guild.members.me`, deterministically sorted and cached per guild for 60 seconds. The prompt contains no expiry timestamp. Members get a truthful short version; only moderation gets exact roles, permissions, command syntax and limits. Current implemented sanction: code-verified explicit ban only. The bot never relays commands to other bots, implements no timeout yet, and explains that entry alerts require the privileged GuildMembers intent (disabled).

`PartnerAccess` requires the configured channel, live moderation authority, caller/bot ViewChannel + ReadMessageHistory, and a destination hidden from @everyone. Protected history pages then prove **every possible destination viewer can view and read the source**, rather than merely checking the requester. `audience.ts` aggregates all possible non-Administrator role combinations as at most 4,096 permission signatures, applies everyone → aggregated role deny/allow → individual deny/allow, and checks raw role IDs from single-member GETs for every user overwrite in either channel. Owners/Administrators bypass both channels. Missing roles/users, unsupported overwrites, inconsistent grants or a counterexample fail closed. Additional restricted cross-channel reads support text/news channels; private-thread access stays on the existing own-channel membership path. Public callers receive no exception.

Audit reads use the same proof with guild ViewAuditLog as the source audience. Partner-only `server_audit_log` reads at most 50 slots / 15k serialized entry characters per call and 3 pages per turn, supports type/actor/target/before, and declares approximate 45-day retention and partial coverage. History keeps its existing 30-day/100-message/character budgets; only verified partner reads include bot/webhook log text and embed fields, bounded at 4k per message. These are quoted evidence, never current instructions. `verifyDelivery` repeats authority/settings/audience checks after protected evidence is read; revoked access replaces the answer with a safe explanation. Discord has no atomic read/permission/send transaction, so a final network race remains.

Public member reports expose `server_escalate_report` only for an eligible **current** trigger in a community-visible channel. The model chooses a serious high-confidence alta/urgente report; obvious joke markers fail in code. Trigger content/author/edit state and current source permissions are rechecked, targets are restricted to current mentions, and routing identities are fixed. Reservations dedupe by trigger/action/target and enforce reporter 30-min, source-channel 5-min and 20/guild/UTC-day caps across restarts. A second genuine report may be suppressed during cooldown; tickets remain available. Default send policy is `{parse: [], users: [], roles: [], repliedUser: false}`; opt-in escalation roles are at most four configured existing moderation-role IDs. Notes/logs use stable nonces to prevent Discord REST retries duplicating sends.

`framework_moderation_trail` stores guild, requesting actor, target, action, short reason/summary, trigger ID, source channel, outcome and timestamp. It is an action trail, not a message-content archive. Ban requests are reserved before effects; success is recorded before mod-log delivery. Verified refusals stay in SQLite without a Discord line. `refused:effect_unconfirmed` / `refused:delivery_unconfirmed` represent unconfirmed results, **not proof that Discord applied nothing**, and are never automatically replayed. A failed mod-log delivery logs `moderation.mod_log_delivery_failed` and does not change an executed action into failure. Caller permission remains moderation; protected targets remain the wider events tier.

## The Spanish voice contract (`src/lang/`, added 2026-08-13, v1.19.2)

How the bot _sounds_ is framework state, not per-capability taste. Three pieces:

- **`voice.ts` — `SPANISH_VOICE_RULES`.** One block, interpolated verbatim into every community-facing system prompt: calendar (mod + read-only), general_chat (generic + assistant + moderation partner), workshop, event_intake (proposal + ticket), instagram_monitor, and the daily calendar announcement. It fixes the register (**tuteo**, never usted), the inclusive forms the community actually uses (`lxs`, `todxs`, `bienvenidx`, `amix` — but never an invented pronoun like `elx`/`unx`/`lx`), the ban on quoting its own rules (ALL-CAPS emphasis, tool/field names), service-desk closers, and enclitic accents. `src/lang/__tests__/voice-contract.test.ts` fails if any of those prompts drops it. **Not** applied to `configuration` (operator console — its prompt tells it to name tools out loud).
- **`spanish-style.ts` — `lintSpanish()`.** Deterministic, high-precision rules for the same defects, over prose only (code fences, inline code, URLs, mentions and custom emoji are masked out). Rules: `usted`, `mixed_register`, `inclusive_malformed`, `scaffolding`, `service_closer`, `enclitic_accent`, `spanglish`. It grades known defects, never taste — a false positive is worse than a miss, since it runs on every live reply.
- **`report.ts` — `reportSpanishStyle()`.** Called at each delivery site (`discord/handlers.ts`, workshop watcher, event_intake proposal + ticket turns). Logs `style.spanish_voice_drift` at warn level with the rules and snippets; never edits or blocks a reply. `journalctl --user -u chopperbot | grep style.spanish` is the drift alarm.

**Why:** the 2026-08-13 backend cutover held tool-calling parity and changed the voice the same afternoon — one calendar reply carried usted (`se le habla`), an invented pronoun (`para elx`) and a verbatim prompt rule (`le pregunto UNA cosa a la vez`). Nothing in the suite could see it. The regression corpus in `src/lang/__tests__/corpus.ts` is the real transcript of that channel, both backends' replies, joined to their backend by journal timestamp.

**Changing the model?** `scripts/spanish-voice-probe.ts` replays the scenes that broke — including the exact turn that shipped the bad reply — against the live backend. Run it before switching `.env` (the retired `scripts/text-backend-trial.ts` parity battery went with the v4.1 migration; its replacement evidence is the `scripts/probe-deepseek-v41-*.ts` set plus that voice probe).

## Capabilities and tools

Each Capability composes one or more `ToolSource`s via `composeToolSources()` (`src/tools/source.ts`). Tool specs are **provider-neutral** (`{ name, description, inputSchema }`); the LLM client is the only place that knows how to wrap them into the OpenAI-compatible chat-completions `tools` shape. Tool name collisions across sources fail at boot — fix the duplicate, don't suppress.

## Persistence

Single SQLite file, **one row per capability+version in `_migrations`** (see `src/memory/migrations.ts`). Each capability owns its tables by **id-prefix convention** (`calendar_events`, `instagram_monitor_accounts`, `configuration_bindings`) — the framework does not enforce this, but the `configuration` capability's admin tools rely on it for scoped inspection.

`NamespacedMemory` wraps the shared store for one capability: it forwards `db()` to the raw handle but fixes `capabilityId` on `migrate()` so a capability cannot migrate another's tables. `__framework__` is reserved for the user directory and shared moderation state. Its v2 migration owns `framework_moderation_settings` and `framework_moderation_trail`; the explicit `framework_` prefix identifies shared ownership and keeps these records outside capability-scoped purges. The workspace is shared by general_chat, delivery and the console, so it does not belong to event_intake.

## Routing

`src/capabilities/routing.ts` builds a `MutableCapabilityRouter` from an initial channel→capability map. The `configuration` capability holds the only reference that can call `setBinding`/`removeBinding` — read-only consumers type their dep as the parent `CapabilityRouter`. Bindings are persisted to SQLite, so live re-bindings from chat survive restarts; **no bot restart needed when re-binding a channel.**

## Authority tiers — v2.3.1 (2026-10-04)

`mod-roles.ts` owns the pure matcher and the two default lists. `isModTurn` now means **moderation**: Administradora `1483734077944365149`, Administrador `1436259908222713917`, Técnico `1517610228969902130`, Moderación `1436055845392879778`, or Discord Administrator. Bot callers never qualify. `isEventTurn` means effective moderation plus the configured/default **events** list (defaults additionally include Gestión `1483694810253492235`). Missing authority fails closed.

The console, IG mutations, reviews and bans use moderation; the ban executor's *protected-target* check uses the wider events tier, so the bot is never the instrument against Gestión staff either. Calendar writes/broadcasts, intake approval, flyer staff operations, event pings and minutas commands use events; Agitprop retains its separate flyer authorization. Effective event pings inherit custom moderation roles too.

Migration event_intake v3 preserves `mod_roles_json` as the event setting and adds `moderation_roles_json`, initialized empty (safe moderation defaults, never copied from the old mixed list). `set_mod_roles` remains the compatible event-setting alias; `set_event_roles` and `set_moderation_roles` are explicit. Empty lists mean defaults. Health exposes `authority.{moderation,events}` with effective IDs and configured/default source.

Proof: 112 files / 1,334 tests, typecheck/build green; service active and `Discord client ready` after deployment. Read-only live verification confirmed two Gestión-only callers: events true, moderation false; the bot: false for both. No sanctions or test posts. `npx tsx scripts/verify-mod-authority.ts [memberId…]` reports both tiers without member listing or content output.
